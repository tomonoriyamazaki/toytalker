# RTX 5090 Qwen3-TTS 内部時間の実測（2026-09-12）

生成処理の約81%をトークン生成、約19%を波形デコードが占めた。入力準備やその他の処理は小さい。次の速度改善はトークン生成を中心に調べる。今回測ったのは処理区間の壁時計時間であり、5090の演算能力・帯域の限界を確定する測定ではない。

## 条件と比較結果

Qwen3-TTS 1.7B、faster-qwen3-tts 0.2.6、chunk_size=4、vivian、同じ41文字の短文。各モードで単独要求をウォームアップ1件＋測定5件。元のAPIをインポートする別プロセスをlocalhost:8001で動かした。通常8000番APIと監視タスクは測定中のみ停止し、同じGPU上でモデルが重ならないようにした。

| 指標 | 計測なし | 内部計測あり |
|---|---:|---:|
| 成功 | 5/5 | 5/5 |
| 初回PCM受信 p50 | 0.734秒 | 0.743秒 |
| 初回PCM受信 p95 | 0.753秒 | 0.770秒 |
| 完了時間 平均 | 2.248秒 | 2.279秒 |
| 生成音声秒 / 実時間秒 | 3.181倍 | 3.159倍 |
| 模擬再生の枯渇 | 0件 | 0件 |
| GPU使用率 平均 | 82.4% | 81.8% |
| GPU消費電力 平均 | 168.1W | 169.2W |
| GPUメモリ 最大 | 7,790MiB | 7,742MiB |

生成倍率はAPIが末尾に追加する0.5秒の無音を除外。GPU値は各要求の実行区間に入った約1秒間隔のサンプル（各10点）で、GPU全体の値。GPU使用率82%を「最大演算性能の82%」と解釈しない。

音声秒数で正規化した処理時間の差は計測あり側が約0.70%増。今回は少数標本で生成乱数も固定していないため、これを厳密な計測オーバーヘッドと断定しない。大幅な速度低下は観測されなかった。

## 内訳

ウォームアップを除く5件の平均。生成音声は平均7.20秒。区間の前後でCUDA同期を行い、CPU処理・GPU処理・待ちを含む時間を測った。

| 区間 | 1要求あたり平均 | 生成処理の占有時間に対する割合 |
|---|---:|---:|
| 入力準備 | 0.0018秒 | 0.08% |
| トークン生成（prefillを含む） | 1.8277秒 | 80.89% |
| 波形デコード（最後の全体デコードも含む） | 0.4281秒 | 18.95% |
| その他の生成処理・計測処理 | 0.0020秒 | 0.09% |

ライブラリが返すtimingでは、prefill平均27.5ms、後続decode合計平均1,789.3ms、生成ステップ平均90。ここでのdecodeはトークン生成であり、表の「波形デコード」とは別。波形デコード呼び出しは平均23.8回だった。内部timingと外側の区間計測は境界が違うため完全一致しない。

モデルが最初の音声チャンクを返すまで平均0.150秒、HTTPクライアントの初回PCM受信はp50で0.743秒。APIの1チャンク保留、同期推論中の通信処理、転送経路などが間にある。起点・統計も異なるため、この差全体をネットワーク待ちと断定しない。HTTP送信・イベントループ待ちの個別計測は今回未実施。

## 改善の判断

1. **トークン生成の内訳をさらに調べる。** 時間の約81%がここにある。GPUカーネルの実行、CPUからの起動、同期、メモリ転送のどれが支配的かは今回未分離。次は短い単独生成をプロファイルし、CUDA graphの実行やステップ間の空白を確認する。
2. **chunk_size=4と8/12の比較は有効だが、改善幅には上限がある。** 波形デコードを仮に半分にできても、他の時間が同じなら全体は約1.10倍。完全にゼロという非現実的な仮定でも約1.23倍。実際には初回音声・音質への影響を同時に確認する必要がある。これらは実測高速化率ではない。
3. **通信の応答性と総処理量を別々に評価する。** 推論と通信の分離・協調的な中断は引き続き候補。今回の単独計測では、並列要求がGPUで同時に処理されるかは検証していない。並列方式の改善は2件・4件で総生成倍率が増えることを確認して判断する。

100人対応の見積もりを変えるほどの高速化は、まだ実施も確認もしていない。
