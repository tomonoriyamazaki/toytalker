# Qwen3-TTS バッチ推論エンジンの実装と検証（2026-09-12）

**要求ごとに独立したKV行を持つバッチ推論を実装し、HTTP経由の同時16件で総音声生成倍率20.95倍、初回PCM p95 0.84秒、模擬再生枯渇0件を確認した。** 現行実装は同時16件で約3.1倍・初回PCM p95 33.6秒・全件枯渇だった。数値は本番プロセスが同じGPUに常駐（アイドル）した状態の測定で、本番への適用はまだ行っていない。聴取と音声認識による内容確認は未実施。

## 実装

`tts-models/faster-qwen3-tts/` に追加。元の `api_server.py`・インストール済みライブラリは変更していない。

| ファイル | 役割 |
|---|---|
| `batch_engine.py` | 推論エンジン本体。1本のワーカースレッドが全要求を1ステップずつ進める |
| `api_server_batch.py` | `api_server.py` と同じHTTP契約（`/health`、`/v1/tts/stream`、`/v1/speakers/*`）のバッチ版サーバー |
| `benchmarks/concurrency/batch_selftest.py` | HTTPなしの自己検証（隠れ状態の一致、同一seed比較、別話者同時、同一文バースト） |
| `benchmarks/concurrency/batch_step_bench.py` | 実装前の見込み計測（下記「設計の根拠となった事前計測」） |

設計の要点:

- **KVキャッシュは `[最大同時数, heads, 2048, dim]` の共有バッファで、要求ごとに1行を占有する。** 元実装の「サーバーに1つのStaticCache」を置き換え、同時要求が互いの文脈を上書きする問題（[現状まとめ](qwen3-tts-current-status.md)）を構造的に解消する。
- **全行が同じキャッシュ位置 `g` に書き込む。** 要求ごとの参加時刻の差は、行ごとのattentionマスク（自分のprefill以降だけを見る）とRoPE位置（`prefill_len + step + rope_delta`）で表す。transformersのStaticCacheはバッチ全体で1つの `cache_position` しか受け付けないため、この方式にした。`g` が末尾に近づいたら全行を前へ詰める（relocation）。
- **バッチ数1/2/4/8/16のCUDA graphを起動時に捕捉し、活動中の行数以上で最小のものを使う。** 各クラスのStaticCacheは共有バッファのviewを指すので、クラス切替時にKVのコピーは不要。行が完了したら末尾の行を詰めて連続に保つ。
- 予測器（15コードブック）もバッチ数別のgraph。波形デコーダーは同じステップでチャンクを出す行をまとめて1回で復号する（左文脈25フレーム＋新規4フレーム、元実装と同じ窓）。
- 1ステップの手順（予測器→埋め込み和→talker→codec head→反復ペナルティ→サンプリング→EOS/最大長判定）は `fast_generate_streaming` を行単位で再現。反復ペナルティは語彙マスク方式（下記の事前計測で元実装と厳密一致を確認済み）。
- HTTP側は要求ごとの `asyncio.Queue` から音声を受け取るだけ。推論はイベントループを占有しないので、受付・health・切断の応答性も改善する。クライアント切断時は次のステップで行を解放する。
- 制約: x-vector話者のみ（ICL方式の `ref_code` は非対応、本番はx-vectorのみ使用）。prefill長は128トークン以下、本文は1024トークン以下、生成は958ステップ（約77秒）以下。

## 設計の根拠となった事前計測（2026-09-12、元実装での測定）

バッチ化と第2版の最適化箇所を決めた計測。数値は元実装（`api_server.py`、1件ずつ処理）で測ったもので、詳細ログは `benchmarks/concurrency/results/`（Git対象外）にある。

**バッチ推論の見込み（`batch_step_bench.py`、cache長2048）。** talkerと予測器のCUDA graphをバッチ次元Nで捕捉し直し、1ステップ時間を測った。N=1で19.9msのステップがN=8で27.9ms、N=16で38.3ms、N=32で52.1ms、N=48で66.0ms。1件あたり実時間比はN=16で1.58倍、N=24で1.30倍、N=32で1.06倍、N=48で0.80倍と実時間を下回る。N=8以降はtalker部分が1件あたり約0.9ms、波形復号が約3.1msずつ線形に増え、この2つが上限を決める。同時クラスを32で打ち止めにしたのはこの結果による。N=16でtalker部分が伸び始める要因としてcache長2048への注意計算を挙げていたが、第2版のcache長1024で実際に短縮した（N=16 38.3→29.2ms）。

**GPU時系列（torch.profiler）。** 単独生成でトークン生成区間はGPU活動80%、波形変換区間は15%。波形変換区間にはcudaLaunchKernelが22,631回記録され、小さなカーネル起動で埋まっていた。これが第2版で波形デコーダーをCUDA graph化した動機。トークン生成区間では `apply_repetition_penalty` の `token_history.unique()` が毎ステップ（94回）呼ばれ、`aten::_unique2` と `aten::item` のCPU区間が各666msあった。ただしこれらはGPU処理と重なっているため、消せば同じ時間が短縮するわけではない。GPU活動の割合はSM飽和率や帯域使用率ではないので、「余力34%」のような換算はしない。

**反復ペナルティのマスク方式。** `unique()` を語彙サイズ固定のboolマスクへ置き換えた。CPU/CUDA、float32/bfloat16、logitsの2形状、履歴長0/1/94/2048、penalty 1/1.05/1.5の96条件で元実装と厳密一致（許容誤差0、NaN同士は一致扱い、正・負・ゼロ・無限大・NaNのlogitsと重複履歴を含む）。単独逐次のABBA比較20件で同一seedの波形SHA256が5ブロックすべて一致し、モデル生成時間は約1.2%短縮。効果は小さいが、音声を変えない置き換えとしてバッチ版に採用した。

**波形変換の間隔（chunk_size）。** 4を8/12に広げると処理量は8.7%/13.2%増えるが、初回PCMは平均0.22秒/0.35秒遅くなる。ユーザーが4/8/12の音声を聴取し違和感なしと報告。先頭だけ小さくする可変チャンク（先頭6チャンクは4、以後8）は処理量7.2%増・初回0.079秒増で、既存APIが末尾フェード用に1チャンク保留するため先頭2チャンクだけでは初回が速くならない。いずれもバッチ化で論点ごと置き換わったため不採用。

10:27にユーザー指示で本番を `api_server_batch.py` へ切り替え（[手順](tts-boot-recovery.md)）。切替後、公開URL経由で同じ試験を実施。

ngrok経由のため初回PCMはlocalhostより約0.1秒遅い。別話者8件同時も8/8完了、初回0.69秒（`results/prod-batch-20260913/mixed-*.wav`）。

4件の生成倍率6.75倍は、`measure-001-00` が41文字に対して28.32秒を生成した1件（受信は正常、枯渇なし）で全件完了時間が伸びたため。この要求は他3件の完了後に単独で走り続けた。切り分けとして次を確認した。

- バッチ版の全要求229件（8001番128件、本番41件、本番の単独60件）のうち12秒超はこの1件のみ。単独60件は6.64〜8.56秒に収まった。
- 同時実行の構造が1行の計算を変えないことを直接検証した（`batch_selftest.py --parity-only`、`concurrency_parity`）。同じ入力に対して、他の行が動いていてもその行の出力は単独時と**完全一致（差0）**、行の移動（compaction）後も差0。バッチ4用graphとバッチ1用graphの間には、bf16の行列演算カーネルの丸め順序の違いによる差（現実の入力40ステップで最大3.2、中央値1.1、出力の絶対値20〜50に対して）があるが、これは他の行の有無によらない固定的な数値差で、構造的誤り（対照: 差30）とは区別できる。
- 実装の差として、prefill直後に得た最初のトークンが反復ペナルティの履歴に入っていなかった点を修正した（元実装は最初のステップからペナルティ対象にする）。10:40に本番を再起動して反映済み。

以上から、28秒の1件は同時実行による干渉ではなく、サンプリングで稀に生成が伸びる現象（元実装の単独でもseedにより10秒になる例あり）が第一候補。発生率は低く（229件中1件）、原因確定には音声認識付きの長時間観測が要る。
