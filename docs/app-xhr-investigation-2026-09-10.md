# 2026-09-10朝 PC再起動後のApp XHRエラー調査

## 報告と現時点の結論

ユーザー報告: 9/10の8:30ごろ起床するとデスクトップPCが再起動していた。スマホアプリで会話するとXHRエラーが表示され、クローンボイスからずんだもんへ変えても同じだった。

Windowsイベント、TTS起動ログ、CloudWatch、DynamoDB、ローカルのアプリ実装を読み取り調査した。設定変更・再起動・デプロイ・コード修正は行っていない。

- **PCの再起動原因はWindows更新による計画再起動と確認できた。**
- **TTS自動起動はログオン時。** 深夜の再起動後、次の起動記録は朝8:24。ログオンまでクローン音声が復旧しない構成上の弱点がある。ただしプロセスの全稼働履歴までは取得していない。
- **ずんだもんにも出たXHRエラーは、PC上のTTS停止だけでは説明できない。** Appの本文送信先は直接AWS Lambda Function URL。ずんだもんのTTSはLambdaからSakuraへ接続する。
- **実会話の記録は8:40に2往復。** 同時間帯にSakuraとZakiCorpの返答テキストが保存され、相槌は両方とも音声生成成功のログがある。
- XHRエラーの正確な発生時刻・端末側の原因情報が残っていないため、今回のXHRエラーの根本原因は未確定。

これは9/11の別端末ba:e1の音途切れ報告とは別の事象として扱う。

保存された入力は音声認識テキストで、元音声ではない。サーバー側では両方の要求が受け付けられ、LLM返答を得ていたことは分かるが、アプリでその音声を再生できたかは分からない。

## アプリのXHRエラーの意味

対象: [chat.tsx](../app/app/(tabs)/chat.tsx) の`sendToServer`内のXMLHttpRequest。

- `xhr.onerror` → `XHR error`
- `xhr.ontimeout` → `XHR timeout`（設定30秒）
- サーバーからSSEの`error`イベントを受信 → `Error: ...`
- SSEの解析例外 → `ParseErr(...)`

ユーザーが見た表示が正確に`XHR error`であれば、SakuraやクローンAPI固有のエラー表示ではなく、**スマホの本文HTTP要求のエラーコールバック**だったことを示す。失敗は要求開始時だけでなく応答受信中にも起こり得るため、DynamoDBに履歴があることと矛盾しない。

現在の`onerror`は固定文言と送信フラグの解除だけで、経過時間・受信済み文字数・HTTP状態・アプリ状態などを保存しない。ネットワーク切り替え、接続の再利用、TLS、ストリーム途中の切断などを、現存するこの表示だけで特定することはできない。単純な音声再生エラーをXHRエラーと同一視しない。

## 追加のユーザー報告と改修案

追加報告: 朝にPCへログインしてからアプリを試した。音声認識・文字起こしは動作し、確定文を送る段階以降でXHRエラーが出た記憶がある。後からアプリの会話履歴を見てもXHRエラーは残っていなかった。

STTが動いていたことから、調査対象は本文要求の送信からストリーム受信までに絞れる。ただし、送信開始時に失敗したのか、受信途中だったのかは未確定。PCログイン直後はモデル準備中の可能性があるが、それだけでSakuraにも起きたXHRエラーを説明することはできない。

### 1. 会話の失敗履歴と通信診断を残す

ローカル実装の`xhr.onerror`は画面の`log`へ文字列を追加するだけで、永続保存もサーバーへの診断送信も行わない。`loadSession`は保存済みのuser/assistantメッセージから画面ログを作り直すため、このエラー表示は履歴再読込で失われる。

DynamoDBが「成功した会話だけを保存している」という理解は正確ではない。保存対象はサーバー側の会話テキストであり、音声生成・受信・再生の成功を保証しない。一方、Lambdaに届かなかった要求やクライアントだけで起きた障害は、現在のサーバー履歴には残らない。

改修案:

- アプリで送信前に要求IDを発行し、送信開始、応答開始、最初の音声受信、応答完了、再生完了、失敗を区別して記録する。LambdaのRequest IDとも対応付ける。
- エラー時刻、経過時間、HTTP status/readyState、受信量、アプリの前面・背面状態など、取得可能な診断情報を記録する。XHRから取得できないネイティブエラー詳細は別途検討する。
- 通信失敗時にも残せるよう、まず端末内へ永続保存し、通信復旧後に診断を送信する。失敗の瞬間のアップロードだけに依存しない。
- 履歴に「送信失敗」「応答受信中に切断」などの状態を表示し、LLMへ渡す会話本文とは分ける。テキスト履歴があるだけで再生成功と表示しない。
- LambdaではTTS成功・失敗とストリーム送信終了を記録する。送信終了とクライアントの受信・再生完了は別の状態として扱う。

検証は、送信前のオフライン化、応答途中の切断、TTS失敗、アプリ再起動を対象にする。失敗履歴が残り、サーバーと要求IDで照合できることを確認する。自動再送を追加する場合は、重複会話・重複課金を避けるため冪等性も検討する。

### 2. Windows更新の再起動制御を見直す

調査時点のレジストリ`HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU`には以下が設定されていた。

- `NoAutoRebootWithLoggedOnUsers = 1`
- `AUOptions = 3`

設定スクリプトにも同じ値があり、「自動再起動を無効化した」という完了表示がある。しかし、Microsoftの説明では`NoAutoRebootWithLoggedOnUsers`の適用条件はConfigure Automatic Updatesのオプション4であり、オプション3は自動ダウンロード・インストール通知の設定。現在の値の組み合わせから「再起動は起きない」とは保証できない。[Microsoft公式: Manage device restarts after updates](https://learn.microsoft.com/en-us/windows/deployment/update/waas-restart)

これは調査時点の設定で、前夜に実際に適用されていたポリシーや再起動予約まで確認したわけではない。今回の再起動理由は更新と確認できるが、その設定をすり抜けた詳細な理由までは未確定。

改修時はWindowsのエディション・バージョンで有効な制御方法と実効ポリシー、更新・再起動予約を確認する。単に`AUOptions`を4へ変えるとインストール動作も変わるため、それだけを解決策にはしない。意図した保守時間に更新・再起動し、その後サービスが無人復旧する運用を合わせて設計する。

### 3. PC起動時にログオンなしでTTSを復旧する

実際のタスクはログオン時起動なので、OS起動時のタスクまたはWindowsサービスへ移行する案とする。

- ログオンなしで実行できるアカウント、Pythonの絶対パス、作業ディレクトリ、モデル・環境変数・ngrok設定へのアクセスを明示する。
- ネットワークとGPU・モデルの準備を待ち、起動失敗を再試行する。プロセス起動と実際のTTS準備完了を分けて記録する。
- APIサーバーとトンネルの継続ログ、ヘルスチェック、異常終了時の再起動、二重起動防止を用意する。
- 検証時は、PCを再起動してログオンしない状態で外部から音声生成できること、プロセス停止後も復旧することを確認する。

この改修はローカルTTSの可用性を改善するもの。今回のXHRエラー原因の特定とは別に進められる。現段階では改修案の記録のみで、設定変更・再起動・コード修正は行っていない。
