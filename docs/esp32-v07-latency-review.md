# v0.7 本文開始の高速化検討（2026-09-10）

保存点 `d3a59a8` のファームと、ローカルのESP32用Lambdaを読み、19:02の実機画像と照合した。その後、ユーザーが候補②の実装を指定したため、相槌通知だけをファームで修正した。①の並行化は保留、③の本文プリバッファ32KBはユーザーの希望で維持する。Lambdaの変更、書き込み、デプロイは行っていない。

## 結論

高速化の余地はある。相槌の取得待ちと本文要求の並行化、および相槌の扱いをサーバーへ正しく伝えることが候補。ユーザーと検討した結果、並行化は相槌自体の取得速度や負荷へ影響する可能性があるため、まず②の通知を直す順序とした。短縮量は未測定であり、今回の画像が遅いターンだったとも確定していない。

後ろ2つの差は132ms。最初のテキストまでに約2.24秒を使っているが、これはサーバーの処理時間だけではない。相槌取得待ち、端末準備、TLS、サーバー処理、受信・解析の待ちを含む。テキストとTTSヘッダーの43ms差も、サーバーのTTS所要時間そのものではない。

`first_pcm_chunk_ms` は最初の1 byteの受信時刻ではなく8KB読み終わり、`first_tts_i2s_ms` は発音開始ではなくDMAへのコピー完了。相槌終了時刻も画像外なので、音響上の相槌→本文の空白をこの132msや2,502msと同一視しない。

## 優先候補1：相槌の取得待ちと本文要求の並行化

対象：[`sendToLambdaAndPlay()`](../devices/mcu/esp32_s3/toytalker_mini_v0.7/toytalker_mini_v0.7.ino)。

現在の順序は以下。

1. 録音を停止し、相槌取得タスクの終了を待つ。
2. I2S準備、Soniox先行接続、本文要求の組み立て。
3. LambdaのTLS接続・POSTタスクを起動。
4. アンプ準備、AEC初期化、取得済みの相槌を再生。
5. 本文レスポンスを受信・解析。

既に「相槌の再生」と「本文の接続・要求」は並行するが、「相槌の取得完了待ち」と「本文の接続・要求」は直列。相槌がまだ届いていないターンでは、本文生成に必要のない待ちが要求前に乗る。この順序はv0.6にも存在し、AEC追加による速度低下の証拠ではない。

変更案：発話確定後、本文の接続・要求を先行させ、相槌取得の残りと重ねる。相槌が既に準備済みなら、この変更による待ち削減はほぼない。本文を相槌再生中から読み込む変更は、受信・I2S所有権に影響する別段階とする。

実装では、単に待ちループを消さない。相槌タスクが使う履歴・文字列・PCMの寿命を守り、遅着した前ターンの結果を次ターンで再生しない仕組みが必要。キャンセル時にも使用中のTLSクライアントやタスクを強制破棄しない。相槌・本文のTLSが同時に増える区間の内部RAM・PSRAMも確認する。背景は [TLSメモリ調査](esp32-s3-tls-memory-investigation-2026-09-06.md) と [v0.7のTLS対策](esp32-v07-aec.md) を参照。

まず既存の `BC wait done` の経過時間を複数ターンで確認する。ここがほぼゼロなら、主な高速化対象を次のサーバー側調査へ移す。待ち時間すべてが短縮されるとは約束しない。

## 優先候補2：相槌後の重複した前置きを減らす

変更前のファームでは `backchannelFired` は `playBackchannelIfReady()` の再生後にtrueになるが、本文POSTの `backchannel_fired` はその前に組み立てていた。通常のターンでは前回終了時にfalseへ戻しているため、取得済みの相槌をこの後に再生する場合でも、本文要求にfalseが入っていた。

[`ESP32用Lambda`](../backend/toytalk-api-stream-for-esp32-lambda/index.mjs) では、trueのときだけ「相槌は別途再生済み、本題から返答する」という指示を追加する。変更前はその指示が付かず、本文も相槌・挨拶から始まる可能性があった。

実装：取得済み・再生予定・再生済みを区別し、要求直前に `backchannelPlanned` を固定した。キャンセルされておらず、readyでサイズが正のPCMがある場合だけ予定をtrueとする。`backchannelFired || backchannelPlanned` を既存APIの `backchannel_fired` に送り、ローカル再生も同じ予定を使う。実再生フラグの更新や本文要求のタイミングは維持する。通知後の再生失敗・キャンセルは、送ったPOSTへ遡って反映できない。詳細と確認ログは [相槌通知の実機試験手順](esp32-v07-aec.md) を参照。

これは主に「本題に入るまで」を短くする案で、最初の音声が早くなる保証はない。短い前置きがなくなって最初の文が長くなると、文末を待つ現在のTTS方式では最初の発音が遅くなる可能性もある。最初の音声開始と本題開始を別々に評価する。

## その他の候補と優先度

| 候補 | コード上の根拠・見込める効果 | 注意点 |
| --- | --- | --- |
| Lambdaの設定取得を並行化 | device→character取得後のvoice・LLM取得が直列。ID確定後の独立した2取得を重ねる余地がある | 実デプロイ版との差、各取得の所要時間を確認。キャッシュは設定反映の仕様変更を伴うので別扱い |
| 最初の文とTTS準備を改善 | 文末または100文字まで待ち、SakuraではWAV全体の取得後にPCMを送る | 初回テキスト/TTSをサーバーで計測してから検討。短すぎる分割は抑揚・区切り・リクエスト数に影響。ストリーム対応はAPI仕様の確認が必要 |
| 初回だけ再生バッファを小さくする | 現在は32KBのstereo PCM、8KBのmono読み込み2回分で開始。初回を16KBにすると1回分で開始できる | 19:02の最初の8KB読了→I2S書き込み132msの一部が対象。32KBは音声約341ms分であって、常に341ms待つわけではない。音切れ再発を比較し、再バッファ量は維持する |
| AEC演算・配置を軽くする | Core 1の優先度2でAEC、同じコアでloopが受信。競合はあり得る | まず平均・分位の処理時間を測る。最大値だけでCPU使用率を判断しない。Core 0にも再生・TLSがあり、移すだけで改善するとは限らない |
| AEC初期化を前倒しする | 毎ターンの同期初期化は相槌前に存在 | `[AEC_RESET] elapsed_us` を先に確認。今回安定した毎ターン初期化を無効化して速度を稼ぐ案は初手にしない |

TTSセグメント間400msは従来設定で、最初の本文PCMの前には挿入しない。AECの保持128ms・ウォームアップ500ms・飽和後256msも検出の条件で、本文をその時間sleepさせる処理ではない。

## 比較の進め方

1. `d3a59a8` を基準に、同じ配置・音量で短い質問と長い質問を複数ターン計測する。`Sending to Lambda`〜`first_tts_i2s_ms` の全区間と、`BC wait done`、`Backchannel phase done`、`AEC_RESET`、`lambda_connect_ms / lambda_send_ms / headers_ms` を残す。
2. ユーザーが選んだ候補2を単独で比較する。`[BC] reply_hint / planned / played` と初回本文の前置きを確認し、本文開始と本題開始を混同しない。別途ユーザーが更新した検索用プロンプトによる変化もあるため、検索なしの通常会話でも確認する。
3. 相槌待ちが支配的なら候補1を次の比較版として検討する。起動初回、相槌取得済み、取得中、失敗、本文中キャンセル、連続ターンを確認する。相槌開始の遅延も測り、待ちがないターンまで同じ短縮量を期待しない。
4. プリバッファは現状維持とし、サーバー待ちが支配的なら設定取得・最初の文・TTSを検討する。中央値と遅い側の値を比較し、誤停止・声の取りこぼし・音切れ・メモリ失敗を増やさない。

短縮量を測る実機比較、サーバーログやデプロイ設定の調査はまだ行っていない。候補2のビルド結果は [v0.7の検証記録](esp32-v07-aec.md) に記載する。
