# 認証導入時の設計メモ（owner_id の扱い）

2026-09-13、Cartesiaのクローンボイスをアプリから作れるようにした際に整理した。本格認証（Cognito + Sign in with Apple、[先送り項目](deferred-items.md) 参照）を入れるときに、この内容をそのまま設計の出発点にする。

## いまの状態（認証なし）

- `owner_id` はアプリ初回起動時に生成する `u_<UUID>`。iOSはキーチェーンに保存。
- キャラクター・カスタムボイス（ZakiCorp / Cartesia）・利用状況・会話ログは、すべてこの `owner_id` で保存されている。
- 見え方の制御は「クライアントが送ってきた `owner_id` を信用する」方式:
  - `GET /voices` は `owner_id` が付いた行（＝誰かのカスタムボイス）を除外する。
  - `GET /custom-voices?owner_id=X` は X の行とシステム行だけ返す。
  - 作成・削除・名前変更も `owner_id` を本人確認なしに受け付ける。
  - 本文Lambdaは、キャラクターに設定された `voice_id` を持ち主の確認なしに合成する。
- つまり「他の利用者には見えない」は成り立つが、「守っている」わけではない。IDが推測できない長さであることだけが壁。ZakiCorpのカスタムボイスも当初からこの前提。

## 認証を入れたときに変える点

原則: **Lambdaは、クライアントが送る `owner_id` ではなく、検証済みトークンから取り出した本人のIDを使う。** これだけで一覧・作成・削除・合成のすべてが本人に限定される。今回のクローン機能の作りはそのまま活きる。

1. **既存 `owner_id` との対応（データ移行を避ける）**
   - Cognito の `sub` に置き換えると全テーブルの移行が要る。
   - `owner_id` を内部IDとして残し、`sub → owner_id` の対応表（例: `toytalker-users`）を1つ持つ。初回ログイン時に端末が持っている `owner_id` を紐づける。別端末で同じアカウントにログインしたら対応表から `owner_id` を引いて配る。
   - 紐づけ前の端末（未ログイン）をどう扱うかは、導入時に決める（ログイン必須にするか、ゲスト継続を許すか）。

2. **ESP32はログインしない**
   - 本体は `device_id` だけを送る。Lambdaが `toytalker-devices` からオーナーを引く現在の方式は維持。
   - 代わりに **デバイス登録（`POST /devices` 相当）をログイン必須** にし、トークンの本人にしか紐づけられないようにする。既存デバイスは登録済みのオーナーのまま。

3. **トークン検証の場所**
   - 本文LambdaはFunction URL（RESPONSE_STREAM）で動いているため、CloudFrontやAPI Gatewayを前段に置くより、**Lambda内でJWTを検証**するのが簡単で構成を崩さない。JWKSはLambdaでキャッシュしてネットワーク往復を毎回入れない（会話レイテンシ維持）。
   - CloudFrontは静的配信・WAF・レート制限などの目的があれば別途。認証の必須要素ではない。
   - 相槌LambdaやSoniox一時キー発行など、本文以外のLambdaも同じ検証関数を共通化して使う。

4. **合成時の持ち主チェック**
   - 本文Lambda・読み上げLambdaで、キャラクターとボイスの `owner_id` がトークンの本人（またはシステム）と一致するかを1回確認する。IDを知っていても他人のクローン声を喋らせられなくなる。
   - デバイス経由（ESP32）の場合は、デバイスのオーナーとキャラクターのオーナーの一致を確認する。

## 影響範囲のメモ

- デバイス設定Lambda: `/voices` `/custom-voices` `/characters` `/devices` `/usage` すべてで `owner_id` の出どころをトークンに切り替える。
- 本文Lambda（App / ESP32）・読み上げ・相槌: トークン検証と持ち主チェックを追加。
- アプリ: ログイン画面、トークンの保持と付与、初回紐づけ。
- ESP32ファーム: 変更なし（デバイス登録の経路だけアプリ側が変わる）。
