# ToyTalker 音声生成の現状まとめ

2026-09-12の検証と、その後のユーザーによる音声確認を整理したもの。

## 今の結論

**改善版は1件ずつなら少し速くなり、確認した音声も問題なかった。しかし、4件同時では待ち時間・再生の途切れが残り、言葉の繰り返しや抜けも見つかった。複数人を快適に捌ける状態には、まだできていない。**

改善版は本番に適用していない。検証後に元のプログラム・設定へ戻し、音声生成と監視タスクの復帰を確認済み。現在は調査を停止しており、このまとめの作成中に追加の負荷試験は実行していない。

## 何を目指しているか

ToyTalkerを100人が使えるようにしたい。そのために、自前のRTX 5090＋Qwen3-TTSでどれだけ音声を生成できるか、改善の余地があるかを調べている。

「100人がサービスを利用する」ことと「100件が同時に音声生成を要求する」ことは同じ条件ではない。実際の会話頻度や返答の長さも必要だが、現段階では少人数の同時要求でも問題が残っている。100人対応は未達・未検証。

## ここまで何をしたか

| 段階 | やったこと | 分かったこと |
|---|---|---|
| 元の性能を測定 | 元のプログラムに1・2・4・8・16・32件の要求を同時に送った | 初期試験では1〜16件の総生成量がほぼ一定。要求数を増やすと待ちが長くなり、32件は大半が期限超過 |
| 時間の内訳を調査 | トークン生成・波形変換とCPU/GPUの処理時間を計測 | 最初の区間計測ではトークン生成約81%、波形変換約19%。GPUの性能限界そのものは未確定 |
| 小さな高速化を試行 | 重複トークン除去の変更、波形への変換間隔の調整 | 重複除去の変更は約1%の時間短縮。変換間隔を広げると処理量は増えるが、初回音声が遅くなった |
| 先頭を小さく保つ改善版を試行 | 先頭6チャンクは通常と同じにし、その後の変換間隔を広げた | 単独では処理量約7.2%増、初回音声は約0.079秒遅い。ユーザーが比較音声を聞き、違和感なしと確認 |
| 改善版の同時利用を比較 | 通常版と改善版で同時2件・4件を測った | 同時数を増やしても総生成量は増えず、改善版4件では待ち・模擬再生の途切れが残った。保存音声にも異常の報告あり |

## 「並列テスト」という説明について

**複数の要求を同時に送る試験は、最初から行っている。今回が初めてではない。**

今回作ったのは、音声への変換回数を減らす改善版。複数人分を効率よくGPUで同時に計算する仕組みを新しく実装したわけではない。

実測で言えるのは「要求数を増やしても、全体の音声生成量が増えていない」ということ。内部が完全な直列処理なのか、途中で交互に動いているのかを、この結果だけで決めつけない。以前の説明では「同時要求の試験」と「並列化の実装」を混同させてしまった。

## 改善版の最新結果

| 条件 | 結果 |
|---|---|
| 単独 | 通常比で処理量約7.2%増。初回音声0.748秒→0.827秒。保存した比較音声はユーザー確認で問題なし |
| 同時2件 | 総生成倍率3.40倍。初回音声p95は2.34秒。10/10受信完了、模擬再生の途切れ0/10 |
| 同時4件 | 総生成倍率3.31倍。初回音声p95は4.05秒。20/20受信完了だが、模擬再生の途切れ20/20。聴取した先頭4音声のうち2つに異常 |

「生成倍率3.40倍」は、実時間1秒あたり合計約3.40秒分の音声を生成できたという意味。対応人数を表す数値ではない。2件から4件へ増やしても、この総量は増えなかった。

模擬再生の途切れは、受信時刻から計算した推定。実機スピーカーの音を直接測った結果ではない。また、受信完了は音声内容の正常性を保証しない。完成WAVを再生しても、通信中の待ち時間や途切れはそのまま再現されない。

## 追記（2026-09-12 夜）：原因の特定とバッチ推論の見込み

コードとログの再分析で、繰り返し・抜けの有力原因を特定した。推論グラフのKVキャッシュ（`talker_graph.py` の `StaticCache`）がサーバーに1つしかなく、同時要求が交互に進むたびに `prefill_kv` のリセットと各ステップの書き込みで互いの文脈を上書きする。生成済みトークン・テキスト供給・波形復号は要求ごとに独立しているため、声は崩れず文脈だけが混ざる。可変チャンク改善版の問題ではなく、元の実装の構造。同一文・同一話者の試験では症状が確率的にしか出ないが、本番のように文と話者が異なる要求が重なると露骨に出るはず。改善版4件の「音声総量37%増」は、41文字に54.88秒を生成した1件の暴走が主因。切り替えは送信バッファが約64KB（約1.6秒分）を超えた時点で起きており、チャンク境界ごとではない。

同時要求で総処理量が増えないのも同じ構造（1件分のバッチ固定グラフを時分割）による。

実装前の見込み計測として、talker・予測器・波形デコーダーをバッチNで動かした結果、1ステップはN=1の19.9msに対しN=8で27.9ms、N=16で38.3ms。4ステップ＋復号の見込みで総音声生成倍率はN=4で約10.8倍、N=8で約18.4倍、N=16で約25.2倍（現行約3.1倍）。詳細は [バッチ推論の見込み計測](qwen3-tts-batch-step-bench-2026-09-12.md)。

次の順は、(1) 別文・別話者を交互に進める再現試験で相互上書きを確定、(2) 音声認識による本文照合を性能計測へ組み込む、(3) 暫定で生成を1本の推論スレッドへ直列化、(4) 要求ごとに独立KV領域を持つバッチ推論の実装と2/4/8件の実測。本番の共有キャッシュ問題は未対策。
