# ElevenLabs連携の課題と検証候補

更新日: 2026-09-11

## 結論

現状は、LLMの出力を文などのブロックに分け、各ブロックを順番にTTSへ送る構成。ブロックが多くても、本文のLambda呼び出し1つからTTSを大量に並列実行する実装にはなっていない。

改善余地として確認できたのは、ElevenLabsから受信した音声をブロック全体の受信完了まで保持している点。到着した音声を順次端末へ渡せば、再生開始を早められる可能性がある。ただし、実際の効果やリクエスト分割による負荷は未計測であり、現状を「同時実行枠を浪費している」とは断定しない。

本書は調査・相談の記録。コード変更や実機検証は行っていない。記載の実装はローカルのソースを確認したもので、本番デプロイ状態との照合は未実施。

## 確認した現在の実装

対象:

- [ESP32用Lambda](../backend/toytalk-api-stream-for-esp32-lambda/index.mjs): `ttsBufferElevenLabs`、`emitSegment`
- [App用Lambda](../backend/toytalk-stream-handler-lambda/index.mjs): `ttsToBase64ElevenLabs`、`emitSegment`

両方とも、LLM出力を句点・疑問符・感嘆符や文字数の条件で区切り、`await emitSegment(...)`でTTS処理の完了を待ってから次のブロックへ進む。

ElevenLabsにはHTTPの`/v1/text-to-speech/{voiceId}/stream`を呼び出し、`pcm_24000`を要求している。しかし、応答は`await resp.arrayBuffer()`で全体を受信してから処理する。

- ESP32向け: ブロック全体のPCMを受信し、無音を処理して、サイズ付きメタデータとPCMを送信する。
- App向け: ブロック全体のPCMを受信し、WAV/base64へ変換して送信する。

```text
LLMの1文目 → TTS要求 → 1文目の音声を全受信 → 端末へ送信
                                                    ↓
LLMの2文目 → TTS要求 → 2文目の音声を全受信 → 端末へ送信
```

端末は先に届いた音声を再生しながら後続を受信できるが、Lambdaからの送信はブロック単位。ElevenLabsから到着する音声を即座に端末へ中継する構成ではない。

## 課題1: ブロック全体の受信待ち

最初の音声データがElevenLabsから到着しても、そのブロックの受信完了までは端末へ渡していない。この待ち時間を短縮できる可能性がある。

改善候補は、HTTP応答の音声を読み取りながら端末へ順次送信する方式。ただし、単に`arrayBuffer()`を置き換えるだけではなく、以下との整合が必要になる。

- ESP32向けの音声サイズを先に通知するプロトコル
- ブロック全体を対象にしている無音処理
- App向けのWAV/base64送信と再生方式
- 端末側のプリバッファ量と再生開始条件
- 途中でTTSが失敗した場合の扱い、割り込み停止後の残り音声の扱い

「早く送信する」だけで必ず体感が改善するとは限らない。端末が必要量をバッファする時間も含めて評価する。

## 課題2: 細かな分割とリクエスト回数

短いブロックなら先頭の音声を早く取得しやすい一方、分割ごとにHTTPリクエストと処理開始の待ちが発生する。短く分割すれば、合計の処理時間や枠の使用時間も必ず短くなるわけではない。

説明用の仮定:

| 送り方 | 各要求の処理時間 | 合計の要求処理時間 |
|---|---:|---:|
| まとめて1回 | 1.5秒 | 1.5秒 |
| 5ブロックを順番に送信 | 各0.5秒 | 2.5秒 |

この例では分割の方が先頭を早く渡せるが、合計時間は長い。数値は実測ではない。また、クライアント側で測るHTTP処理時間と、プロバイダー内部で同時実行として数える時間は完全に一致するとは限らない。

改善候補:

- 最初のブロックを短くし、後続は適度にまとめる。
- ElevenLabsのTTS WebSocketへテキストを順次投入する方式を比較する。

どちらも、文のつながり・抑揚・音切れ・再生開始時間を含めて評価する。WebSocket化だけで同時実行枠の制約がなくなるわけではない。

## 同時実行枠への影響

現在の本文処理は、Lambda呼び出し1つにつきTTSを最大1件ずつ実行する。複数ユーザー、相槌、読み上げなど、同じ契約枠を使う要求が重なれば全体の同時実行数は増える。割り込みで旧処理が残った状態で次の要求が始まる可能性も、別途確認する必要がある。

登録ユーザー数や、音声を再生中の端末数が、そのままTTS同時実行数になるわけではない。音声生成が再生より早く終われば、再生中でも生成枠は空く。

平均値の見積もりは以下を出発点にする。

```text
平均同時実行数 ≒ 毎秒の要求数 × 平均の枠占有時間（秒）
```

ToyTalkerでは「1往復の本文ブロック数 + 相槌の要求数」を含める。以前の会話で用いた「本文1回 + 相槌1回」の仮定は、本文が複数に分割される場合の実態を表していない。

平均だけではピーク時の待ちやエラーを判断できないため、利用タイミングが重なる条件でも確認する。

ElevenLabsの公式説明では、HTTPは各要求が同時実行に数えられる。TTS WebSocketは音声生成中のみ数えられ、接続を開いているだけでは枠を占有しない。Text to Dialogue WebSocketは別のセッション方式なので混同しない。

## 検証で記録したい項目

- 1往復の本文ブロック数、各ブロックの文字数、相槌の要求数
- TTS要求開始から最初の音声データ到着までの時間
- TTS要求開始から音声全体の受信完了までの時間
- Lambdaからの先頭音声送信時刻と、端末の実再生開始時刻
- ElevenLabsの`current-concurrent-requests`と`maximum-concurrent-requests`ヘッダー
- 混雑時の処理時間の分布、429などのエラー、音切れ
- 割り込み後に旧TTS要求が継続しているか

現在の`tts_first_byte`マークはTTS呼び出し前に記録されており、ElevenLabsから最初の音声バイトを受信した時刻ではない。この値をTTSの初回音声到着時間として評価しない。

まず現行方式を計測し、その結果を基準に、音声の逐次中継、ブロック長調整、TTS WebSocketを個別に比較する。最初の音が出るまでの時間と、合計処理時間・同時実行数を分けて判断する。
