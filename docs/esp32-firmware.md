### ボイスキーホルダーモード（0.7.31〜0.7.32、2026-11-14。試験機で動作を確認、beta に発行済み。0.7.32 での一晩つけっぱなしは取っていない＝0.7.26 で見てあるので取り直さないと利用者が決めた）

登録しておいた声を、ボタンを押すたびに1つ鳴らすモード。Wi-Fi もマイクも使わない（外でも鳴る）。コードは `.ino` の「ボイスキーホルダーモード」と `VoiceKeyholder.h`。

- **操作**: 会話モードで **3回押し**（0.6 秒以内の間隔）→ 再起動してキーホルダーモード（ド・ミ・ソの合図）。押すたびに次の声（一巡するまで同じ声は出ない。鳴っている途中で押すと止めて次へ）。もう一度3回押しで会話モードへ戻る。**BLE 設定中（速い点滅）の3回押しでも入れる**（0.7.32。Wi-Fi の無い場所で起動すると BLE 設定に入るので、ここで受けないと外で切り替えられなかった。Wi-Fi 設定が無い本体でも入れる）。モードは NVS（`mode/keyholder`）に残り、電源を入れ直しても同じモードで始まる。声が入っていない本体（古い区画・空の区画）は切り替わらない。OTA で入れた直後（有効印の前）も切り替えない（再起動するとブートローダーが前の版へ戻すため）。
- **会話モードで変わったこと**: 2回押しで休むまでが 0.6 秒遅くなった（3回目を待つ）。BLE 設定中の1回押し（設定をやめて起動し直す）も同じく 0.6 秒遅い（0.7.32）。
- **声の入れ物**: `voices` 区画に、先頭の表（`TTVK`、件数、CRC32）と IMA ADPCM（4bit・24kHz・モノラル、1 秒 12KB、384KB で約 32 秒）を置く。形式の欄があるので、後から mp3 などを足せる。音量は会話と同じ処理（`PlaybackLimiter`）を通る。
- **声の入れ方1（USB）**: `node devices/mcu/esp32_s3/tools/make-voices.mjs <音声ファイル…> --flash COM12`（ffmpeg で 24kHz にそろえ、前後の無音を落とし、山をそろえて圧縮する。入らなければ止まる。`--erase --flash COM12` で空に戻す）。音の整え方・ADPCM・入れ物の組み立ては `backend/shared/voice-image.mjs`（下のアプリ用の Lambda と同じもの。切り出しの前後で同じバイト列が出ることを 12 件の素材で確認）。
- **声の入れ方2（アプリから。0.7.34、2026-11-14 実装。Lambda は RnD に deploy して API で確認済み、ファームは beta に発行済み。本体の取り込みとアプリの画面は未確認）**: アプリのデバイス設定 →「ボイスキーホルダー」で文と声を選んで足す・消す・試聴する（`app/components/VoiceKeyholder.tsx`、`app/lib/keyholder.ts`）。
  - **サーバー**: 読み上げ Lambda が `/read-aloud-app` の本文の `keyholder`（`list` / `add` / `remove` / `preview`）で受ける（`backend/toytalker-tts-only-lambda/keyholder.mjs`）。`add` は各社へ 24kHz の PCM を頼み（`pcm-tts.mjs`。mp3 を経ない。主の声が失敗しても別の声では作らない）、1件ぶんの ADPCM を S3 `toytalker-firmware` の `esp32s3/voices/<機器>/clips/` に置き、全件から `voices.bin` を組み直して同じ場所に置く。一覧と印は `devices` の行の `keyholder`（`rev`・`lines`・`image{key,size,crc,sha256}`）。試聴は ADPCM を展開した WAV（本体が鳴らすのと同じ音）。費用は読み上げと同じ記録（`usage` と台帳。作った時点でかかるので、長すぎて入らなかった時も記録する）。文は 80 文字まで、16 件まで、全体で区画（393,216 バイト）まで。
  - **本体**: 起動時の鍵取得に、いま入っているイメージの印を `vk=<CRC32 の 16 進 | none>` で添える（区画が無い本体は付けない）。鍵発行 Lambda は `devices` の `voices_crc` に残し、`keyholder.image.crc` と違えば応答に `voices { url, sha256, size }` を入れる（ファームの更新を勧めた回は出さない）。本体は全部を PSRAM に受けてから SHA-256 と入れ物の形を確かめ、区画を消して書く（`VoiceSync.h`。先頭の 16 バイトを最後に書く）。受け取りの失敗では前の声が残り、次の起動でまた試す。
  - **決まりごと**: アプリの一覧が正。USB で入れた声がある本体でも、アプリで1件足すと一覧の中身に入れ替わる（画面に注意を出す）。全部消すと 0 件のイメージが届き、本体は声なしになる（3回押しでも切り替わらない）。入れ替わるのは**会話モードで起動して Wi-Fi につながった時だけ**（キーホルダーモードの間は Wi-Fi を使わない）。アプリの「本体に入っています」は、本体が最後に名乗った印で判断するので、入れ替えた直後ではなく**その次の起動**で変わる。
  - **サーバーで見たこと（2026-11-14、RnD、試験機の行）**: `list`（他人の owner_id は 403）、`add` を2件（Cartesia と ずんだもん、各 2.1 秒・約 25KB、応答まで約 1 秒）、`preview`。S3 の `voices.bin`（51,074 バイト）の SHA-256 が行の `keyholder.image.sha256` と一致。試聴の WAV は 24kHz・モノラルで音が入っている。ログに費用まわりの警告なし。試験機の一覧にはこの2件が入ったままなので、**試験機が今回の 0.7.33 で起動すると、USB で入れた 12 件はこの2件に入れ替わる**（戻すなら `make-voices.mjs` で書き直し、アプリで全部消す前に一覧を空にしないこと＝空の一覧も「声なし」として届く）。
  - **版の整理（2026-11-14）**: 同じ時間に、アプリからの音量（下の「音量」）とこの変更の両方が 0.7.33 を名乗った。S3 の beta に出た 0.7.33（タグ `fw-0.7.33`）は**声の取り込みだけが入った版で、アプリからの音量は入っていない**。試験機に USB で書かれた「0.7.33」は逆に音量だけの版。両方が入っているのは **0.7.34** から。
  - **確認の仕方（本体）**: アプリで1件足す → 鍵発行のログに `voices_offer`、シリアルに `[VOICES] done: clips=…` → 3回押しで鳴る → もう一度起動するとログの `voices_crc` が変わり、アプリの表示が「本体に入っています」になる。
- **実機で見たこと（2026-11-14、試験機、シリアルは `.local/serial/keyholder-2026-11-14-buttons.log`）**: 3回押しで両方向に切り替わる、5 件が一巡ごとに全部鳴り巡の変わり目でも続かない、途中の押下で止まって次が鳴る、会話モードへ戻った後の会話は通常どおり。この時の声は Windows の読み上げで作った 5 件（約 10 秒、115KB）。その後、読み上げ Lambda（RnD、利用者の指定なし＝`user_123`）で Cartesia「女性1」と ZakiCorp「ことね」を 6 件ずつ作って入れ替えた（12 件、32.1 秒、385,305 バイト＝区画の 98%。元の mp3 は `.local/voices/demo-2026-11-14/`、git の外）。`flash-published.sh` で書き直しても声とモードは残る（`clips=12` で起動）。電源の抜き差しでの確認はシリアルでは取れていない（再起動での保持は確認）。0.7.32 の BLE 設定中の3回押し・1回押しは、利用者が試験機で操作して「問題なさそう」（2026-11-14。シリアルの記録は無い）。
- **未着手・未確認**: アプリから足す経路の実機確認（上の「声の入れ方2」）。消した声の ADPCM は S3 から消すが、機器を削除した時の `esp32s3/voices/<機器>/` は残る（掃除は未実装）。待機中の電流（Wi-Fi は起動しないが、CPU は起きたまま）。ボタンは GPIO35 で、深いスリープから起こせるピン（0〜21）ではない。長押し（BLE 設定）はこのモードでは何もしない。モードはサーバーへ報告していない。

### OTA の検証と失敗の扱い（2026-11-11〜12、試験機で確認済み）

- **検証3件は済**: SHA改ざん（マニフェストの SHA を1文字変える → `sha256 mismatch` → `fail: stage=sha256` で元の版のまま会話へ）、電源断（60% で USB を抜く → 元の版で起動 → `try=2` で入り直して成功）、ロールバック（鍵取得の前に `abort()` する版 → ブートローダーが元の版へ戻す → `rollback detected` → `skip: … rolled back before` でループせず会話へ）。
- **失敗の扱いを変えた（0.7.12、直しは 0.7.17）**: 以前は失敗の種類を問わず3回でその版を諦めていた（偶然の失敗が3回でその版が二度と来ない。試験機で実際に起きた）。いまは、ロールバックした版だけ以後試さず（`bad`）、ダウンロードの失敗（電源断・通信・SHA 不一致）は諦めずに、続けて3回で「5回の起動に1回」へ間を空ける（弱い Wi-Fi で起動のたびに最大3分待たせないため。数字は決め打ち）。次の版が出ればどちらも数え直す。
- **成功の判定は有効印の時**（`confirmRunningImage()` → `markUpdateSucceeded()`）。0.7.12 は起動の最初に「入れた版が動いている＝成功」として記録を消したため、落ちる版を入れ直し続けた（試験版 0.7.16 で約5周。beta を戻して止めた）。0.7.12〜0.7.15 にはこの穴があるので配らない。
- **結果はサーバーで見える**: 起動時の鍵取得に `ota_last` / `ota_fails` / `ota_bad` を添え、Lambda の1行ログに出る（[infra/README](../infra/README.md)）。発行の誤りの疑い（勧めている版のロールバック・SHA 不一致）は警報 `toytalker-ota-broken-rnd` が即メール、版の分布と失敗が続く機器は月次レポート。警報の条件・月次の節・ログの項目は実ログで確認済み。警報のメールが届くことは 2026-11-13 に確認（下の「OTA の直し2つ」。通知の許可漏れを直した）。
- **残っていた弱点（下の「OTA の直し2つ」の1で対応済み）**: 新しい版の最初の起動で、鍵取得の前に電源が切れると、ロールバック扱いになってその版を試さなくなる（次の版で追いつく）。

### 待ち受けの見張り: 切れたら戻す・無音なら休む（0.7.19、2026-11-13。ロードマップ20・24。**ビルド確認のみ・実機未**）

### 音量: EQ とリミッター（0.7.20、2026-11-13。試験機に USB で書いて聞いた。発行は未）

`PlaybackLimiter.h`。本文と相槌の両方が通る（`monoToStereo`）。以前は 1.5 倍して山を切るだけだった。

- **仕組み**: ① EQ（300Hz より下を削り、3kHz を +6dB。小さいスピーカーが鳴らせない低い音に上限の枠を使わない）→ ② リミッター（全体を倍率ぶん持ち上げ、山が上限を超えそうな所だけ 2ms 先読みして絞る）。
- **倍率**: 既定 6 倍（`PLAYBACK_GAIN_DEFAULT`）。NVS の `audio/gain` があればそれを使う。**試験用にシリアルの1文字で変えられる**（聞き取り中。`1`〜`8` = 1.5 / 2 / 2.5 / 3 / 4 / 5 / 6 / 8 倍で保存、`0` = 既定、`e` / `f` = EQ あり / なし（保存しない））。試験機の NVS には 6 倍が入っている。
- **計測**: 返答ごとに `[PCM_LEVEL] eq gain in_peak in_rms out_rms limited_pct min_reduction hard_clips`（シリアルだけ。サーバーへは送っていない）。
- **実測（Cartesia、2026-11-13）**: 届く音声は山 13000〜17000・平均（RMS）1900〜2100。出す音の平均は、以前の 1.5 倍で約 3000、6 倍・EQ なしで約 8300（+9dB）、6 倍・EQ ありで約 6800〜7200。絞りが効くのは 35〜50%、音割れ（`hard_clips`）は 0。聞いた感想は「3 倍: 少し上がった」「6 倍: あまり伸びない」「6 倍 + EQ: 大きくなった、OK」。
- **EQ は既定でなしにした（0.7.25、2026-11-13）**: 6 倍・EQ ありで使ってみると、再生中ずっとシャラシャラした音が乗った。聞き比べ（試験機、シリアルで切り替え）: 4 倍・EQ あり = シャラシャラは減るが音量も減る（出す音の平均 約 5500、絞り 12%）、**6 倍・EQ なし = シャラシャラがほぼ消え、音量もある（平均 約 7900、絞り 27〜34%）**。原因は 3kHz の +6dB と判断し、EQ の既定を「なし」にした（コードと `e` / `f` の切り替えは残してある）。低い音を削るだけ（持ち上げなし）の版は試していない。倍率は 6 倍のまま。
- **雑音と GAIN**: 音量を上げたぶん、声の合間の小さい音も持ち上がる。アンプの GAIN を上げると雑音も割り込みにくさも増えるので、GAIN は後回し（先にファーム側の調整と、声の合間だけ絞る処理・割り込みの作り直しを試す。2026-11-13）。
- **分かったこと**: 倍率を上げる方向はここで頭打ち（山が上限に張り付く）。この先はハード側（スピーカーの能率、ケース、アンプの GAIN）。アンプ MAX98357A の GAIN ピン（B2）は未接続＝9dB で、GND（隣の C2）につなぐと 12dB、100kΩ 経由で 15dB（Adafruit の解説の値。データシートは未確認で、いまの設定で最大の音が電源の上限に当たっているなら上げても変わらない）。
- **割り込みへの影響**: 再生音が大きくなったぶん、声の割り込みの数値（下）はずれる。音量を優先し、割り込みは後から合わせる（2026-11-13 決定）。
- **アプリから変える（0.7.33、2026-11-14。試験機で確認）**: アプリのデバイス設定の「音量」（小 / 中 / 大）→ `PUT /devices/{id}` で `devices` の `volume_level`（`low` / `mid` / `high`）→ 一時キー Lambda が応答に載せる → 本体が起動時に読んで倍率に直す（`applyVolumeLevel`: 小 2 倍・中 4 倍・大 6 倍＝既定）。**反映は電源の入れ直しの後**。サーバーに置くのは段階の名前で、倍率は本体の表（基板やスピーカーが変わったら表を変える）。NVS には書かない。段階を決めていない機器には何も返さず、本体は NVS の `audio/gain` か既定のまま。0.7.32 以前は項目を無視する。鍵発行のログに `volume_level` が出る。聞いた感想は「小と大で明確にわかる」（試験機、ログで low → high → mid の配信を確認）。段階ごとの飽和・割り込みの通りやすさは測っていない。
- **次**（ロードマップ35）: 再起動なしの反映（25 の `settings`）、声ごとの音量合わせ、ハード側。

- **v0.3 のマイク（SPH0655）で飽和が減る見込み（推測。PDM 化したら実測する）**: v0.7 が数える飽和は、マイクの 18bit の値を 16bit へ切り詰めるところ（`AecMonitor.h` の `>> 14`）で起き、マイク自体の上限の 1/4（−12dB）で頭打ちになる。SPH0645 は感度 −26dBFS・上限 120dB SPL なので、頭打ちは約 108dB SPL（データシートの値からの計算）。2026-09 のケースなしの入力ピーク 86,640（上限 131,072）は約 116dB SPL で、マイク自体もほぼ限界だった。SPH0655 は感度 −37dBFS・上限 132.5dB SPL で、PDM の 16bit の値を増幅せずに使えば頭打ちは約 131dB SPL になる。**感度を補う増幅を AEC の前に入れると飽和も元に戻るので、増幅は AEC の後に置く**。声も同じだけ小さく入るので、しきい値（RMS 1200）と STT へ送る音量は合わせ直す。ESP32 の PDM 受信が出す値の大きさは未確認。飽和が減っても、消し残りで誤って止まる回数が増える可能性はある（2026-09 の入力 1/4 縮小では飽和が 97.8% 減っても誤停止が残った。[入力クリップ比較](esp32-aec-input-headroom-2026-09-12.md)。今は「止めてから確かめる」方式なので当時より耐えられる見込みだが未検証）。確かめ方: 同じ音量・同じケースで `pre_scale_clips` と `aec_clip_frames` を v0.2 と比べる。

### 声の割り込み（0.7.9〜0.7.10、2026-11-09〜10。ロードマップ21）

**仕組み**（値は `AecBargeGate.h`、判定は `AecMonitor.h`、一時停止は `.ino` の `playerPaused`）。1コマ＝512サンプル＝32ms（ESP-SR の AEC の単位）。音の値は 16bit（±32767）で、しきい値は1コマの AC RMS。
1. **1段目（一時停止する）**: AEC 後の AC RMS が 1200 以上で4コマ（128ms）続き、かつ AEC 後がマイクの 25% 以上残っている。判定しないのは、再生開始から 500ms、再開から 300ms、マイク飽和から 256ms、処理が 200ms 以上遅れたコマ。
2. 発火したらアンプを切り（AMP_SD LOW）、再生タスクは無音を流し続ける（I2S と AEC 参照の時計を止めないため）。再生位置は 8×1023×4B（約0.34秒）巻き戻す。
3. **2段目（確かめる）**: 64ms 待ってから 384ms（12コマ）、AEC を通さずマイクだけを見る。「AC RMS 1200 以上（または飽和）」かつ「ESP-SR の VAD（モード2、先頭30ms）が声」のコマが3つで割り込み成立、足りなければ続きから再生。マイクのコマが1秒来なければ割り込み扱い。
4. 止まる長さは、声なら 0.19〜0.32 秒（そのまま聞き取りへ）、声でなければ約 0.5 秒＋巻き戻し分の繰り返し。
5. ログは次の要求の `device.prev`: `aec_triggers`（発火回数）・`aec_confirm_rejects`（続きから再生した回数）と、最後の確かめの `aec_confirm_voice_frames` / `_vad_frames` / `_loud_frames` / `_mic_max`（スピーカーを止めた後のマイクの最大）/ `_ms` / `_timeout`。**最後の1回しか残らない**ので、1返答で何度も再開した回の中身は分からない。

**分かったこと**
- 0.7.8 のデータでは、本物の声と誤停止で、AEC 後の強さも残り具合（声 38〜99%、誤停止 25〜88%）も重なり、1段目の数値だけでは分けられなかった。これが「止めてから確かめる」に変えた理由。
- 0.7.9（音量だけで確かめ）: 続きから再生した回はスピーカーを止めた後のマイク最大 61〜169、本物の声 2044 / 4311。マイクに指を当てた音（2400 台）で割り込みになった → 0.7.10 で VAD を条件に足した。
- 0.7.10（2026-11-10、ケースなし）: 声の割り込みは成立（マイク最大 2606〜4242、大きい音・VAD とも3コマ）。「わ！」・何もしていない時の発火は続きから再生。約2分の昔話で発火6回のうち5回が再開。無音（マイク最大 42）でも VAD が2コマ「声」と言った例があり、**VAD 単独では使えない**（音量との両方を条件にしているのはこのため）。
- **マイクの飽和で判定がほとんど休む返答がある**。ケースなしでも返答によってはコマの4〜6割が飽和（AEC 後 2万〜2.9万）、飽和しない返答は AEC 後 1300〜2000 程度。違いの原因は未確認（検索の有無と揃って見えたが、ケースありでは検索した返答も飽和したので偶然かもしれない）。
- **ケース（v0.6 系ペンダント）に入れると、飽和＋その後の休みで返答の約9割の間、判定が働かない**（2026-11-10 21:29〜、マイク最大 3万超）。「おーい」で止まらない。マイク SPH0645 / 0655 は基板の下向きポートで、箱にマイクの穴が無いので、閉じた箱の中のスピーカー音を聞いていると推定（推測）。対策はケース側（マイク直下の穴と、ポートを囲うガスケットで箱の内側と仕切る、スピーカー前面をパッキンで蓋の穴に密着、両者を離す）。音量は上げたい（利用者の希望）ので、音量を下げる対策は採らない。ファーム側で飽和後の休みを短くするのは誤停止が増えるので痛み止め以下。

`marks`・`segments`。ほかに `stt.ws_wait_ms`（録音開始時に Soniox が未接続だった時間。その間の声は落ちる）、`stt.disconnects` / `stt.errors`（ロードマップ20 の Soniox 切断の回数）。元の決定（2026-11-01・11-08）: 割り込みの記録（判定時の AC RMS としきい値・再生開始からの - **Soniox 切断後に録音へ戻す**（ロードマップ20、2026-11-04）: **実例らしきもの（2026-11-09〜10、0.7.9）**: 21:28 の会話の後つけっぱなしにし、翌朝 LED は点いているのに話しかけても無反応、電源の入れ直しで戻った。ログでは 22:00 頃の鍵の取り直しを最後に約10時間通信が無く、8:21 に起動し直している（推測: 待ち受けの長時間接続がどこかで切れ、録音に戻れなかった。切断回数は次の要求に添える方式なので、再起動で消えて残っていない）。直しには、切断後の再接続に加えて、長く待ち受けるだけのときに自分からつなぎ直すこと、切断と復帰の記録を再起動で消えないようにするか復帰直後に送ることを含める。0.7.8 以降のログでは、再生中の先行接続の切断（エラー付き）が長い返答の後などに 1 日数回あり、次の返答でつなぎ直して助かっている（つなぎ直しを待つ間の声は落ちる。2026-11-10 は 1.2 秒）。いまは `WStype_DISCONNECTED` で `isRecording` を false にするだけで、録音を立て直す処理が無い（戻す手段は電源の入れ直しだけ）。先行接続は返答の再生開始時に開始メッセージまで送り、再生が終わるまで音声を送らずに待つので、Soniox が最初の音声を待てずに 408 で閉じる、または idle（close 1001）で閉じる余地がある（閉じるまでの秒数は文書に無い。鍵の期限は開いている接続を切らないと文書にある）。直し: 切断されたら録音状態へ戻し、先行接続が無ければ接続し直す。証拠はシリアルで「Soniox disconnected」の後に「Starting STT recording」が続かない箇所。
- **Soniox の鍵を接続時に渡す**（ロードマップ22、期限 2027-01-15）: 開始メッセージの `api_key` は廃止予定で、接続時の `Authorization: Bearer` ヘッダーかサブプロトコル `soniox-api-key` に移す。先行接続ワーカーは鍵を先に用意してから接続する形に変える。
- **話し終わりの猶予 0.6 秒**（ロードマップ25から先に。2026-11-08 実装、ビルド確認のみ・実機未）: `END_SILENCE_MS`（途中結果が 800ms 更新されなければ送る予備判定）を外し、アプリの「ふつう」と同じ猶予にした。Soniox の `<end>` の後 `STT_GRACE_MS`（600ms）待ち、その間に声（ブロック RMS ≥ `STT_GRACE_SPEECH_RMS`）か新しい文字が出たら同じ発話として次の `<end>` を待つ。声だけで文字が `STT_GRACE_RESUME_MAX_MS`（3秒）来なければ送る。Soniox が `<end>` を送らずに 4 秒黙ったときの救済（`STT_STALL_MS`）は残した。Soniox の待ちの値（感度・最大待ち）は開始メッセージに足していない（25 でサーバーから配る）。**声のしきい値 1200 は暫定**（再生中監視と同じ `>>14` の尺度で、静かな部屋の声の大きさは未計測）。シリアルの `[GRACE] sent +…ms after first end (quiet|no new text|stall, resumed=…, speech_peak_rms=…, grace_peak_rms=…)` で、話している間と猶予中の音量を見て詰める。物音で毎回つなぐなら上げ、言葉の続きを拾えないなら下げる。
- **電池電圧・温度・充電状態を要求に添える**（ロードマップ25から先に。2026-11-08 実装、ビルド確認のみ・実機未）: `PowerSense.h`。起動時と録音中 30 秒ごとに読み（シリアル `[POWER]`）、会話の要求に `"device":{"vbat_mv","board_temp_c","chip_temp_c","chg_stat1","chg_stat2"}` を添える。Lambda は `trace.mjs` の `describeDevice` で1行ログの `device` に写す。電圧は分圧×2 の未校正値、基板温度は TH2（B=3380）から計算、STAT1/2 はピンの値のまま（意味は BQ25185 のデータシートと実機で確かめる）。`devices` への記録・一時キー要求への添付・アプリ表示は 25。本体側の計測（上）も同じ `device` に足す。**0.7.5 を試験機へ OTA（2026-11-08 15:47、beta）し、ログに値が届くことを確認**。このときは電池なし・USB 給電で、`vbat_mv` 4058〜4216、STAT 1/1 と 1/0 が入れ替わった（電池が無いので充電ICの BAT 端子の電圧と、電池を探す動きを読んでいると推定。電圧と STAT の意味は電池をつないで USB の抜き差しで確かめる）。基板温度 43〜46℃・チップ 51〜54℃（TH2 がチップの熱を拾っているかは未確認）。猶予は「若干遅いが許容」（ユーザーの体感。`[GRACE]` は未取得）。
- 接続先は CloudFront の固定ドメイン（0.7.4 で済）。OTA 対応（0.7 系で済）。
## 環境・ビルド

- ビルド確認済みのコアはArduino ESP32 3.3.11 / IDF 5.5.5。利用可能なAPIは実際のインストール済みコアで確認する。起動時の `[BUILD]` で実機の版を確認する。
- ボードはESP32-S3-MINI-1-N4R2（Flash 4MB、quad PSRAM 2MB）。Partition Schemeの設定は `no_fs` のままだが、スケッチのフォルダの `partitions.csv` が優先される（アプリ 1,792KB ×2 ＋ `voices` 384KB。0.7.30 から）。書き込みで「Erase All Flash」は使わない（Wi-Fi 設定とデバイス鍵が消え、鍵が変わって 403 になる）。
- mbedTLSのcallocは `TlsMemory.h` で起動時にPSRAMへ固定し、内部RAMへはフォールバックしない。
- Arduino IDE付属のarduino-cliでもビルド確認できる。リポジトリルートから（書き込み時は実機のボード・ポート・IDE設定を確認する）:

```powershell
arduino-cli compile --fqbn esp32:esp32:esp32s3:PSRAM=enabled,FlashSize=4M,PartitionScheme=no_fs,CDCOnBoot=cdc --build-path "$env:TEMP/toytalker_v07_build" devices/mcu/esp32_s3/toytalker_mini_v0.7
```

`sketch.yaml` の `default_fqbn` があるので `--fqbn` を省略してもよい。
