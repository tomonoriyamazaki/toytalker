### OTA の検証と失敗の扱い（2026-11-11〜12、試験機で確認済み）

- **検証3件は済**: SHA改ざん（マニフェストの SHA を1文字変える → `sha256 mismatch` → `fail: stage=sha256` で元の版のまま会話へ）、電源断（60% で USB を抜く → 元の版で起動 → `try=2` で入り直して成功）、ロールバック（鍵取得の前に `abort()` する版 → ブートローダーが元の版へ戻す → `rollback detected` → `skip: … rolled back before` でループせず会話へ）。
- **失敗の扱いを変えた（0.7.12、直しは 0.7.17）**: 以前は失敗の種類を問わず3回でその版を諦めていた（偶然の失敗が3回でその版が二度と来ない。試験機で実際に起きた）。いまは、ロールバックした版だけ以後試さず（`bad`）、ダウンロードの失敗（電源断・通信・SHA 不一致）は諦めずに、続けて3回で「5回の起動に1回」へ間を空ける（弱い Wi-Fi で起動のたびに最大3分待たせないため。数字は決め打ち）。次の版が出ればどちらも数え直す。
- **成功の判定は有効印の時**（`confirmRunningImage()` → `markUpdateSucceeded()`）。0.7.12 は起動の最初に「入れた版が動いている＝成功」として記録を消したため、落ちる版を入れ直し続けた（試験版 0.7.16 で約5周。beta を戻して止めた）。0.7.12〜0.7.15 にはこの穴があるので配らない。
- **結果はサーバーで見える**: 起動時の鍵取得に `ota_last` / `ota_fails` / `ota_bad` を添え、Lambda の1行ログに出る（[infra/README](../infra/README.md)）。発行の誤りの疑い（勧めている版のロールバック・SHA 不一致）は警報 `toytalker-ota-broken-rnd` が即メール、版の分布と失敗が続く機器は月次レポート。警報の条件・月次の節・ログの項目は実ログで確認済み。**警報のメールが実際に届くところは未確認**（本物のロールバックを勧めている最中に起こす必要がある。次に試験版を出すときに見る）。
- **残る弱点（未対応。下の「次にやる OTA の直し」の1）**: 新しい版の最初の起動で、鍵取得の前に電源が切れるか Wi-Fi が繋がらないまま電源を切ると、ロールバック扱いになってその版を試さなくなる（次の版で追いつく）。
- 試験の進め方: 版だけ上げて `publish-firmware.sh beta`、マニフェストは S3 から取って手で直して置く（Lambda は60秒覚えている）。シリアルは PowerShell の `System.IO.Ports.SerialPort` で DTR/RTS を立てずに開く（立てると開くたびに本体がリセットされ、試行回数を消費する。`arduino-cli monitor` は標準入力が無いとすぐ終わる）。

### 次にやる OTA の直し（2026-11-13 に決定、未着手。11/15 の配布版に入れる）

いまの状態: 試験機は 0.7.17、beta = 0.7.17、stable は未設定。S3 には 0.7.11〜0.7.18 が残っている（0.7.16 と 0.7.18 は落ちる試験版でタグなし）。**次の版は 0.7.19 から**。

1. **2回戻ったら試さない（ファーム、`OtaUpdater.h`）**。いまは1回のロールバックでその版を `bad` に入れる。良い版でも、最初の起動で有効印（`confirmRunningImage()`）の前に電源を切られると同じ扱いになり、次の版が出るまで取り残される。直し: NVS の `ota` に、いま狙っている版が戻った回数を足す。`checkPreviousUpdate()` で戻りを見つけたら数を増やし、1回目は `bad` に入れず同じ版を入れ直す、2回目で `bad` に入れる。数は、狙う版が変わった時と成功した時（`markUpdateSucceeded()`）に 0 へ戻す。落ちる版のループは2周で止まる。
   - 決めること: 1回目の戻りをサーバーへどう伝えるか。案は `ota_last=rollback1`（警報なし）、2回目で従来の `rollback`（`ota_bad` と合わせて警報）。こうすれば Lambda（`toytalk-soniox-stt-lambda` の `ota_alert` の条件）は変えなくてよい。月次レポートの文言も変わらない。
   - 実機で見ること（試験機、シリアルは下の「試験の進め方」）: (a) 落ちる試験版（鍵取得の前に `abort()`）を beta に出す → 入れる → 戻る → **もう一度入れる** → 戻る → `skip: … rolled back before` で止まる。(b) **このとき警報 `toytalker-ota-broken-rnd` のメールが届くこと**（11/12 に未確認のまま残した点）。(c) 良い版を出し、入った直後の最初の起動で鍵取得の前に電源を切る → 次の起動で入れ直して成功する。
   - 終わったら beta を良い版へ戻す。落ちる試験版にはタグを付けない。
2. **SHA の誤りを発行の時点で止める（`publish-firmware.sh`）**。マニフェストを書いた後に、S3 に置いた .bin を取り直して SHA-256 とサイズをマニフェストの値と比べ、合わなければエラーで終わる（beta を前の版へ戻すかは実装時に決める）。機器が `sha256` で弾いて警報が鳴る前に、原因の側で止める。確認は、わざと違う値で比べさせて止まること。

### 待ち受けの見張り: 切れたら戻す・無音なら休む（0.7.19、2026-11-13。ロードマップ20・24。**ビルド確認のみ・実機未**）

値と仕組みは `.ino` の「待ち受けの見張り」（`watchSttConnection` / `enterIdleSleep` / `serviceIdleSleep` / `playSleepChime`）。

- **切れたら戻す**: 聞き取り中のはず（`sttWanted`）なのに「録音中かつ Soniox 接続済み」でなければ、1.5 秒後に `startSTTRecording()` をやり直す（鍵が古ければ取り直してから新しく接続）。続けて失敗したら 3 → 6 → … 30 秒まで間を空け、30 秒つながっていたら 1.5 秒に戻す。Wi-Fi が切れている間は数えない。シリアルは `[STT_RECOVER]`。以前は切断で `isRecording` を false にするだけで、ライブラリが自動でつなぎ直しても音声を送らず、電源の入れ直しでしか戻らなかった。
- **無音なら休む**: 文字が出ないまま 3 分（`STT_IDLE_SLEEP_MS`）聞き続けたら、Soniox を閉じて休む（Soniox は無音でも接続の時間で課金する。ロードマップ24）。数え始めは待ち受けの開始と最後に文字が変わった時の遅いほう。つなぎ直しでは巻き戻さない。休みに入る時に下がっていく短い音（880→330Hz、0.35 秒。ファームの中で作る）を鳴らし、LED は PWM でゆっくり明滅（4 秒に1回。PWM を使うのは休み中だけ）。**ボタンを押すと聞き取りに戻る**（長押しは従来どおり BLE 設定）。シリアルは `[IDLE] sleep` / `[IDLE] wake`。休み中は `ws.loop()` を呼ばない（ライブラリが自分でつなぎ直すため）。
- **休み中に変わること**: Soniox の鍵の取り直しも止まるので、`devices` の `last_seen` が休みに入った時刻で止まる（休んでいるのか電源が切れているのかはサーバーから区別できない）。Wi-Fi はつないだまま（省電力はロードマップ19）。切断・復帰・休みの回数はサーバーへは送っていない（`stt.disconnects` は従来どおり次の要求に載る）。
- **試験（実機で見ること）**: ① 黙って 3 分 → 音が鳴り、明滅し、`[IDLE] sleep` ② ボタン → LED がゆっくり点滅 → 点灯になり、話すと返事が来る ③ 休み中の長押し → BLE 設定に入る ④ 休みから戻った後の会話で割り込み・相槌・猶予が今までどおり ⑤ 止まる音の大きさと音色、明滅の速さと明るさ ⑥ 切断: 長い返答の後などに `Soniox disconnected` が出たら `[STT_RECOVER]` → `Starting STT recording` が続くこと（狙って起こすなら会話の待ち受け中にルーターの電源を数秒切る）⑦ 一晩つけっぱなし → 朝ボタンで戻る。
- **次**: 声で起こす（ロードマップ32）、休みに入るまでの時間をサーバーから配る（25）。

### 声の割り込み（0.7.9〜0.7.10、2026-11-09〜10。ロードマップ21）

**仕組み**（値は `AecBargeGate.h`、判定は `AecMonitor.h`、一時停止は `.ino` の `playerPaused`）。1コマ＝512サンプル＝32ms（ESP-SR の AEC の単位）。音の値は 16bit（±32767）で、しきい値は1コマの AC RMS。
1. **1段目（一時停止する）**: AEC 後の AC RMS が 1200 以上で4コマ（128ms）続き、かつ AEC 後がマイクの 25% 以上残っている。判定しないのは、再生開始から 500ms、再開から 300ms、マイク飽和から 256ms、処理が 200ms 以上遅れたコマ。
2. 発火したらアンプを切り（AMP_SD LOW）、再生タスクは無音を流し続ける（I2S と AEC 参照の時計を止めないため）。再生位置は 8×1023×4B（約0.34秒）巻き戻す。
3. **2段目（確かめる）**: 64ms 待ってから 384ms（12コマ）、AEC を通さずマイクだけを見る。「AC RMS 1200 以上（または飽和）」かつ「ESP-SR の VAD（モード2、先頭30ms）が声」のコマが3つで割り込み成立、足りなければ続きから再生。マイクのコマが1秒来なければ割り込み扱い。
4. 止まる長さは、声なら 0.19〜0.32 秒（そのまま聞き取りへ）、声でなければ約 0.5 秒＋巻き戻し分の繰り返し。
5. ログは次の要求の `device.prev`: `aec_triggers`（発火回数）・`aec_confirm_rejects`（続きから再生した回数）と、最後の確かめの `aec_confirm_voice_frames` / `_vad_frames` / `_loud_frames` / `_mic_max`（スピーカーを止めた後のマイクの最大）/ `_ms` / `_timeout`。**最後の1回しか残らない**ので、1返答で何度も再開した回の中身は分からない。

**分かったこと**
- 0.7.8 のデータでは、本物の声と誤停止で、AEC 後の強さも残り具合（声 38〜99%、誤停止 25〜88%）も重なり、1段目の数値だけでは分けられなかった。これが「止めてから確かめる」に変えた理由。
- 0.7.9（音量だけで確かめ）: 続きから再生した回はスピーカーを止めた後のマイク最大 61〜169、本物の声 2044 / 4311。マイクに指を当てた音（2400 台）で割り込みになった → 0.7.10 で VAD を条件に足した。
- 0.7.10（2026-11-10、ケースなし）: 声の割り込みは成立（マイク最大 2606〜4242、大きい音・VAD とも3コマ）。「わ！」・何もしていない時の発火は続きから再生。約2分の昔話で発火6回のうち5回が再開。無音（マイク最大 42）でも VAD が2コマ「声」と言った例があり、**VAD 単独では使えない**（音量との両方を条件にしているのはこのため）。
- **マイクの飽和で判定がほとんど休む返答がある**。ケースなしでも返答によってはコマの4〜6割が飽和（AEC 後 2万〜2.9万）、飽和しない返答は AEC 後 1300〜2000 程度。違いの原因は未確認（検索の有無と揃って見えたが、ケースありでは検索した返答も飽和したので偶然かもしれない）。
- **ケース（v0.6 系ペンダント）に入れると、飽和＋その後の休みで返答の約9割の間、判定が働かない**（2026-11-10 21:29〜、マイク最大 3万超）。「おーい」で止まらない。マイク SPH0645 / 0655 は基板の下向きポートで、箱にマイクの穴が無いので、閉じた箱の中のスピーカー音を聞いていると推定（推測）。対策はケース側（マイク直下の穴と、ポートを囲うガスケットで箱の内側と仕切る、スピーカー前面をパッキンで蓋の穴に密着、両者を離す）。音量は上げたい（利用者の希望）ので、音量を下げる対策は採らない。ファーム側で飽和後の休みを短くするのは誤停止が増えるので痛み止め以下。

**次**
- 会話の検証はケースから外し、置き方と音量を固定して行う。数値（1200・25%・VAD モード・確かめの 1200）の詰めはケースの形が固まってから。
- 確かめの回ごとの値を残す（1返答で複数回の再開を見るため）。飽和する返答としない返答の違い（再生音量・参照 RMS）を調べる。
- スマホからの ON/OFF（25）。11/15 の束（下）にはこの方式を入れたまま配る（2026-11-10 決定。配布機も以後は OTA で直せるため）。

- **電池電圧・温度・充電状態を要求に添える**（ロードマップ25から先に。2026-11-08 実装、ビルド確認のみ・実機未）: `PowerSense.h`。起動時と録音中 30 秒ごとに読み（シリアル `[POWER]`）、会話の要求に `"device":{"vbat_mv","board_temp_c","chip_temp_c","chg_stat1","chg_stat2"}` を添える。Lambda は `trace.mjs` の `describeDevice` で1行ログの `device` に写す。電圧は分圧×2 の未校正値、基板温度は TH2（B=3380）から計算、STAT1/2 はピンの値のまま（意味は BQ25185 のデータシートと実機で確かめる）。`devices` への記録・一時キー要求への添付・アプリ表示は 25。本体側の計測（上）も同じ `device` に足す。**0.7.5 を試験機へ OTA（2026-11-08 15:47、beta）し、ログに値が届くことを確認**。このときは電池なし・USB 給電で、`vbat_mv` 4058〜4216、STAT 1/1 と 1/0 が入れ替わった（電池が無いので充電ICの BAT 端子の電圧と、電池を探す動きを読んでいると推定。電圧と STAT の意味は電池をつないで USB の抜き差しで確かめる）。基板温度 43〜46℃・チップ 51〜54℃（TH2 がチップの熱を拾っているかは未確認）。猶予は「若干遅いが許容」（ユーザーの体感。`[GRACE]` は未取得）。
