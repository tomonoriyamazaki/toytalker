# レコーダー（ペンダント型の録音・文字起こし機）

ToyTalker とは別の製品の案。**状態（2026-11-23）: 構想だけ。コードも基板も無く、売ると決めてもいない。** ロードマップには載せていない（載せるのは「やる」と決めてから）。この文書は構想の現在の形を持ち、上書きで更新する。

## 何を作るか

- ペンダント型の本体が録音し、BLE でスマホへ送る。スマホの中で文字起こしと要約をする。
- **既定はどこにも送らない。** サーバーもアカウントも要らない。本体は売り切りで、サブスクは無い。
- 利用者が選んだ録音だけ、クラウド（Soniox の非同期の文字起こし）で高精度にやり直せる。料金は前払いポイントから引く。送る前に金額と送り先を出す。
- アプリ内に会話機能は作らない。文字起こしと要約を、OS の共有と、利用者が選んだフォルダへの Markdown 書き出しで、利用者自身の ChatGPT や Claude へ渡せるようにする。
- 録音中の表示（LED）は消せない作りにする。

狙う立ち位置: 他社は本体 2〜3 万円 + サブスク + クラウド前提（Plaud NotePin、Omi）。Limitless は Meta、Bee は Amazon に買われた。「安い・売り切り・既定で端末の外に出ない」の組み合わせは主要どころに無い。価格だけでは安い中国製に勝てないので、守るのは「データが外に出ない」のほう。利益は本体で取り、ポイントは必要な人が原価に近い値段で使えればよい。

言い方の注意:
- 基板は JLCPCB で作るので「日本製」とは書かない（原産国の不当表示になるおそれ）。「日本で設計・開発」まで。
- クラウドを足した後は「完全ローカル」ではなく「既定はローカル、許可した分だけ外へ」と書く。
- クラウドの要約を作る場合、文章はこちらの Lambda を通る（保存はしない）。「サーバーに送らない」とは言えない。

## 決めたこと

| 項目 | 決定 | 理由 |
|---|---|---|
| アプリ | ToyTalker とは別のアプリ | ストアのプライバシー表示がアプリ単位。対象（子供向け / 大人向け）と権限（BLE の常時バックグラウンド）が違う。アカウント無しで使わせたい |
| AWS と Cognito | ToyTalker と共用。レコーダー用の Lambda は別の CDK スタック | 財布を共通にするには利用者の名簿も共通にするしかない。権限は「財布から引く」「利用者を読む」だけに絞る |
| ポイント | ToyTalker と同じ財布（1 ポイント = 税込み 1 円のまま） | 同じ発行者なら 2 製品でも自家型前払式支払手段のまま（[原価と課金の考え方](pricing-and-cost-model.md) 11.7）。別法人に分けると第三者型になるので、法人化するなら両製品を同じ法人に入れる |
| ログイン | 任意。ローカルだけの人はアカウント不要 | 売りを保つため |
| 文字起こしと要約の実装 | アプリの中で「音声を渡すと文章が返る」「文章を渡すと要約が返る」の口を 1 つずつにまとめる | スマホ内とクラウドを後から差し替えるため |
| 処理のタイミング | リアルタイムにしない。本体に貯めて送り、スマホは充電中などにまとめて処理 | 大きめのモデルを使えて精度が上がる。本体の電池と BLE の切断にも効く |
| 最初の版 | サーバー無し・ログイン無し | クラウドはローカルの精度が足りないと分かってから足す |

ポイントの呼び名は製品名ではなく発行者に寄せる（「ZakiCorp ポイント」か、単に「残高 ◯円分」）。購入ページは使える先を「ToyTalker 専用」と言い切らないでおく。

### 誰の声かの区別

| 段階 | 内容 | この製品での扱い |
|---|---|---|
| 話者分離（話者 1・話者 2 に区切る。名前は分からない） | Plaud にある。Soniox にも付いている | クラウドでやり直した録音は分かれて返る。スマホ内は OS 標準の文字起こしに無いので、最初の版は区別なし |
| 「自分」と「それ以外」だけ分ける | Omi が持ち主の声を登録してやっている | 持ち主 1 人分の声をスマホの中に登録する形なら、預からない設計のまま作れる。要約で自分の発言と相手の発言を分けられる。足す候補 |
| 他人の声を名前付きで識別する | Limitless にあったはず（記憶） | **作らない。** 声の特徴（声紋）は個人情報保護法で個人を識別する情報にあたり、本人の同意なしに持つことになる。「相手の声紋は作らない」は売りとも合う |

他社の機能は記憶によるもので、調べ直していない。

## ハード

| 項目 | 案 | 確かめた範囲 |
|---|---|---|
| マイコン | Nordic nRF54L15 のモジュール **Raytac AN54LQ-15**（チップアンテナ、9.5×13.7mm） | LCSC の部品番号 C49419243。JLCPCB の Pre-order で 1 個 $6.52・納期 約 11 日（2026-11-23 の画面）。LCSC の定価は 100 個で $4.87（在庫 0）。基板パターンのアンテナの AN54LQ-P15 は JLCPCB に登録なし |
| 技適 | Raytac の製品ページに Telec (MIC) の記載 | **認証番号は未照合**。発注前にデータシートの番号を総務省の検索で確かめる |
| 電源電圧 | 1.7〜3.6V | 電池（4.2V）を直結できない。3.3V か 3.0V に落とす |
| 開発環境 | Zephyr（nRF Connect SDK）。Arduino は使わない | nRF54L15 は USB のデータ回路を持たないはず（記憶。要確認）。書き込みは SWD、買った人の更新は BLE 経由 |
| 書き込み | 開発ボード nRF54L15 DK の内蔵 J-Link から、自作基板の SWD パッド（SWDIO・SWCLK・GND・電源・リセット）へ | DK に「Debug out」があるかは未確認（nRF52840 DK にはある） |
| 録音の保存 | 基板にはんだ付けする SPI フラッシュ（WSON-8、6×5mm か 8×6mm）。**上限の目安は 128MB**。最初は SPI NOR の 64MB（Winbond W25Q512 など）で始め、順番書きの仕組みができたら同じ形の SPI NAND 128MB（W25N01 など）に載せ替える | Opus 16kbps で 1 時間 約 7MB（64MB で約 9 時間、128MB で約 17 時間）。NOR と NAND でピンの並びが同じかは未確認（記憶）。Omi の製品版は 512MB |
| マイク・充電・3.3V | 基板 v0.4 の回路を写す（SPH0655LM4H・BQ25185・AP2112K-3.3）。スピーカーとアンプは削る | 充電電流は電池に合わせて下げる（v0.4 は 300mA、小さい電池なら 100mA 前後） |

ESP32-S3 を製品に使わない理由: BLE だけ使っても送受信時に 100mA 前後、CPU も数十 mA で、200mAh の電池だと数時間。nRF は録音 + 送信の平均が 2〜3mA の見込みで、同じ電池で 3 日前後（見積もり。実測はまだ）。Omi は開発キットが nRF52840、製品版が nRF5340。

nRF52840（Raytac MDBT50Q-P1MV2、技適の記載あり、正規の販売店で 1 個 $6〜9）も候補だったが、nRF54L15 のほうが安く、小さく、消費電流が約半分（Nordic の公表値）。JLCPCB と LCSC の「Other Suppliers」経由の MDBT50Q は $17〜21 と割高。

フラッシュの容量と種類の考え方:
- **128MB より増やさない理由は同期の時間。** BLE の実効速度を 300kbps と置くと録音の約 19 倍の速さで送れ、8 時間分（58MB）で約 25 分、17 時間分（128MB）で約 55 分、512MB だと約 4 時間。nRF54L15 は USB でデータを送れないので、BLE より速く吸い出す道が無い。スマホが近くにあれば随時送るので、貯めるのは離れている間の分だけ。
- **NAND は不良ブロックの扱いが要る**が、録音は「先頭から順に書いて、送り終わったら消す」だけなので、汎用のファイルシステムを使わず、不良ブロックを飛ばして順に書く作りにすれば難しくない。Zephyr の標準のドライバーは NOR 向けで、NAND は自分で書くことになりそう（要確認）。
- **電池持ちは選ぶ理由にならない。** 1 秒に 2KB 書くだけなので、書き込みの電力はどちらでも小さい（書き込み自体は NAND のほうが速くて省電力）。待機時の消費は NAND のほうが大きいが、フラッシュの電源をスイッチで切れば済む。
- SD NAND（はんだ付けする SD カード、512MB〜）は、不良ブロックの管理を部品がやるが、上の理由で大容量が要らないので採らない。

電流を測ってから見直す点（2 版目の仕事）:
- **マイク**: SPH0655 の消費電流は DigiKey の掲載で 2mA（最大値か通常時かは未確認）。全体が 2〜3mA なので一番電気を使う部品になりうる。低電力モードの有無と、省電力のマイク（TDK T5838 など。記憶）を比べる。
- **3.3V の電源**: AP2112K の自己消費 約 55µA は、録音中は 2% 程度で無視できる。効くのは電源を入れたまま録音していない時間だけ。替えるなら自己消費 1µA 以下の LDO か、Nordic の電源 IC（nPM1100 / nPM1300）。

JLCPCB の部品の買い方: Pre-order で買うと自分専用の在庫（Parts Manager の My Parts Lib）に入り、以後の実装はいつもの日数で進む。保管料は無料、取り出しは原則できない。**買ったら、その基板の部品表に個数と日付を書く**（部品検索の画面には「Stock: 0」としか出ないので、忘れると気づけない）。

## 進める順番

お金のかかる判断を後ろに寄せる。

1. **スマホ内の文字起こしを試す**: 胸元の位置で会話を 30 分録り、スマホ内の文字起こしに通す。読める文章にならなければ、この案は「安い従量制のクラウド型」に変わる。
2. **アプリ側を作って自分で使う**: 今ある ESP32-S3 の基板で BLE 送信だけ作り、受信 → 文字起こし → 要約を 1〜2 週間使う。電池が数時間でも検証はできる。
3. **nRF54L15 DK を買う**: PDM マイクの小さな基板をつなぎ、録音・Opus 圧縮・BLE 送信と電流の測定。
4. **並行して基板を設計し、モジュールを Pre-order する**。開発ボードで録音と送信が動いてから基板を発注する。
5. **売ると決めたら**: 技適の番号の照合、Bluetooth の申告、PL 保険。

## 置き場所

- 今はこの文書だけを ToyTalker のリポジトリに置く。
- コードを書き始めたら、**ファーム・アプリ・基板は別のリポジトリ**にする。製品も開発環境（Zephyr）も違い、「アプリが何も送らないこと」を第三者が確かめられるようにコードを公開するなら、ToyTalker のコードと混ざっていないほうが読みやすい。
- クラウド側（財布から引く Lambda）だけは、認証と課金を共用するので ToyTalker の `infra/` と `backend/` に置く。
