# TTSフォールバックとプッシュ通知

Cartesiaの同時接続上限（Pro 3 / Startup 5 / Scale 15、超えると即429、キュー無し）に当たっても会話を止めないための仕組みと、それに付随する通知の考え方（2026-09-13合意）。

## いまの状態

- **実装済み（2026-09-13）**: 本文・相槌・読み上げのLambda5本のフォールバック（第2・3・5節）。
- **実装済み（2026-11-01、ロードマップ5）**: 本文Lambdaの遅延条件（1文が3秒を超えたら切り替える）、月次レポートの「切り替え回数」と「ピーク同時本数」、アプリの表示（会話画面と読み上げ）。
- **未確認**: 本番で Cartesia の上限を超える負荷をかけて、実際に切り替わることを見る試験（第7節）。
- **やらない（前払いポイント制のときに作る）**: 親向けの「今日はN回ずんだもんに切り替わりました」と、プッシュ通知（第6節）。

## 1. 背景

- Cartesiaは声の品質と速度で本命だが、同時接続数がプランで固定されている。1人の会話が消費する同時接続は平均0.3本程度（1文0.5〜1秒の要求）で、Scaleなら40〜50人が同時に会話できる見込み。ただし瞬間的な重なりで16本目が来れば429になる。
- 複数アカウントで上限を回避する案は却下。規約がグレーなことに加え、クローンボイスがアカウント単位なので利用者を分けると声の資産が分断される。上限の追加購入・Enterpriseの条件はCartesiaに問い合わせ中（2026-09-13送信、返答待ち）。
- **Cartesiaの回答（2026-09-13、営業担当）**: (1) Scaleの15を超える同時接続はEnterpriseのみで、追加購入は無い。Enterpriseは月$1,750から、月67,000分（約5,000万字）込み、同時接続と単価はコミット量で改善。(2) サーバー側の順番待ちは無く、クライアント側の再試行が想定どおりの使い方。エラーはクレジットを消費しない。(3) 同一組織の複数APIキーは同時接続の枠を共有（上限は組織単位）。本番と検証を分けるなら別組織。(4) クローンボイスは組織単位なので、バックエンドが1組織の認証情報で作れば全部同じ組織に集まる。
- 線引き: Enterpriseの入口（月$1,750、5,000万字≒AI発話2,400時間）は1人月10時間で約240人分。そこまではScale（15）で運用し、検証用はFreeの別アカウントを作る。
- 実測（2026-09-13、Pro、読み上げLambda経由で1文ずつ同時に投げた）:

| 同時件数 | 中央値 | 90%点 | 最大 | 429で切り替わった数 |
|---|---|---|---|---|
| 16 | 1.3秒 | 2.2秒 | 2.4秒 | 0 |
| 32 | 2.6秒 | 4.0秒 | 4.4秒 | 0 |
| 48 | 4.2秒 | 6.5秒 | 6.9秒 | 0 |
| 64 | 4.5秒 | 7.6秒 | 8.5秒 | 0 |
| 96 | 3.1秒 | 7.8秒 | 9.1秒 | 27（全部429、フォールバックで利用者にはエラーなし） |

  Proの「同時3」は短い要求には実質64件程度まで拒否されず、代わりに待たされる。「順番待ちは無い」という回答とは食い違うが、短い要求は瞬間的に枠が空くためと見ている。実用上の上限は429の手前ではなく「遅くなり始める16〜32件」で、同時に話す10人程度ならPro、それ以上はScale。
- このため失敗だけでなく遅さでも切り替える（第2節）。待たされる状態でも会話のテンポを守れる。Scaleへ上げる時期は月次レポートの「ピーク同時本数」「切り替え回数」で判断する（第4節）。
- フォールバック先はSakura Internet（ずんだもん）。原価が1文字0.0003円と最安で、円建て・国内・同時接続の制約が緩い。

## 2. フォールバックの動き（本文Lambda: App / ESP32 共通）

```
文ごとのTTS呼び出し
  → 主プロバイダー（キャラクターの声）で生成
  → 429 / 408 / 5xx なら 0.3秒待って再試行、だめなら 0.6秒待ってもう1回
  → 1回の呼び出しが3秒を超えたら、待たずに打ち切る（再試行しない）
  → どちらでもだめなら、その文からずんだもん（Sakura）で生成
```

- 追加の遅延は、失敗なら最大1秒程度、遅さなら3秒。それ以上待つより声を変えたほうが体感は良い。
- **3秒の根拠**（2026-10-12〜11-01の本文ログ、会話118回）: Cartesia は1文の合成が中央値0.5〜0.7秒・最大2.0秒、FishAudio は中央値1.2秒（48文字の文で1回だけ3.1秒）、OpenAI は約2秒。ふだんの会話では切り替わらず、詰まったときだけ効く。10/31 の「……！」の件（Cartesia が1文に92秒）もこの条件なら3秒で抜けられた。
- **Gemini は遅延条件の対象外**。ふだんから1文に数秒かかり、毎回ずんだもんになってしまうため（`TTS_SLOW_EXEMPT`）。失敗での切り替えは効く。
- 打ち切った呼び出しは裏で走り切り、結果は捨てる。その分の主プロバイダーの費用は記録されない（遅いときだけなので無視できる量）。ログの `ext` には `slow: true` が付き、エラー名は `TtsSlowError`。
- 主プロバイダーもフォールバック先もPCM 24kHz（Appは同じWAV化経路）なので、再生側の変更は不要。
- **返答単位で固定する。** 一度切り替えたら、その返答の残りの文はずんだもんのまま。文ごとに声が行き来しないようにする。次の返答からは再び主プロバイダーを試す。
- **切り替わった最初の返答の頭に一言足す**（例:「いまは混んでるから別の声で話すね」）。ESP32は画面が無いので、子供にはこれで伝える。
- Cartesia専用にせず「主プロバイダーが失敗したらSakuraへ」の共通の仕組みにする。ElevenLabsやOpenAIの障害・上限にも同じコードが効く。
- 判定は例外のHTTPステータスで行う。各プロバイダーの関数は `status` を持つエラーを投げるように揃える（現在はメッセージ文字列に埋め込んでいるだけ）。

## 3. コスト記録

- 実際に使った声で記録する。返答内の文字数を主プロバイダー分とSakura分に分け、`toytalker-usage` に2行（例: `cartesia#tts` と `sakura#tts`）として加算する。現在は返答全体を1プロバイダーで記録しているため、集計側の変更が要る。
- 会話ログにも `tts_fallback: { from, to, chars }` を残す。

## 4. 記録と可視化

- Lambdaログ（1リクエスト1行のJSON、`backend/shared/trace.mjs`）: 本文は `tts_fallback_chars` と、文ごとの `segments[].fallback`。相槌・読み上げは `tts_fallback: "sakura"`。主プロバイダーの失敗は `ext` と `errors`（`tts_primary`）に残る。
- **月次運用レポート**（`toytalker-ops-monthly-lambda`、[原価と課金の考え方](pricing-and-cost-model.md) 第10節）の「■ TTS の切り替えと同時本数」: 本文・相槌・読み上げそれぞれの切り替え回数（うち遅さで切り替えた回数）と、声の会社ごとのピーク同時本数とその時刻。Lambda5本のログ（CDKが `TTS_LOG_GROUPS` で渡す）を Logs Insights で1日ずつ読む（1回の問い合わせは1万行まで。超えた日はレポートに「途中まで」と出る。120秒で打ち切り、レポートの残りは送る）。会話の文章はログに無いので、読むのは時刻・所要時間・声の会社・エラーの種類だけ。同時本数は、本文なら文ごとの [`text_at`, `text_at + tts_ms`]、相槌・読み上げなら段階の時刻から区間を作って重ねる。再試行の待ちも含むので少し多めに出る（上限の判断には安全側）。これが Scale / Enterprise へ上げる時期の判断材料になる。
- **アプリ**: `tts` イベントに `fallback: "sakura"` が付いたら、会話画面に「（混み合っているため、一時的に別の声で話しています）」を返答ごとに1回出す。読み上げは `X-TTS-Fallback` ヘッダーを見て「混み合っているため、一時的に別の声で作りました」を出す。
- 親向けの「今日は混雑でN回ずんだもんに切り替わりました」は作っていない。プッシュ通知と一緒に、前払いポイント制のときに作る（第6節）。

## 5. 相槌と読み上げ

- **相槌Lambda（App / ESP32）**: 主プロバイダー失敗→即ずんだもん。短文なので再試行はしない。
- **読み上げLambda**: 利用者が声を選んでいるので勝手に変えるのは微妙だが、エラーで止めるより親切なので「切り替えて生成し、レスポンスヘッダー（例: `X-TTS-Fallback: sakura`）で知らせる」にする。アプリは再生前に一言表示する。

## 6. プッシュ通知の考え方

- **切り替わるたびにプッシュはしない。** 混雑中は数分間切り替わり続けるので通知が連打になる。通知するなら「1日1回まとめ」か「主プロバイダーが長時間落ちているときだけ」。
- プッシュの仕組み（Expo Push Notifications）:
  1. アプリ: `expo-notifications` で許可を取り、端末のExpo Push Tokenをデバイス設定Lambdaへ送って `owner_id` に紐づけて保存（テーブル1つ追加）。
  2. サーバー: 通知を出すLambdaがオーナーのトークンを引き、Expoの送信API（`https://exp.host/--/api/v2/push/send`）へJSONを1つPOST。ExpoがAPNs / FCMへ配る。Apple側の証明書はEASが管理。
  3. 費用: Expoの送信は無料。Lambda側は数十行。
- プッシュが本当に効く場面: 前払いポイントの残りが少ない（課金の導線として最重要）、1日の会話まとめ、本体のオフライン・エラー、外部サービスの長時間障害。
- 順番: 429対策は「返答の頭に一言＋サーバー記録＋アプリ表示」で完結させる。プッシュは前払いポイント制を作るときに一緒に入れ、そのときに切り替え通知も「1日1回まとめ」として乗せる。

## 7. 確認

- 2026-09-13: 読み上げLambda経由で96件を同時に投げ、27件が429でずんだもんに切り替わって利用者にエラーが出ないことを確認した（第1節の表）。
- 未確認: 本文の会話中に上限を超えたとき、声が切り替わって一言が入ること、記録が2行に分かれること、月次レポートに回数が出ること。月次レポートは手動実行（`{"send": false}`）で今月分を出して確かめられる。
