# 意図的に先送りしている項目

コードから読み取れない「やらないと決めた理由」と、着手時の設計メモ。着手したらここから消す。

## 読み上げモード（`toytalker-tts-only-lambda` / `app/components/ReadAloud.tsx`）
- 長文分割: 単一TTS呼び出しのみ。OpenAIの4096字などプロバイダー上限を超えるとエラーがそのままアプリに出る。
- 日英分割読み: 単一ボイスで一括読み。
- Androidのバックグラウンド再生: フォアグラウンドサービスが必要。現状アプリはiOSのみ提供。
- iOSのバックグラウンド再生は `app.json` に `UIBackgroundModes: ["audio"]` を追加済みだが、EASのネイティブ再ビルドが必要でOTA更新では反映されない。

## ユーザー認証
- 現状の `owner_id` はアプリ初回起動時のランダムUUIDで、認証なし。iOSはキーチェーンに保存、Androidはアンインストールで消える（許容済み）。
- 本格認証はCognito + Sign in with Appleを想定。実装時はJWT検証をLambda内のJWKSキャッシュでローカル完結させ、音声パイプラインにネットワーク認証を挟まない（会話レイテンシ維持）。既存 `owner_id` のデータは初回ログイン時にアカウントへ紐付け移行する。
- いまの見え方の制御は「クライアントが送る `owner_id` を信用する」方式。公開一覧は `owner_id` 付きの行を除外し、カスタムボイス（ZakiCorp / Cartesia）の一覧・作成・削除・合成は本人確認なし。他の利用者には見えないが守ってはいない（IDが推測できない長さであることだけが壁）。
- 導入時の原則は **Lambdaがクライアントの `owner_id` ではなく検証済みトークンの本人IDを使う**。これで一覧・作成・削除・合成のすべてが本人に限定され、クローン機能の作りはそのまま活きる。決めておく点は次の4つ。
  1. `owner_id` は内部IDのまま残し、`sub → owner_id` の対応表（例: `toytalker-users`）を1つ持つ。初回ログイン時に端末の `owner_id` を紐づければデータ移行が要らない。未ログイン端末の扱い（ログイン必須かゲスト継続か）は導入時に決める。
  2. ESP32はログインしない。本体は `device_id` だけ送り、Lambdaが `toytalker-devices` からオーナーを引く現在の方式を維持。代わりにデバイス登録をログイン必須にする。
  3. トークン検証は本文Lambdaの中で行う（Function URLのストリーミング構成を崩さない）。JWKSはLambdaでキャッシュ。相槌・Soniox一時キー発行なども同じ検証関数を共通化。CloudFrontは静的配信・WAF等の目的があれば別途で、認証の必須要素ではない。
  4. 本文・読み上げLambdaで、キャラクターとボイスの `owner_id` がトークンの本人（またはシステム）と一致するかを確認する。デバイス経由はデバイスのオーナーとキャラクターのオーナーの一致を確認。
- 影響範囲: デバイス設定Lambda（`/voices` `/custom-voices` `/characters` `/devices` `/usage`）、本文・読み上げ・相槌Lambda、アプリ（ログイン画面・トークン付与・初回紐づけ）。ESP32ファームは変更なし。

## ESP32 本文開始の高速化（2026-09-10の検討、[v0.7記録](esp32-v07-aec.md)）
- 19:02の実機画像では `sendToLambdaAndPlay()` 開始から最初の本文テキストまで2,239ms、TTSヘッダー2,282ms、8KB読了2,370ms、I2S書き込み2,502ms。相槌待ち・端末準備・TLS・サーバー処理を含む値で、サーバー時間そのものではない。
- 実装したのは「相槌の再生予定を本文要求の `backchannel_fired` に正しく反映する」修正だけ。
- **保留: 相槌取得待ちと本文要求の並行化。** 現在は相槌取得タスクの終了を待ってから本文の接続・要求を始める。並行化は相槌自体の取得速度や負荷に影響し得るため後回し。着手するなら先に `BC wait done` の経過時間を複数ターンで測り、ほぼゼロなら対象をサーバー側へ移す。相槌タスクの履歴・文字列・PCMの寿命と、遅着した前ターン結果の再生防止が必要。
- **保留: 本文プリバッファ32KBの縮小。** 初回だけ16KBにすると8KB読み込み1回で開始できるが、ユーザー希望で32KBを維持。音切れ再発と比較してから。
- その他の候補: Lambdaの設定取得（voice・LLM）の並行化、最初の文とTTS準備の見直し。AECをCore 0へ移す・毎ターン初期化をやめる案は、移すだけでは改善しない可能性があり初手にしない。

## TTS音声の逐次中継（2026-09-11の調査、コード変更なし）
- 本文Lambda（App / ESP32）はTTSプロバイダーからの音声を `arrayBuffer()` でブロック全体受信してから端末へ送っている。到着分を順次渡せば再生開始を早められる可能性があるが、ESP32のサイズ先行通知、ブロック全体を対象にした無音処理、Appのbase64送信との整合が要る。効果は未計測。
- ログの `tts_first_byte` マークはTTS呼び出し前に記録されており、初回音声到着時刻ではない。初回音声の評価に使わない。
- ElevenLabsの同時実行枠はHTTPでは各要求が数えられ、WebSocketは生成中のみ。分割を細かくすると先頭は早いが合計時間と要求数は増える。着手時は現行方式を計測してから、逐次中継・ブロック長・WebSocketを個別に比較する。

- 9/10朝、PCの計画再起動後にアプリで「XHR error」が出た件。ずんだもんでも出たためPC上のTTS停止だけでは説明できず、根本原因は未確定。同日のPC再起動対策（[Windows更新](windows-update-restart-control.md)）とログオン不要のTTS起動（[起動・復旧](tts-boot-recovery.md)）は実装済み。
- 未実装: `xhr.onerror` は画面のログに固定文言を足すだけで、経過時間・受信済み量・HTTP状態を残さず、履歴再読込で消える。改修するなら、送信前に要求IDを発行し、送信開始・応答開始・初回音声・完了・再生完了・失敗を端末内に永続保存してから送信し、LambdaのRequest IDと照合できるようにする。DynamoDBの会話テキストがあることは音声の生成・受信・再生の成功を意味しない。

## ZakiCorp TTS 待ち行列の可視化（2026-09-13の検討、コード変更なし）
- 本番は同時16件構成で、17件目以降は `batch_engine.py` の待ち行列に入る。待ちが発生しても音声は壊れないが、待ち行列の長さと待ち時間はログにも `/health` にも出ておらず、混み始めたことに気づく手段が無い。
- 案: `/health` に `queue_length`（待ち中の要求数）と `max_wait_ms`（直近の最大待ち時間）を出し、監視タスク（`tools/tts-service/supervisor.py`）が閾値超えを記録する。内側からの `/health` のみ（公開側は `status` だけを返す仕様を維持）。
- 待ちが常態化したら `.env` の `TTS_BATCH_CLASSES` を `1,2,4,8,16,32` に戻す（VRAM約19GB）。48件構成は未実装・未計測で、見込みは [バッチエンジンの文書](qwen3-tts-batch-engine-2026-09-12.md) 第3版。

## Lambda初期化の短縮（2026-09-15の検討、コード変更なし。[複数アカウント計画](multi-account-iac-plan.md)）
- 温め（EventBridge 5分ごと + 実リクエスト中の予備インスタンス温め）が効いていて、実リクエストのコールドスタートは7日で10件未満。初期化約400msはユーザーに届いていないため、短縮は優先度が低い。
- **却下: `openai` パッケージの遅延読み込み。** 温めpingは `openai` を読まないので、温まった後の最初の実リクエストが読み込み代を払うことになり、今より悪化する。
- **却下: `openai` を外して `fetch` 直叩き。** ストリーミングとツール呼び出しの解析を書き直す危険の割に、温まった状態の応答は速くならない。
- **却下: Provisioned Concurrency。** 温めで同じ効果が出ている。月数千円/関数の固定費だけ増える。SnapStartはNode.js非対応。
- arm64とAWS SDKのtree-shaking同梱はCDK化のときに入れる（効果は小さいが手間もゼロ）。
