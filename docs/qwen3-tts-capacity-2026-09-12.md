# Qwen3-TTS / RTX 5090 現行構成の処理能力測定

測定後のコード・ログ分析と優先順位は [分析レポート](qwen3-tts-capacity-analysis-2026-09-12.md) を参照。

## 測定の目的と条件

2026-09-12、ユーザー指示により現状のAPIのまま4→8→16→32件の同時HTTP要求を段階的に投入。遅延が大きくても続行し、受信エラー・タイムアウトは停止条件とした。1・2件の初回測定は比較用に併記する。

測定中はモデルとサーバーを変更・再起動していない。全段階でディスク上のAPIソースハッシュは初回と一致（SHA256 `82799770206ac86b54f2769feed9dbb83fee00989cb69bd1ceb7434b040d2c79`）。1.7B Base / faster-qwen3-tts 0.2.6 / RTX 5090 / localhost / 同一話者 / 同じ41文字の日本語短文。生成にはサンプリングがあるため音声長は毎回異なる。32件試験後はヘルス応答が戻らず、復旧のためAPIプロセスだけを停止し、既存監視で再起動した。

4件以上は各3バースト、ウォームアップ1回、期限120秒、バースト間隔2秒。初期再生バッファ683ms。1件は10回、2件は5バースト。少数標本の探索試験で、長期安定性の認定ではない。

「同時数」はクライアントから同時に送ったHTTP要求数。GPU内部で全要求が同時に計算されていることを示す数値ではない。内部の受付・推論開始時刻は未計測。ヘッダーと音声の到着時刻はクライアントで記録した。

## 集計の読み方

- 成功はHTTP/PCM形式の受信成功。文章・話者の正常性は別評価。
- TTFAは要求開始から最初のPCM受信まで。聞こえる声や実機の再生開始とは異なる。
- 全件完了は各バーストの最初の要求開始から最後の要求終了までの時間。
- 音声生成倍率は、全件の生成音声秒数（末尾追加無音0.5秒を除外）÷バースト実時間。ウォームアップと意図的な休止を除く。
- GPUは約1秒間隔の、バースト中のサンプル平均/最大。別のデスクトップアプリも含み、試験専用GPUの値ではない。
- 音切れ推定は受信時刻と累積PCM量を基にしたバッファ枯渇。保存WAVは待ち時間を詰めた音声なので、WAVを連続再生しても通信中の待ちは再現しない。

16件では音声長が7.54〜21.70秒（中央値8.82秒）となり、1件の7.30〜8.74秒（中央値7.70秒）より長い例が出た。高負荷時の繰り返し等の有無は聴取確認が必要。音声長の伸びがあるため、件数/秒だけでなく音声秒/秒も比較した。後者も正しい内容が生成されたことを保証しない。

### 32件での失敗と測定側の制約

最初のバーストで1件が102.06秒で受信完了し、31件がTimeoutError。残り2バーストは実施していない。クライアントの120秒期限にも不具合があり、終了時刻は約120〜239.57秒にばらついた。HTTPが応答へソケットを移した場合に `conn.sock` だけでは打ち切れない経路があり、接続ソケットを保持して期限時にshutdownする修正、および受信後の期限再確認を追加した。Connection: closeの応答を使った模擬試験で修正を確認済み。

そのため、この32件試験を「厳密に120秒で全接続を打ち切った測定」として扱わない。修正後の32件再測定は行っていない。途中受信された音声は部分WAVであり、正常完了音声と区別する。

投入停止後もGPU処理が続き、10秒のヘルス確認がタイムアウト。監視ログにもhealth unavailableが記録された。監視は引き継いだ既存APIをヘルス失敗だけでは止めないため、実行ファイルと起動引数を照合したPID16796だけを停止し、既存監視で復旧した。API実装・ngrok・AWS設定は変更していない。切断時に不要な生成が速やかに止まるかは、運用上の優先調査項目とする。

## 改善候補と根拠

### 1. 処理時間の内訳を測り、最も時間を使う部分から改善する

要求数を増やしても生成倍率がほぼ一定という結果を受け、次の比較ではモデル入力処理、音声トークン生成、波形への変換、CPUへの転送、HTTP送出にかかった時間を別々に記録する。CUDA処理は非同期なので、単にPython関数の前後だけを測ってGPU時間と呼ばない。計測用の同期を加える場合は通常測定と分ける。

ローカルライブラリにはトークンごとの `.item()`、チャンク区切りの `torch.cuda.synchronize()`、波形の `.cpu().numpy()` がある。これらは調査箇所だが、必要な同期もあるため、削除すれば速くなるとは断定しない。現在はGPU内部の計算装置・帯域の詳細利用率を測っていない。

### 2. 波形変換の回数とチャンクサイズを比較する

現在はchunk_size=4で小刻みに生成・波形変換する。最初のチャンクを小さく保ち、後続をまとめる方法、またはchunk_size=8/12との比較を候補とする。狙いは呼び出し・転送回数の削減。初回音声の遅延や音切れとの交換条件があるため、設定変更後の実測が必要。今回は未変更。

### 3. 1.7Bと0.6Bを品質・速度の両面で比較する

TTSリポジトリには0.6B/1.7Bの既存単独ベンチがある。小さいモデルの処理能力を測り、日本語品質・声の再現性が許容できるなら候補になる。両モデルの話者embeddingを流用できるとは仮定しない。APIのモデル切り替えは今回行っていない。

### 4. 複数要求をまとめて計算する方式は、別構成として比較する

現行APIへHTTP要求を増やすだけでは、まとめて計算する仕組みを追加したことにはならない。要求ごとの状態を分離した推論方式、または複数の独立したモデルインスタンスを候補にできる。ただしVRAMが余っていることだけを理由に高速化を約束しない。GPUの取り合いで変わらない場合もある。導入・実装コストを含め、上記の軽い比較の後に判断する。

直列の順番待ちは正しさ・負荷制御の選択肢であり、総処理能力の向上策として扱わない。生成キャッシュ共有はコード上の論点として残すが、今回ユーザーが確認した初回2件の音声は問題なし。実際の干渉・高負荷時の内容破損は確認できていない。

## 制限

本結果から5090の理論限界、別モデル・別推論エンジンの上限、クラウドでの同型GPU性能、100人の実会話対応を断定しない。音声内容を未確認のまま音声秒数が増える現象を性能向上と解釈しない。長文・複数話者・ngrok・Lambda・端末経由は今回の条件に含まれない。
