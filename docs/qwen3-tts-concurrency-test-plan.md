# Qwen3-TTS 同時要求試験の計測方法と用語の定義

2026-09-12作成、2026-09-13に定義部分だけへ整理。[元実装の測定](qwen3-tts-capacity-2026-09-12.md) と [バッチエンジンの検証](qwen3-tts-batch-engine-2026-09-12.md) の表は、ここで定義した指標で集計している。旧版にあった試験手順・結果表・次の作業は、実施済みの分を上記2本と [調査の経緯](qwen3-tts-current-status.md) に移した。

## 目的と資材の置き場所

ToyTalkerで100人が同時に会話するために、RTX 5090による自前TTSがどこまで対応できるかを測り、Cartesia等の外部APIと比較する。

計画と製品としての判断は `toytalker/docs/`、試験プログラム・入力ケース・生の測定結果はTTS実装の隣に置く（実行手順は [TTS側README](../../tts-models/faster-qwen3-tts/benchmarks/concurrency/README.md)）。音声と生ログはGit対象外。

```text
tts-models/faster-qwen3-tts/benchmarks/concurrency/
├── README.md           # 環境準備・実行コマンド・結果の読み方
├── run.py              # HTTPストリーミング負荷クライアント（--capacity で遅延・枯渇を停止理由にせず記録）
├── cases.json          # 固定の日本語入力と試験条件
├── batch_selftest.py   # バッチ版のHTTPなし自己検証
└── results/<run-id>/   # 設定、要求別計測、GPU計測、集計
```

## 試験環境の3段階

1. **同じPCからlocalhost**: 負荷クライアントはHTTPのみでモデルやCUDAをロードしない。専用のPython仮想環境（標準ライブラリのみ）。既存監視とサーバーを二重起動しない。OS・GPU・ドライバー・Python・PyTorch・ライブラリの版・ソースのハッシュ・生成設定を記録する。
2. **公開経路**: 同じ要求をngrok経由で送り、ネットワーク・トンネルの影響を分ける。
3. **ToyTalker全体**: Lambda経由の会話と端末の実再生。HTTP試験だけでは、STT・LLMの待ち、Lambda中継、ESP32のプリバッファを含む体感速度は保証できない。

APIキーは環境変数から渡し、コマンド引数・MD・結果ファイルに値を記録しない。

## 試験ケース

実ユーザーの会話履歴を使わず、固定の日本語文を使う。全条件で同じケースを使い、長さと本文を結果に紐づける。

| ケース | 目安 | 用途 |
|---|---|---|
| 相槌 | 5〜15文字 | 短い要求が重なる場合 |
| 短文（short） | 30〜60文字 | 通常の先頭応答。既定は41文字の「今日は公園で〜」 |
| 中程度（medium） | 100〜200文字 | 複数文の返答 |
| 長文（long） | 400〜800文字 | 読み上げ・寝かしつけ |

最初は1話者で測り、次に異なる話者を混在させる。同時生成時には音声を保存して聞き比べ、内容欠落・声の混線・破損がないか確認する。

## 計測するもの

| 指標 | 定義・使い道 |
|---|---|
| 初回PCM到着時間（TTFA） | HTTP要求開始から最初の空でない音声データ受信まで。p50/p95/最大 |
| 完了時間 | 要求開始から受信終了まで |
| 受信時刻と累積PCMバイト数 | 初期バッファを仮定して再生中の枯渇をシミュレーション |
| 成功率・失敗内訳 | HTTPエラー、タイムアウト、不正PCM、音声異常を分ける |
| 総音声生成倍率 | 全件の生成音声秒数（末尾追加無音0.5秒を除外）÷バースト実時間。「実時間1秒あたり何秒分の音声を作れたか」で、対応人数ではない |
| 1件あたり実時間比 | 1要求の音声秒数÷その要求の完了時間。1倍を切ると再生が追いつかない |
| RTF | 生成完了までの実時間÷生成音声時間。小さいほど速い。既存ベンチの `RTF` 表示は音声時間÷実時間（速度倍率）なので混同しない |
| GPU | 使用率、VRAM、温度、電力を約1秒間隔で記録。別のデスクトップアプリも含む値 |

注意点:

- 初回PCMが無音の場合もあるため、TTFAは「聞こえる声の開始」と同義ではない。HTTPの受信単位もモデルの生成チャンクと一致しない。
- 音切れはチャンク間隔だけで判断せず、累積受信量と再生速度で評価する。模擬再生の初期バッファは683ms（ESP32のプリバッファ相当）を既定とし、必ず結果に記載する。保存WAVは待ち時間を詰めた音声なので、連続再生しても通信中の待ちは再現しない。
- 24kHz・16bit・モノラルは48,000バイト/秒。末尾の追加無音を含む転送音声時間と、除いた音声時間を分ける。
- p95はnearest-rank。10件では最大値と等しい。小標本のp95は参考値。
- ウォームアップ要求は本計測から除く。再起動直後の試験は別条件として記録する。
- 「同時HTTP要求数」「GPUが実際に並列生成する数」「同時会話人数」は別々に報告する。

## 暫定の評価基準

TTS単体で「初回PCM p95が1秒以内・要求エラーなし・再生シミュレーションで枯渇なし」を仮の目標とする。最終的な合格は実端末の設定・再生ログと、ユーザーが許容する応答時間で決める。有限回のエラー0件は将来のエラー率0を保証しないので、成功数・総数・継続時間を併記する。

100人対応の感度分析には「1人20秒に1回答、約8秒の返答」（約40音声秒/実時間秒）を使えるが、実測された利用パターンとは扱わない。

## 停止・回復条件

- GPUメモリ不足、サーバー異常終了、音声混線・破損が1回でもあれば新規投入を止める。
- クライアント切断でサーバーの生成が止まるとは仮定しない。投入停止後、残存処理・GPU負荷が落ち着くことを確認し、ヘルスと短文生成で回復を確認する。
- 正常に回復しない場合は [起動・復旧手順](tts-boot-recovery.md) に従う。負荷を上げた自動再試行はしない。

## 結果の保存形式

各runに `config.json`、要求別の `requests.jsonl`、受信時刻・累積バイト数、`gpu.csv`、`summary.json`。時刻は実行日と単調時計の経過時間を分ける。モデル・設定・入力ケース・話者ラベルで再現できるようにし、認証情報は保存しない。
