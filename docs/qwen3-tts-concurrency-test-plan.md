ユーザーが初回2件同時の保存音声を聴き、問題なしと報告。現状のまま4→8→16→32件を実測し、その後に改善候補を整理する方針へ変更した。以下の旧計画の「遅延目標超過で増加保留」「キャッシュ確認を先行」は今回の探索試験には適用しない。

- サーバーとモデルは変更せず、既存HTTPクライアントを拡張して測定する。
- 各段階3バースト、ウォームアップ1回、要求期限120秒。遅延・模擬再生枯渇は停止理由にせず記録する `--capacity` を使う。
- HTTPエラー、不正PCM、タイムアウト、明らかな生成異常が出たら、その段階で負荷増加を止めて回復を確認する。
- 最初のバーストは全要求の音声を保存する。保存音声は受信間隔を含まないため、聞き比べによる内容確認と、受信ペースからの再生枯渇推定は別に評価する。
- サーバー内部ログ追加や重いプロファイリングは今回の基準測定に含めない。要求開始・ヘッダー到着・音声チャンク到着・終了、GPU使用率・消費電力を記録する。
- キャッシュ干渉は未確認の改善調査項目として残し、現状測定を妨げる前提条件にはしない。

この計画と製品としての判断は `toytalker/docs/` に置く。試験プログラム、入力ケース、生の測定結果はTTS実装の隣に置き、ここから参照する。

## 現時点で確認した実装

ローカルソースでは、`Qwen/Qwen3-TTS-12Hz-1.7B-Base` を `FasterQwen3TTS` でロードし、保存済み話者embeddingを使用している。`POST /v1/tts/stream` は24kHz・16bit・モノラルPCMを返す。生成の `chunk_size` は4。

単一のモデルを共有し、asyncジェネレーター内で同期的なモデル生成を呼んでいる。API側に明示的なバッチ処理や推論の排他制御は見当たらない。実際に直列化されるか、要求が交互に進むか、共有状態が安全かは、ライブラリ実装の確認と小規模試験で判断する。GPU使用率だけでボトルネックを断定しない。

`bench_warmed.py` と `bench_streaming.py` は存在するが、文を1件ずつ処理するモデル速度試験であり、稼働APIの同時要求試験ではない。別モデルをロードするため、今回の負荷クライアントとして流用実行しない。

APIは1チャンクを保留してから送信し、末尾には0.5秒の無音を追加している。モデル内部の初回生成時間と、HTTPクライアントで測る初回PCM到着時間は区別する。稼働プロセスがこのソースと一致するかは試験開始前に確認する。

## テスト環境

### 第1段階: 同じPCからローカルAPIを測定

```text
負荷クライアント（CPU） → localhostの既存API → RTX 5090
```

- 試験側はHTTPクライアントのみ。モデルやCUDAをロードしない。
- 専用のPython仮想環境を `python -m venv --without-pip .venv` で試験資材配下に作り、サーバーの依存関係を変更しない。追加依存は不要。
- ホスト、ポート、実行中モデル、起動方式を確認する。ソースの既定ポートは8000。
- APIキーは環境変数から渡す。コマンド引数、MD、結果ファイルに値を記録しない。
- 他の会話利用と競合しない時間帯に行う。既存監視とサーバーを二重起動しない。
- OS、CPU、GPU、VRAM、ドライバー、Python、PyTorch、CUDA、ライブラリの版、ソースのハッシュ、生成設定を記録する。
- GPUを使用する別処理の有無と、試験前のVRAM使用量を記録する。

### 第2段階: 公開経路を測定

同じ要求を別PCからngrok経由で送る。ローカル結果と比較し、ネットワーク・トンネルの影響を分ける。クライアントの設置場所と回線条件も記録する。

### 第3段階: ToyTalker全体で確認

Lambdaを経由した会話と端末の実再生で確認する。HTTP試験だけでは、STT・LLMの待ち時間、Lambda中継、ESP32のプリバッファを含む体感速度は保証できない。

## 試験ケース

実ユーザーの会話履歴を使わず、固定の日本語文を用意する。長さと本文を結果に紐づけ、全条件で同じケースを使う。

| ケース | 目安 | 用途 |
|---|---|---|
| 相槌 | 5〜15文字 | 短い要求が重なる場合 |
| 短文 | 30〜60文字 | 通常の先頭応答 |
| 中程度 | 100〜200文字 | 複数文の返答 |
| 長文 | 400〜800文字 | 読み上げ・寝かしつけ |

最初は1話者で測り、次に異なる話者を混在させる。同時生成時には音声を一部保存して聞き比べ、内容欠落、声の混線、破損がないか確認する。音声と生ログは原則Git対象外とする。

## 試験手順

1. `/health`、認証、利用可能な話者を確認する。短文を1回生成し、PCMの形式・音声内容を確認する。
2. ウォームアップ要求を3回実行し、本計測から除く。再起動直後の試験は別条件として記録する。
3. 1件の基準値を測る。各文章ケースを最低10回実行する。
4. 同時要求を **1 → 2 → 4 → 8** と増やす。各段階で同時開始する一群を最低5回実行する。小標本のp95は参考値として扱う。
5. エラー・音声異常・大きな遅延がなく余裕がある場合だけ16、32へ進む。最初から100件を投入しない。
6. 候補となる同時数で継続試験を行う。まず5分、合格候補では15分以上かつ200要求以上を目安に測る。
7. 要求到着率を固定した試験も行う。完了を待って次を送る方式だけでは、処理不足時の待ち行列増加が隠れるため、予定した送信時刻と実送信時刻のずれも記録する。
8. 100人分の会話模擬を行う。各人の本文ブロックを順番に要求し、受け取った音声の再生時間と人が話す間隔を考慮して次ターンを開始する。開始時刻を分散した条件と、集中した条件を分ける。相槌あり／事前生成済みの条件も分ける。
9. 公開経路と実機で候補構成を再確認する。

会話模擬の初期条件には「1人20秒に1回答」を感度分析用に使えるが、実測された利用パターンとは扱わない。短い会話と長い読み上げの両方で確認する。

### 停止・回復条件

- GPUメモリ不足、サーバー異常終了、音声混線・破損が1回でもあれば新規投入を止める。
- 要求タイムアウトは初期値30秒。タイムアウト、またはTTS初回音声p95が3秒を超えた段階では、さらに同時数を増やさず原因を確認する。3秒は試験を止める暫定値であり、製品の合格基準ではない。
- 有効なサンプルが少ない段階では、個々の要求の遅延も確認する。
- 自動停止条件に達しなくても、段階終了時に暫定目標（初回PCM p95 1秒以内）を超えたら、上位の同時数へ進まず原因を評価する。模擬再生の枯渇も自動停止対象とする。音声内容を確認するまでは音声品質の合格を付けない。
- クライアント切断でサーバーの生成が止まるとは仮定しない。投入停止後、残存処理・GPU負荷が落ち着くことを確認し、ヘルスと短文生成で回復を確認する。
- 正常に回復しない場合は起動監視の復旧資料に従う。失敗条件を残し、負荷を上げた自動再試行はしない。

## 計測するもの

| 指標 | 定義・使い道 |
|---|---|
| 初回PCM到着時間（TTFA） | HTTP要求開始から最初の空でない音声データ受信まで。p50/p95/最大を記録 |
| 完了時間 | 要求開始から受信終了まで |
| 受信時刻と累積PCMバイト数 | 初期バッファを仮定して再生中の枯渇をシミュレーション |
| 成功率・失敗内訳 | HTTPエラー、タイムアウト、不正PCM、音声異常を分ける |
| 処理量 | 完了要求/秒、生成音声秒/実時間秒 |
| RTF | 生成完了までの実時間 ÷ 生成音声時間。小さいほど速い |
| GPU | 使用率、VRAM、温度、電力を約1秒間隔で記録 |
| クライアント | CPU負荷、送信遅延、同時接続設定。負荷を十分送れているか確認 |

初回PCMが無音の場合もあるためTTFAは「聞こえる声の開始」と同義ではない。HTTPの受信単位もモデルの生成チャンクと一致するとは限らない。チャンク間隔だけで音切れと判断せず、累積受信量と再生速度で評価する。

現行APIの24kHz・16bit・モノラルは48,000バイト/秒。末尾の追加無音0.5秒を含む転送音声時間と、追加無音を除く音声時間を分け、処理量が過大に見えないようにする。既存ベンチの `RTF` 表示は音声時間÷実時間（速度倍率）なので、本試験のRTFと混同しない。

## 暫定の評価基準と100人への換算

まずTTS単体で「初回PCM p95が1秒以内・試験中の要求エラーなし・再生シミュレーションで枯渇なし」を仮の目標とする。再生シミュレーションの初期バッファ量は必ず結果に記載する。最終的な合格は実端末の設定・再生ログと、ユーザーが許容する応答時間で決める。

有限回のエラー0件は、将来のエラー率0を保証しない。成功数・総数・継続時間を併記する。

「同時HTTP要求数」「GPUが実際に並列生成する数」「同時会話人数」は別々に報告する。100人の会話には全員が常時生成する必要はないが、寝かしつけ等では生成負荷が高くなる。

現在の実装で頭打ちになっても、RTX 5090そのものの限界とは断定しない。待ち行列、同期処理、共有モデルの安全性、バッチ対応、通信のどこが制約かを調べる。改善前後は別の構成として再測定する。

クラウドの同型GPUへ移しても、CPU、電力制限、ライブラリ、ネットワーク等が違うため同じ人数を保証しない。クラウド候補でも再測定する。

各runに `config.json`、要求別の `requests.jsonl`、受信時刻・累積バイト数の記録、`gpu.csv`、`summary.json` を保存する。時刻は実行日と単調時計の経過時間を分ける。モデル・設定・入力ケース・話者の匿名ラベルで再現できるようにし、認証情報を保存しない。
