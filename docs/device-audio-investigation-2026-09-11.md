# 2026-09-11 デバイスの音途切れ報告・初回調査

## 調査対象と結論

中島さんからの「デバイスと会話できたが、会話が途切れ途切れになる。Wi-Fi環境は良い」という報告を受け、CloudWatchと対象候補のDynamoDB登録情報を読み取り調査した。設定変更・デプロイ・ファーム変更は行っていない。

報告に近い時間帯に、デバイス `90:da:72:49:ba:e1` の会話要求7回を確認。TTSは **Sakura / zundamon**、LLMは **Google / gemini-2.5-flash**。ElevenLabsの同時実行制限を今回の原因とする根拠はない。

ただし、このIDが中島さんへ渡した実機と一致するかは確認待ち。実機ファームのバージョンも未確認。

1回の返答には、短い先行音声の後、Web検索などで次の音声送信が遅れる区間がある。他の返答はサーバー側では比較的速く音声を送信しており、この1件だけで報告全体の音途切れを説明できない。端末の受信・再生状況はCloudWatchだけでは確認できていない。

## 音声間の空白候補: 00:17:42の返答

Request ID: `7a68104e-f55d-42df-a706-d03d68bb1220`

| イベント | JST |
|---|---|
| Lambda START | 00:17:42.069 |
| 音声1送信ログ: 58,002 bytes、約1.208秒分 | 00:17:43.252 |
| Web検索開始 | 00:17:43.253 |
| Web検索結果取得 | 00:17:45.192 |
| 音声2送信ログ: 403,164 bytes、約8.399秒分 | 00:17:46.481 |
| Lambda END | 00:17:46.513前後（REPORT所要時間4.444秒） |

先頭音声と次の音声の送信ログ間隔は **3.229秒**。このうち検索要求〜結果取得は **1.939秒**。先頭音声は約1.208秒なので、先頭をすぐに再生する仮定なら、次の音声が出るまで約2.02秒の不足が生じ得る。

これは実測の無音長ではない。相槌、端末の初期バッファ、受信遅延、再生開始時刻で実際の空白は変わる。また3.229秒をすべてTTS待ちと解釈しない。検索・検索後のLLM出力・TTS・送信処理を含む。

検索対象はシアトルの天気だったが、話題から物理的な滞在場所を確定しない。今回取得したログには、所在地を判定できる送信元IP情報は確認できなかった。

## 残る候補と確認方法

| 候補 | 根拠と限界 | 次の確認 |
|---|---|---|
| 短い先行音声の後で検索待ち | 上記1件で送信間隔に不足候補あり | 検索なしの返答でも同じ症状か比較 |
| 文ごとの意図的な間 | ローカルv0.5/v0.6/v0.7には`TTS_SEGMENT_GAP_MS = 400`がある | 実機の版を確認し、文間の間なのか単語途中の音切れなのかを区別。v0.4へ同じ設定を当てはめない |
| 端末受信・再生バッファの枯渇 | サーバーが早く送れている返答でも、ネットワークや端末処理による遅れは残り得る | `[PLAYER] underrun`、`[STATS] underruns`、受信・I2Sログ。Wi-Fi電波が良いだけでは通信経路全体の安定性は分からない |
| 音声認識や発話区切りの問題 | 「会話が途切れる」が返答音声だけを指すか未確定 | 入力認識の途切れと出力再生の途切れを区別 |
| 実機ファーム固有の問題 | 実機の版が不明 | 配布時の版・設定を確認。手元のv0.7のAEC等を原因と決めつけない |

端末の再生ログは現在確認したCloudWatchデータには含まれない。シリアルログ取得が難しい場合は、まず短い録画で「文と文の間」「単語の途中」「返答までの待ち」のどれかを切り分ける。その後、必要なら遠隔診断データの送信を別の実装として検討する。

## 次に進む順序

1. 対象IDが中島さんの端末と一致するか、配布ファームの版を確認する。
2. 検索なし・短い返答で症状が出るかを確認する。
3. 端末の受信・バッファ枯渇・再生時刻と、CloudWatchのRequest ID/時刻を対応づける。
4. 原因の所在を絞ってから、文間の間、検索時の応答設計、バッファや送信方式の変更を検討する。

## DynamoDB会話履歴との照合（同日追記）

ユーザーから追加依頼を受け、現在の`owner_id`と対象デバイスIDの組み合わせをパーティションキーとして`toytalker-chat-logs`をQueryした。期間はUTC 2026-09-10 14:00〜16:00（JST 23:00〜翌01:00）。14レコードを評価し、14レコードが該当した。すべて`source=esp`、セッション`1280-470114`の7往復。現在の所有者との組み合わせについての結果であり、過去の別所有者に紐づく履歴まで調べたものではない。

「枕に入れるデバイス」「音が途切れるね」が対象デバイスの本文履歴にもあるため、相槌ログの時刻相関だけだった初回調査より、報告との対応が強まった。氏名による本人確認には至っていない。

00:23:00の入力に対する返答は「枕に入れるデバイスですね！面白そう！それは何をするものなのですか？」。00:23:19の入力に対しては「ごめんなさい、音が途切れてしまいましたか。もう一度お話しいただけますか？」と返答している。後者はユーザー入力に応じたLLMの発言で、システムが音切れを検出した診断ログではない。

### 保存テキストの重複と実際の音声送信の違い

天気の返答はDynamoDB上で「調べてみるね。調べてみるね。」と先頭が重複している。しかし、CloudWatchの音声送信ログは次の2ブロックのみ。

1. 「調べてみるね。」
2. 天気の回答本文

ローカル実装の`emitSegment`には直前の同一文を再送しない処理があり、このログと整合する。**履歴の重複は確認できるが、同じ音声を2回再生した証拠ではない。** テキストの保存経路と音声化経路の差を、別の課題として扱う。

### 設定・利用集計

- 現在のデバイス設定は`character_id=default`。当時のCloudWatchには`hasPersonality=false`があり、独自の人格設定を読み込んだ形跡はない。一般的なシステムプロンプトがないという意味ではない。
- 取得したデバイスレコードには`backchannel_enabled`属性がない。ローカルのキー発行実装では未指定時は有効扱い。実際に同時間帯の相槌生成も観測されている。
- `owner_id`はアプリが生成・保持する`u_`付きUUID。確認したアプリ実装では氏名から生成するIDではなく、取得レコードにも氏名・所在地はない。この値だけで本人や滞在地を特定できない。
- 対象端末の9月利用集計にはUTC日付9/10のLLM/STT/TTSレコードが各1件あり、各`requests=7`。本文TTS文字数は208文字。これは利用集計の加算回数であり、TTSの実HTTPリクエスト数7件という意味ではない。CloudWatchの本文音声ブロックは合計14件。
- 記録上の合計金額は約0.8296円（LLM約0.6640円、STT約0.0720円、TTS約0.0936円）。内部設定のマージン1.5等を含む計算値であり、プロバイダー請求額・AWS費用・相槌も含めた総原価としては使わない。今回、料金設定の妥当性は検証していない。

登録時刻9/6は既存レコードの作成時刻。9/11の登録処理では所有者が更新され得るため、9/6から同じ人が使用していたとは断定しない。

参照: [所有者ID生成](../app/hooks/useOwnerId.ts)、[会話履歴保存・利用集計](../backend/toytalk-api-stream-for-esp32-lambda/index.mjs)
