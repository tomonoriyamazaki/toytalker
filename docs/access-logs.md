# アクセスログと送信元 IP の扱い

決定・根拠・設計・手順をここに持つ。状態が変わったら上書きする。残作業は [ロードマップ](roadmap.md) 29。

## 状態（2026-11-09）

- **方針を変えた**: 2026-10-28 の「送信元 IP はどこにも書かない」をやめ、**CloudFront のアクセスログとしてだけ、180 日残す**ことにした。Lambda ログ・`chat-logs`・会話の記録には今までどおり IP を入れない。

## なぜ取るか（2026-11-09 の相談で決めた）

- 不正アクセス禁止法の被害届、ISP への開示請求、遮断のどれも、**IP と時刻の組が無いと始まらない**。国コードだけでは何もできない。
- 前払いポイントを Stripe で売る（ロードマップ 4）と、**チャージバック（異議申立）への反証**が要る。Stripe の証拠項目にはデジタル商品向けに `customer_purchase_ip` と `access_activity_log`（購入後にサービスを使った記録）があり、IP 付きのアクセスログがそのまま証拠になる。
- WAF のレート制限はすでに IP で判定している。「処理」はしていて「保存」だけしていない状態だったので、保存を短期・分離に限るのは方針の転換というより一段階の調整。
- 守る対象が子どもの会話なので、入られたときに「誰か追えない」方が保護者への説明責任として重い。
- 反対側: 利用者 10 人弱の今、必要になる確率は低い。10-28 の決定も「集めなければ漏れない」として筋は通っていた。180 日・自分だけが読める別置きのバケット・会話ログとは別、という形にすれば漏れたときの被害もその範囲に限られ、「必要なときに無い」損失との非対称で取る側に倒した。

## 法的な整理（弁護士の確認は、売り始める前に特商法の表記と一緒に）

- **EU（GDPR）**: IP は動的なものも個人データ（Breyer 判決 2016、前文 30）。取れないのではなく、**6 条 1 項 (f) の正当な利益**で取る。前文 47 が「不正防止に厳密に必要な処理は正当な利益」、前文 49 が「ネットワークと情報の安全確保は正当な利益」と明記。17 条 3 項 (e) で、法的請求（チャージバックの争いを含む）の立証・防御に必要なデータは消去権の対象外。
- **日本（個人情報保護法）**: IP 単体は個人情報に当たらないのが個人情報保護委員会の整理。ただしこのシステムでは Lambda ログの `owner_id` と突き合わせれば本人に届くので、**個人情報として扱う前提で設計する**（GDPR 基準で作れば日本側は満たす）。保存を義務づける法律は無い。総務省の電気通信事業者向けガイドライン（接続認証ログ 6 か月程度まで許容）は ToyTalker の対象外だが、期間の参考として挙げられる。
- **180 日の根拠**: カードネットワークの異議申立期限が取引から 120 日前後 + Stripe の証拠提出期限 + 発覚の遅れ（月次レポートや請求書で気づく運用だと 1〜2 か月）。90 日だと争いになった時点で消えていることがある。1 年以上は子ども向けサービスで「必要最小限」と説明しにくい。短くするのはライフサイクルの日数を変えるだけなので、180 日で始めて足りなければ理由を付けて延ばす。
- **相場**: 運用ログ 30〜90 日、不正対応 90 日〜1 年、決済がらみ・規制業種 1 年、広告・分析 9〜18 か月。180 日は小規模サービスの既定より長く規制業種より短い真ん中。EU の子どもの利用者が増えたら 90 日へ縮める判断もありえる。

### 正当な利益の評価（GDPR が求める記録。書き直したら日付を更新する）

- **目的**: 不正アクセス・費用燃やし・なりすましの検知と調査、遮断（WAF の対象 IP の指定）、警察・ISP への届け出、Stripe の異議申立への反証。
- **必要性**: 国コード・リクエスト ID・Lambda ログだけでは送信元を特定も遮断もできない。IP 以外の手段（認証済みアカウント）は、認証を通らない要求と、盗まれたアカウントからの要求には効かない。項目は IP・時刻・経路・結果に絞り、本文・クエリ文字列・User-Agent・Referer は残さない。
- **均衡**: 利用者が受ける不利益は、180 日以内の IP とアクセス時刻を運営者 1 人が読める状態に置かれること。会話の記録とは別の場所に置き、自動で結合した表は作らず、分析・マーケティングには使わない。プライバシーポリシーに目的と期間を書く。利用者の開示請求には 180 日以内の分を出せる。

## 設計

### 何を、どこに

- **CloudFront 標準ログ v2**（`AWS::Logs::DeliverySource` / `DeliveryDestination` / `Delivery`。項目を選べる）で、API の配信（`api-<環境>.zakicorp.com`）の要求を **専用の S3 バケット**へ出す。旧来の `enableLogging: true` は項目が固定で、クエリ文字列（`device_id` `owner_id` `session_id` が乗る）と User-Agent が入るので使わない。
- **項目は最小**（名前は AWS の v2 の一覧で確認済み、2026-11-09）: `date` `time` `c-ip` `cs-method` `cs-uri-stem` `sc-status` `x-edge-request-id` `x-edge-result-type` `c-country` `time-taken` `sc-bytes` `cs-bytes`。**入れない**: `cs-uri-query`、`cs(User-Agent)`、`cs(Referer)`、`cs(Cookie)`（Cookie は配信側の設定でも切ったまま）、`x-forwarded-for`、`ssl-*`、`asn`。
- 既知の例外: 設定 API の一部はパスに `device_id` を含む（`/devices/{id}`）。機器の識別子であって人ではなく、頻度も低いので受け入れる。
- **バケット**: `toytalker-access-logs`（RnD。本番は `-prd` 等、[命名規則](naming-conventions.md)）。公開ブロック、SSE-S3（本番は 7(a) の CMK と一緒に見直す）、**バージョニング無し、バックアップ（10）の対象外**（消したら消えるのが目的）、**ライフサイクル 180 日で削除**。書けるのは `delivery.logs.amazonaws.com` だけ、読めるのは管理者（自分）だけ。**Lambda ロールには権限を付けない**。
- **サイト（`toytalker.zakicorp.com`、購入ページを含む）の配信は対象外**。静的ページの閲覧 IP は要らない。購入の操作は `/billing*` API を通るので API 側のログに残る。
- **WAF**（本番だけ）のサンプル保存と WAF ログは切ったまま。アクセスログと重複する。
- **Lambda ログ**は変えない。IP は入れない。保持（今は無期限）はロードマップ 8(e) で別に決める。

### 個人と結びつけにくくする

- IP が載るのはアクセスログだけ。`owner_id` `device_id` `session_id` が載るのは Lambda ログと `chat-logs` だけ。**両方に載る共通の鍵は CloudFront のリクエスト ID 1 つ**。
- CloudFront はオリジンへ `X-Amz-Cf-Id` ヘッダーを渡し、値はアクセスログの `x-edge-request-id` と同じ。Lambda の trace（`backend/shared/trace.mjs` の `describeEdge`）に `cf_id` として足す。これで「IP → cf_id → Lambda ログの owner_id」は**両方を読める管理者が手で結合したときだけ**辿れる。
- **自動で結合した表は作らない**。Athena のテーブルも作らない（表にすると結合が一手になり、費用も要る）。調査はその都度、該当日のログを手元へ落として grep し、終わったら手元のファイルを消す。
- 用途外（分析・マーケティング・利用者ごとの IP 一覧）に使った瞬間に正当な利益の理屈が崩れる。使わない。

### Function URL を直接呼ぶ経路（`edge: "direct"`）

- CloudFront を通らないので、この設計では IP が残らない。暫定で Lambda ログに `sourceIp` を書く案は**却下**（会話の識別子と同じ場所に IP を置くことになり、「分ける」設計が崩れる）。
- ロードマップ 3 のとおり、配布機を 0.7.4 以降に書き換えた後 `directFunctionUrls: false` で IAM 認証にして経路自体を閉じる。それまでの直叩きは追えないことを受け入れる。

### Stripe（購入）との関係

- カード入力は Stripe Checkout（Stripe のページ）で行うので、**決済時の IP は Stripe 側が持つ**。こちらで持つのは、購入を始めた要求（`/billing*` でのセッション作成）の IP と、購入後にサービスを使った記録。
- 異議申立では、Stripe が持つ決済時の IP と、こちらのアクセスログ（セッション作成の要求、以後の利用）を `cf_id` → billing の trace（`owner_id`・Checkout セッション）で結び、「本人の環境から購入し、以後も使っている」ことを示す。
- Webhook（Stripe → `/billing/webhook`）の要求も同じログに載る。送信元は Stripe の IP で、利用者ではない。

### CDK の置き方

- CloudFront 向けの delivery 資源（`DeliverySource` / `DeliveryDestination` / `Delivery`）は **us-east-1 に作る**（AWS の文書で確認済み: CloudWatch API は us-east-1 で呼ぶ。バケットは別リージョンでもよい）。edge スタック（us-east-1。証明書・WAF）は本体スタックから参照される向きなので、そこに配信の ARN を渡すと循環になる。**小さな第 4 スタック `ToyTalker-<環境>-logs`（us-east-1）**を本体の後に作り、配信の ARN を `crossRegionReferences` で受ける。バケットは東京の本体スタックでも us-east-1 の logs スタックでもよい。logs スタックに置くと「IP を含む資源は 1 スタック」で見通しがよい。
- `outputFormat` は `json`（作った後は変えられない。変えるなら delivery を作り直す）。出力先（S3 / CloudWatch Logs / Firehose）のうち S3 だけ使う。設定の反映は最大 12 時間。配信 1 つにつき delivery source は 1 つ。
- deploy は `--all` か、`ToyTalker-rnd` と `ToyTalker-rnd-logs` を名指し。[infra/README](../infra/README.md) の手順に足す。
- cdk-nag: CFR3（アクセスログ）の受け入れを外し、代わりにログ用バケットへの S1（バケット自身のサーバーアクセスログ）を「ログのログは取らない」で受け入れる。
- **費用（AWS の文書で確認済み、2026-11-09）**: CloudFront はログの有効化に課金しない。S3 への配送も追加料金なし（CloudWatch Logs や Firehose へ出すと vended logs の料金、Parquet 変換も CloudWatch の料金。どちらも使わない）。掛かるのは S3 の保管と取り出しだけで、月の要求数が数万件なら MB 単位、実質ゼロ。**WAF は不要**（WAF はレート制限のための別サービスで、ログとは無関係。RnD は WAF 無しのままでよい）。配信は CDK が作った従量制（pay-as-you-go）で、CloudFront の定額プラン（Free プランはログ不可）ではない。

### ログの量と費用、WAF との関係（2026-11-09 の相談）

- 費用はログの量に比例するが桁が小さい。項目を絞った 1 行を約 250 バイト、gzip で 1/5、東京の S3 標準 $0.025/GB・月、180 日分の保持で: 月数万件（今）→ 数 MB・1 円未満、月 100 万件 → 約 300MB・約 1 円、月 1 億件（攻撃を受けた月）→ 約 30GB・約 100 円。攻撃のときの本当の出費は CloudFront の要求料金（1 億件で約 $120）と Lambda・外部 API で、ログはその誤差。
- **WAF（本番だけ。同じ IP から 5 分 300 件で 403）が止めるのは「1 つの送信元からの大量要求」**。止めた要求は Lambda に届かないので、高い部分（LLM・TTS・STT）の費用は出ない。多数の IP から少しずつ来る攻撃と、正規のアカウント・機器を乗っ取られた場合には効かない。WAF は「遅くする」道具で、金額の天井ではない。
- **費用の天井を作るのは 4 の認証とポイント残高**（匿名の要求は LLM が走る前に 401、盗まれたアカウントも残高まで）と、ESP32 のデバイス鍵（0.7.6。配布機の書き換え後に初回登録を閉じる）、外部 API 側の使用量アラート。Lambda の同時実行上限は **2026-10-27 に却下済み**（正規利用者を断る副作用。[先送り項目](deferred-items.md)）で、本番で WAF と合わせて見直すならそのとき。
- このログの役目は、多数の IP からの攻撃が来たときに **WAF に何を入れるかを決める材料**になること。ログ無しでは遮断の範囲も決められず、届け出もできない。

### 調査のしかた（必要になったとき）

1. 該当日のプレフィックスだけ `aws s3 sync` で手元の一時フォルダへ落とす（管理者の SSO で）。
2. `x-edge-request-id`（Lambda ログの `cf_id`）か IP で grep。警察・ISP・Stripe へ出すのは、IP・時刻（UTC と JST を併記）・パス・結果コードの行。
3. 終わったら手元のファイルを消す。調査したこと（日付・目的・何を見たか）をこの文書の末尾ではなく、セキュリティ見直しの該当項目に 1 行残す。

## 確かめること（実装の前）

- `X-Amz-Cf-Id` が Function URL の `event.headers["x-amz-cf-id"]` で読めること（OAC 経由でも落ちないこと）。オリジンへ渡すヘッダーは allowList だが、`X-Amz-Cf-Id` は CloudFront が常に付けるヘッダーなので allowList の対象外のはず。RnD で deploy 後、Lambda ログに `cf_id` が出ることで確認する。
- ログが出始めるまでの遅れ（設定の反映は最大 12 時間と文書にある。出始めてからは数分〜1 時間）と、1 要求がログに 1 行で出ること（ストリーミング応答も含めて）。
- バケットポリシーは「有効化すると AWS が自動で足す」と文書にあるが、CDK で作るときは自分で書く（`delivery.logs.amazonaws.com` の `s3:PutObject`、`aws:SourceAccount` と `aws:SourceArn` の条件付き）。

確認済み（2026-11-09、AWS の「Configure standard logging (v2)」）: 項目名の一覧、us-east-1 の制約、バケットは別リージョン可、S3 配送は追加料金なし、`outputFormat` は json / plain / w3c / raw / parquet。
