# ESP32 v0.5 再生終了の計測

対象は `devices/mcu/esp32_s3/toytalker_mini_v0.5/toytalker_mini_v0.5.ino`。
TTSセグメント間の400msは維持する。これは高速化パッチではなく、終了待ちの内訳を調べる診断。

## 実機結果と当面の方針（2026-09-07）

ユーザー提供のArduino IDEシリアルモニター画像（2026-09-07 00:00:39）で、FishAudioの2セグメントの応答を確認した。セグメント間隔は400ms、割り込みなし、Soniox事前接続済み。ボイスIDは画像からは確認できない。

```text
[TURN_END] turn=1 interrupted=0 recv_end_ms=12954 last_i2s_copy_ms=15462 stop_return_ms=15474 flush_end_ms=15804 flush_ok=1 flush_write_ms=328 flush_ws_ms=1
[TURN_END] turn=1 amp_off_ms=15804 mic_setup_done_ms=15806 record_on_ms=15806 ws_ready=1 first_read_ms=15837 first_send_ms=15839 amp_to_mic_ms=2 amp_to_send_ms=35
[DMA_TAIL] turn=1 valid=1 confirmed=1 block_bytes=4092 tail_padding_us=2708 confirmed_us=15803820 after_confirm_us=384
```

| 項目 | 今回の値 | 解釈 |
|---|---|---|
| flush内の書き込み待ち | 328ms | 全量を削減可能な待ち時間とは見なさない |
| 最後のDMAバッファ末尾の追加無音 | 約2.7ms | 計算値。TTS音声自体の末尾無音は含めない |
| DMA完了確認からアンプOFF | 約0.38ms | 確認後の後処理は短い |
| アンプOFFからマイク設定終了・録音モード設定 | 2ms | ソフトウェア上の切り替えは短い |
| アンプOFFから最初の送信成功 | 35ms | 512サンプルを16kHzで収集する約32msも含む。35ms全体が録音できない時間ではない |

この1例では、DMA完了を確認した後の大きな余分な待ちは見えていない。約328msのflushは残っている音声のDMA転送待ちが大部分を占めると考えられるが、完了確認までのタスク起床遅延は分離できない。正確な発声終了時刻や、すべてのボイス・通信条件での挙動を保証する結果ではない。

当面は終了処理の短縮を行わず、既存の他の計測と合わせて、今回の計測コード・ログ出力も現在のまま有効で残す（無効化フラグの追加は行わない）。ボイス変更時にはプロバイダー・ボイスID・返答の長さを記録し、短い返答と長い返答で同じログを比較する。TTS音声に含まれる末尾無音はこの計測では判別できないため、聴感も合わせて確認する。

## 実機確認

短い返答と長い返答で、録音再開後の `[TURN_END]` 2行と `[DMA_TAIL]` 1行を取得する。
出力は毎ターン最初の空でない録音パケットの送信成功後にまとめ、切り替え前のログ負荷を抑える。
起動直後やLambda接続失敗で再生に入らなかった場合はこのログを出さない。

`[TURN_END]` はコピー完了・受信終了・終了待ちからの復帰・無音のflush・アンプOFF・マイク設定終了・録音モード設定・最初の読み取り・最初の送信を記録する。
`mic_setup_done_ms` はマイク設定関数が戻った時刻であり、マイク素子の実測準備完了を保証しない。
`first_read_ms` は読み取りが戻った時刻で、最初のサンプルの取得開始時刻ではない。

## DMA_TAILの意味

| フィールド | 意味 |
|---|---|
| `valid` | 計測条件を満たす。0なら結果を終了時刻として解釈しない |
| `confirmed` | 最後の音声を含むDMAバッファを再取得する位置まで無音を書けた |
| `block_bytes` | TX_DONEイベントから確認した実際のDMAバッファ長。現行設定は通常4092 bytes |
| `tail_padding_us` | 最後の音声データから、そのDMAバッファ末尾までの無音長の計算値 |
| `confirmed_us` | 最後のDMAバッファの送信完了を確認できた時刻（起動からのマイクロ秒） |
| `after_confirm_us` | 上記時刻からアンプOFFまでの実測時間。無効時は-1 |

`valid=1 confirmed=1`の結果を使う。送信イベントキューの満杯、監視中の空きバッファスキップ、DMAエラー、書き込み失敗などでは無効にする。

**これはDMA割り込み時刻そのものでも、スピーカーの発声終了の実測時刻でもない。**
`confirmed_us`にはタスク起床・コピー等の遅延が含まれる。DMAからI2S FIFOへ渡った後の送出、アンプの遅延、音声PCM自体に含まれる末尾の無音は別問題。
`tail_padding_us`も計算値であり、`confirmed_us - tail_padding_us`を正確な発声終了時刻として扱わない。
現行4092-byteバッファは24kHz stereo 16-bitで約42.6ms分。バッファ単位の確認であることに注意する。

`after_confirm_us`が大きければ、送信済みと確認できた後の後処理に短縮候補がある。
これが小さくても、タスク起床前の待ちや音声データ末尾の無音がゼロと証明したことにはならない。
この計測だけで「約320msをすべて削れる」と判断しない。

## 方法と根拠

legacy I2Sの公開TX_DONEイベントは種類とサイズを持つが、バッファ識別子とIRQ時刻を持たない。
単に最後に受け取ったイベントを最後の音声の完了と見なすことはできない。

そこで、相槌・セグメント間無音・本音声を含む全I2Sコピー量をカウントする。
書き込み元が停止した後、実際のバッファ長Bと最後のバッファ内の使用量u（1〜B）を求める。
既存のflushのうち `N * B - u` bytesを書いて残りのバッファを埋め、さらに1 stereoフレーム（4 bytes）を書く。
空きバッファのスキップがない場合、この追加フレームは最後の音声を含んでいたバッファの再取得を要求する。
ドライバはDMA完了でキューに戻ったバッファだけを取得するので、呼び出しが戻った時点でそのバッファのDMA転送完了を確認できる。

- Nは既存設定と同じ8。
- 元の32768-byte flush内の呼び出しを確認境界で分割する。総無音量と8192 bytesごとの `ws.loop()` の位置は維持する。
- 実際のBは送信完了イベントから取得し、4096と決め打ちしない。
- 追加のイベントキューは32件（ドライバ所有）。I2Sドライバのuninstallで解放される。
- 出力の先頭や末尾を切ったり、DMA深さを減らしたりする変更は含まない。

確認した実装: [ESP-IDF v5.5.4 i2s_legacy.c](https://github.com/espressif/esp-idf/blob/v5.5.4/components/driver/deprecated/i2s_legacy.c) の `i2s_write`、`i2s_dma_tx_callback`、`i2s_get_buf_size`。
ドライバのバッファ取得方式が変わった場合、この診断の前提も再確認すること。

## 検証範囲

- Arduino ESP32コア3.3.10でファーム全体のビルド成功。Flash 1396311 bytes、静的RAM 50136 bytes。

- 上記モデルはDMA割り込みやFreeRTOSの実機試験の代わりではない。DMA_TAILの実機結果は上記の1例を取得済み。複数ボイス・長短の返答での比較は未実施。
