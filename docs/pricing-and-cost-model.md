# 原価と課金の考え方（2026-09-13 時点の方針）

従量課金で「使った分だけ、安く、気軽に」を実現するための、原価の見方と料金の組み立て。月次運用レポートLambda（第10節）の前提になる。2026-09-10の市場調査（旧 cost-estimate.md）と2026-09-12のツールコスト記録（旧 search-cost-tracking.md）は末尾に統合した。

## 1. 原価の記録と請求額の関係

```
請求額（円） = API単価（USD） × 使用量 × その月の為替 × マージン
```

- **API単価**: `toytalker-api-unit-prices` にドル建てで保存（Sakuraのみ円建て）。プロバイダー×種別ごと（`google#llm` など）。自動更新はしない。
- **為替**: `toytalker-exchange-rates` に月ごとの行。毎月1日に運用Lambdaが ECB（欧州中央銀行）の公表レートを保存し、その月は固定。行が無い月は150円で計算される。
- **マージン**: `service#margin` の1行。現在 **2.0**。これが従量課金の「売価」そのもの。
- 記録される種別は `stt / llm / tts / tool` の4つ。相槌のLLM・TTSと、AWS・為替・カード手数料は記録しない（マージンで吸収）。

## 2. 1時間の会話の原価（マージン前）

前提: 40ターン、AI発話30分、子供の発話15分、LLMはGemini 2.5 Flash（1ターン入力2,500トークン・出力80トークン）、為替152円。

| 項目 | Sakura（ずんだもん） | Cartesia（リアル系） |
|---|---|---|
| TTS | 3.6円（12,000モーラ） | 約160円（1万字超、$0.00005/字） |
| LLM | 5.8円 | 5.8円 |
| STT（Soniox） | 3.3円 | 3.3円 |
| ツール（検索2回） | 0.3円 | 0.3円 |
| **記録される原価** | **約13円** | **約170〜180円** |
| 相槌（Gemini Flash 40回＋TTS） | 1.6円 | 約2円 |
| AWS（Lambda実行が中心、転送・ログ・DynamoDB） | 3.3円 | 約4円 |
| カード海外手数料（約2%） | 0.3円 | 約4円 |
| **本当の原価** | **約18円** | **約190〜200円** |

- DynamoDBは1時間で0.1円未満。ログを何年ためても問題にならない。
- 記録外の原価は「ターン数に比例」なので、TTSが安いSakuraでは記録原価の約40%、Cartesiaでは約3%にあたる。

| Sakura | 約26円 | 約18円 | 約1円 | 約27% |

## 4. 為替と手数料の扱い

- **為替は月初にECB値で固定**。市場レート（Googleの表示など）とは1〜2%ずれることがあるが、月単位の記録としては誤差の範囲。実勢に寄せたければ運用Lambdaを毎日更新に変えられる。
- **各社からの請求**はドル建て都度課金（OpenAI・Anthropic・Soniox・FishAudio）、前払いクレジット（Cartesia月額。Serperは2026-10-28まで無料クレジットのみ）、円建て（Sakura、Googleは請求アカウント次第）が混在する。カードで払う分には海外事務手数料（1.6〜2.2%）が乗る。
- 実支払いと記録額を一致させようとせず、**ずれはマージンで吸収し、月次レポートで確認する**。
- ユーザーから受け取る側の決済手数料（Stripe約3.6%、App Store 15〜30%）は別物で、売上から引かれる。

## 5. 従量課金の形

- **前払いポイント制**を採る。例: 500円分を購入し、会話のたびに請求額ぶんを減らす。未払いリスクが無く、少額決済の繰り返しを避けられ、ユーザーにも上限が見える。
- いまの記録（利用者・日・種別ごとの円額）がそのままポイント減算の元データになる。
- iOSアプリ内でポイントを売るとApp Store手数料がかかるため、Web購入の経路を検討する。規約・法規制は実装前に確認。
- アプリの声の選択画面に「この声は1回約9円」「ずんだもんは1回約0.7円」のように単価を出し、従量の納得感を作る。

## 6. ポケとも（シャープ）との比較

| | 1回あたり | 400回ぶん |
|---|---|---|
| ポケとも（ノーマル495円/400回、他プランも同単価、無制限3,300円） | 約1.24円 | 495円 |
| ToyTalker Sakura | 約0.65円 | 約260円 |
| ToyTalker Cartesia | 約9円 | 約3,600円 |

Sakuraならほぼ半額で、使わない月は0円。ポケともの1回1.24円は市場が受け入れている水準なので、マージンを上げる余地はある。

## 7. プレミアムボイス（声優の声など）の料金体系

- **使い放題の定額はしない**。声優クローン級の単価（1ターン原価約4.5円）だと、月730ターンで原価割れになる。子供が気に入って使い込むほど赤字になる構造は避ける。
- 採る形は「**月額固定（解放料）＋従量（今までどおり）**」。
  - 月額は声優へのライセンス料をまかなう。ライセンスが売上分配型なら月額は低めでも成立する。
  - 会話はその声の原価×2.0をポイントから消費（1回約9円）。使われ方に関係なく変動費は従量が必ずカバーする。
  - 二重取りに見えないよう、月額にポイントを少し含める（例: 月額500円に300円分のポイント込み）。
- 声優のライセンス条件（用途・期間・停止時の扱い・分配率）は料金設計より先に固める。AIによる声の合成は業界的に敏感なので契約を明確にする。
- 実装: `toytalker-voices` にプラン印を付け、アプリの出し分けに加えて**Lambda側でも加入者かを確認**してから合成する。コスト記録は声ごとの単価で計算しているので変更なし。

## 8. 今後の課題

- **単価はモデル単位の行を優先する**（2026-10-27実装）: 本文Lambdaは `${provider}#llm#${model_id}`（例 `anthropic#llm#claude-haiku-5-5`）→ `${provider}#llm` の順で探す。プロバイダー行は従来どおり残し、同じ会社で2つ目以降のモデルはモデル付きの行を足す。Gemini 3.5 Flash Lite は 2.5 Flash と同単価なので `google#llm` に落ちる。
- **単価行の属性**: 2026-09-13に全行へ `provider` / `api_type` を属性として追加した（キーを `#` で分けた値）。コンソールでの絞り込みと集計コードの簡略化のためで、計算はこれまでどおりキーで引く。新しい行を足すときもこの2つ（モデル付きなら `model` も）を入れる。
- **Sonioxの見積もり**: 文字数から逆算しているが、実際は音声を流した時間で課金されている可能性がある。ESP32は聞いている間ずっと送るので、月次レポートの手動確認で最初に見る。
- **LLM入力トークン**: 会話履歴を長く持つほど膨らむ。履歴の上限を決めておくと原価が安定する。
- **相槌の定型音声化**: 原価よりレイテンシ改善の効果が大きい。別件として検討。
- **AWS Lambda**: 本文Lambdaは2GBでLLM・TTSの応答待ち中も課金される。記録外の原価では最大の項目。

## 9. 有料ツール（外部API）のコスト記録（2026-09-12）

- LLMのfunction callingで呼ぶツールのうち、外部に料金が発生するもの（現状はBrave検索）だけを `tool` 種別で回数課金として記録する。自前のLambda/DynamoDBを呼ぶだけの無料ツールは何も記録しない。検索は「調べ物をよくする子」と「雑談だけの子」で回数が大きく違うため、一律マージンではなく回数で数える。
- 単価は `toytalker-api-unit-prices` の `${provider}#tool` 行、`input_unit_type = "requests"`。`brave#tool` = $0.005/回（定価。毎月$5分=1,000回の無料枠は月次で差し引く）。1回検索のターンでツール代は約0.75円（マージン前）。2026-10-27に Serper（$0.001/回だが$50前払いが6か月で失効し、月27回の利用では1回約$0.31相当だった。API検索クエリの保持ポリシーの記載なし）から切替。`serper#tool` の単価行は履歴の参照用に残す。
- 有料ツールを増やすとき: `backend/shared/llm.mjs` の `PAID_TOOLS` に `ツール名: { provider, model }` を1行足し、単価行を足す。アプリ側は円グラフの色を付けたい場合だけ `CHART_COLORS` に追加。無料ツールを増やすときは何もしない。
- 残骸: 最初は `search` 種別で実装し同日 `tool` へ汎用化した。`2026-09-12#<device>#search` の利用状況行と `serper#search` の単価行が1件ずつ残っている。参照されないので消してよい。

## 10. 月次運用レポートLambda（為替更新・請求突き合わせ・単価点検）

2026-09-12に `toytalker-ops-monthly-lambda` を追加。毎月1日 09:00 JST に動き、結果を1通のメールで送る。値の自動修正はしない。

### やること

1. **為替**: Frankfurter（ECB公表レート、キー不要）からUSD→JPYを取り、`toytalker-exchange-rates` に当月の行が無ければ作る。既存行は維持（`FX_OVERWRITE=true` で上書き）。
2. **先月の記録集計**: `toytalker-usage` を先月分でスキャンし、プロバイダー×種別ごとにマージン後の円額・マージン前のUSD実費・使用量をまとめる。
3. **各社の実績との突き合わせ**: APIで請求を取れる社（OpenAI・Anthropic）は差分と割合を出し、20%超なら要確認印。ElevenLabsは使用文字数。取れない社（Cartesia・Serper・Google・Soniox・Sakura・Fish Audio）は記録実費と確認先URLを並べる。
4. **点検**: 単価行が無くて記録されなかった呼び出し（記録側Lambdaの `[Pricing] missing price` ログを CloudWatch Logs Insights で数える。2026-11-01に `FilterLogEvents` から替えた。頭から読む方式はログが溜まるにつれ遅くなり、10/1に90秒・11/1に106秒かかっていた。替えた後はレポート全体で約14秒）、180日以上更新されていない単価行、対象月の為替行の有無。
5. **TTSの切り替えと同時本数**（2026-11-01）: 本文・相槌・読み上げのLambdaログから、ずんだもんへ切り替えた回数（うち遅さで切り替えた回数）と、声の会社ごとのピーク同時本数を数える。Scale / Enterprise へ上げる時期の判断材料。数え方は [TTSフォールバック](tts-fallback-and-notifications.md) の第4節。
6. **通知**: SNSトピック `toytalker-ops-monthly` にメール。件名はASCII固定（`ToyTalker monthly cost report YYYY-MM`）。

### 記録側の変更（同日）

- App本文・ESP32本文・読み上げの3 Lambdaで、`toytalker-usage` に `cost_usd`（マージン前のUSD実費）を加算する。突き合わせはこの値で行う。2026-09-12より前の行は `cost_jpy / margin / usd_jpy_rate` で割り戻すため概算になる（レポートに行数を表示）。
- 単価行が無いときに `console.warn("[Pricing] missing price for <provider#api_type>")` を出す。以前は静かに記録されなかった。

### 構築と運用

- ディレクトリ: `backend/toytalker-ops-monthly-lambda/`
- 構築・更新はCDK（`infra/`、2026-09-16から）。SNSトピックとメール購読（宛先は `infra/config/stages.ts` の `opsEmail`）、実行ロール、Lambda（Node.js 24、5分、256MB）、EventBridge Scheduler `toytalker-ops-monthly`（`cron(0 9 1 * ? *)`、Asia/Tokyo）をスタックが作る。コード更新も `cd infra && npx cdk deploy --context stage=rnd`。新しいアカウントでは初回deploy後にメール内のリンクで購読を確認する。以前の `setup.sh` / `deploy.sh` は削除済み。
- 手動実行: `{"month":"2026-08","send":false}` のように対象月と送信有無を指定できる。`send:false` は戻り値の `report` に本文を返すだけでメールを送らない。`fx:false` で為替更新を省略。
- 環境変数:

| 変数 | 内容 |
|---|---|
| `OPS_SNS_TOPIC_ARN` | 必須。CDKが設定 |
| `FX_OVERWRITE` | `true` で当月の為替行を毎回上書き。既定は無い月だけ作成 |
| `STALE_PRICE_DAYS` | 単価行の鮮度しきい値。既定180 |
| `OPENAI_ADMIN_KEY` / `ANTHROPIC_ADMIN_KEY` | 任意。組織の請求額をAPIで取る管理者キー。読み取り専用に絞れず漏洩時の影響が大きいため、当面は置かない方針（レポートの数字と各社ダッシュボードを手で見比べる） |
| `ELEVENLABS_API_KEY` | 任意。使用文字数の取得。本文Lambdaと同じ値を設定済みだが `user_read` 権限が無く401になる。権限付きのキーに差し替えると取得できる |

### 確認と見直しの目安

- 2026-09-12に `{"month":"2026-08","send":false}` で8月分（利用者8人、合計81.77円、実費$0.27）を生成し、9-13にメール送信を確認。2026-09の為替行は154.04円（Frankfurter 2026-09-11）。8月以前は為替行が無く150円固定で記録されている。
- 差分が20%を超えて印が付いたら、まず単価行の単位・値を疑う（トークン種別の違い、キャッシュ料金、音声トークン換算など）。
- 「単価行なしの警告」が出たら `toytalker-api-unit-prices` に行を足す。足すまでその呼び出しは記録されない。
- 単価の自動取得はしない。各社がAPIで単価を公開しておらず、料金ページの読み取りは壊れやすいため。
- プロビジョニングプロファイル等の期限は別件（1年）。
- **モデルの終了通知が来たら**（2026-11-03、`gemini-2.5-flash` の終了で整理。ロードマップ15）、見る場所はこの順: (1) `toytalker-llms` の行（会社・モデル名・既定の印）→ (2) その行を指しているキャラクター（`toytalker-characters` の `llm_id`。後継の行へ書き換え、古い行は消す。アプリの選択肢に出たままにしない）→ (3) `backend/shared/llm.mjs` の2行（相槌用と、テーブルが読めないときの予備）と、モデルの呼び方の違い（思考の設定など。同じファイルの判定関数）→ (4) `toytalker-api-unit-prices` の単価行（モデル別の行があれば）。TTS のモデル名は各Lambdaの `TTS_TABLE`（ロードマップ14で1か所にする）。後継へ自動で回されても、要求の形が古いままだと失敗することがある（2.5 用の思考の設定を 3 系へ送ると 400）ので、自動転送に頼らず自分で替える。

## 11. 前払いポイント制の仕様（2026-09-13 合意、段階1・2は RnD deploy済み、段階3の前提は 2026-11-02 に決定）

第5節の方針（従量課金・前払いポイント・マージン2.0が売価）を実装できる粒度に落としたもの。前提は「ログインはCognito（Apple / Google / LINE）、決済はStripe Checkout、購入はWebページ」。認証の設計は [先送り項目](deferred-items.md) の「ユーザー認証」を参照。

### 11.1 決めたこと

**原則（2026-10-31）: 運営側が損をする状況を作らない。** 原価が売上を上回る使われ方（未払い、無料で使い続けられる、無料で配ったポイントの原価が回収されない）は仕組みで塞ぐ。ビジネスとして続けるための前提で、下の表や 11.7 の決めごとはこれに合わせる。

| 項目 | 決定 |
|---|---|
| ポイントの単位 | 円。1ポイント=1円で、購入額がそのまま残高になる。表示も「残り 1,230円分」のように円で出す |
| 消費額 | 記録している請求額（マージン2.0後の円）をそのまま引く。単価表・為替・マージンの仕組みは変えない |
| 消費のタイミング | 会話は本文Lambda（App / ESP32）がターン終了時に `cost_total` を引く。読み上げも同様。相槌は引かない（マージンで吸収） |
| 無料枠・特典 | **配らない（2026-11-01）**。本体の登録特典も特典コードも作らない。仕組みが増えると穴（偽の本体や大量のアカウントで集める）ができ、小さな運営では効果に見合わないので、費用を下げる工夫とサービスの品質に力を使う。お詫びやキャンペーンでポイントを渡すときは、運用者が `adjust` で手で足す。旧案（本体1台に300円分、アプリだけの利用者に100円分）は採らない。本体を買った人は残高0から始まるので、初めて話すまでの流れ（セットアップの途中で購入へ案内するなど）は段階3で考える |
| 払い方 | **前払い ＋ オートチャージ（使うかは親が選ぶ）**（2026-11-01）。基本はポイントを買う形。オートチャージを選んだ家庭は、残高が決めた額を下回ったら保存したカードで決めた額を買い足す（例: 100円を下回ったら500円）。毎月決まった日に買う形にはしない（使わない月に請求が来て、使われない残高も増えるため）。自動で買い足す額には月の上限を付け、親が選ぶ（初期値は月3,000円）。上限に達したら、その月はもう自動で買い足さずに知らせる。後払いと月額の定額は採らない（11.7） |
| 残高0のとき | **会話を止めて親に知らせる**（2026-11-01。旧案の「無料継続モード」（ずんだもん固定で1日50ターン）は原則に反するので採らない）。会話の始めに残高を見て、0以下なら本体が一言伝えて（例:「ポイントがなくなったよ。おうちのひとにきいてね」）その会話を始めない。アプリには表示とプッシュで知らせる。オートチャージが失敗した（カードの期限切れなど）ときも同じで、運営は損をしない |
| 購入 | Webの購入ページ（`toytalker.zakicorp.com/buy/`。11.10）でログイン後、500 / 1,000 / 3,000円から選ぶ。Stripe Checkoutへ遷移し、カード・Apple Pay・Google Pay・Linkが使える。オートチャージの申し込み（カードの保存、買い足す条件と額、月の上限）と止める操作も同じWebページで行う |
| iOSアプリ | 残高と消費内訳の表示のみ。購入導線はアプリ内課金ルールに触れないよう、Webページの案内にとどめる（スマホ新法の運用が固まったら外部リンクを検討） |
| 通知 | 残高が100円を下回ったら1日1回プッシュ（オートチャージの家庭は不要）。残高0で止めたとき、購入完了時、オートチャージで買い足したとき・失敗したとき・月の上限に達したときにプッシュ |
| 返金・調整 | 原則返金しない（11.7）。例外は、買い間違いで手を付けていない購入を14日以内に取り消すときと、運営の障害で減った分をポイントで埋めるとき。どちらも運用者が行う。チャージバックは自動で差し引く |

### 11.2 データ

- **`toytalker-wallets`**（残高の要約、`owner_id` がキー）: `balance_jpy`、`updated_at`、有効期限のための最終利用日 `last_used_at`（`consume` と `purchase` で更新。`adjust` では更新しない。無い財布は毎日の処理が最初に見た日を付ける）、失効の予告の記録 `expiry_warned_at` / `expiry_warned_for`（予告した時点の `last_used_at`。使われて起点が延びれば古い予告と分かる）、失効した時刻 `expired_at`（段階3c）。段階4で `low_balance_notified_date` を足す。オートチャージの設定（買い足す条件と額、月の上限、今月自動で買った額、Stripe の顧客ID）は別テーブル `toytalker-billing`（11.10。財布は本文Lambdaが毎ターン書くので、設定を書ける権限を本文Lambdaに渡さない）。
- **`toytalker-wallet-ledger`**（追記だけの台帳、`owner_id` ＋ `timestamp#type#id` がキー）: `type`（`purchase` / `consume` / `adjust`、段階3で `refund` / `dispute` / `expire`）、`amount_jpy`（消費はマイナス）、`ref`、`memo`。キーの `id` は `consume` なら `device_id`、`purchase` なら Stripe のセッションID。`grant`（特典）は特典をやめたので使わない。
- **`adjust`**（運用者の手作業の調整。返金・お詫び・検証用など）: 1回の調整につき1行を足し、`memo` に理由、`by` に書いた人を入れる。書いた行は直さず、間違えたら逆向きの `adjust` を足して打ち消す。書くのは `backend/shared/wallet.mjs` の `recordAdjust`（`recordConsume` と同じく台帳の行と残高の加算を1回の書き込みで）で、運用者が手元から `infra/scripts/wallet-adjust.ts` で呼ぶ（`--yes` を付けるまでは残高と書く内容を見せるだけ）。Lambda には書く権限が無い。日次詳細は `consume` の行だけを拾うので、`adjust` の行が増えても表示は崩れない。
- `consume` の行は1ターンの原価の正本（11.6）: `ref`（chat-logs の並べ替えキー `session_id#…#timestamp#…`。返答の行と同じ時刻）、`session_id`、`source`（`app` / `esp` / `tts`）、`cost_usd`（マージン前）、`cost_stt` `cost_llm` `cost_tts` `cost_tool`、`stt_chars`、`llm_provider` `llm_model` `llm_tokens_in` `llm_tokens_out`、`tts_provider` `tts_chars` `tts_fallback`、`tool_usage`、`character_id`。文章は持たない。読み上げ（`source: tts`）は `ref` 無し。
- 台帳の行と残高の加算は1つのトランザクションで書く（`backend/shared/wallet.mjs`）。台帳の行は「まだ無ければ」の条件付きなので二重に引かない。片方だけ残ることも無いので、`balance_after` は持たない（必要なら台帳を足し上げる）。
- 権限: 本文Lambda 2本と読み上げLambdaは、台帳に PutItem、財布に GetItem・UpdateItem だけ（台帳を読む・消すことはできない）。相槌Lambda 2本は財布を GetItem・Query で読むだけ。設定Lambdaは両方を GetItem・Query で読むだけ。

### 11.3 流れ

1. **付与**: しない（特典は配らない、11.1）。運用者が渡すときは `adjust`。
2. **消費**: 本文Lambdaがターン終了時、既存のコスト計算のあとに `cost_total` を残高から引き、台帳に `consume` を書く。読み上げLambdaも同じ。そのターンで残高が負になっても最後まで返す（止めるのは次の会話の始め）。オートチャージの家庭で残高が条件を下回ったら買い足す（段階3。Stripe の鍵を本文Lambdaに持たせず、別のLambdaで引く案）。
3. **残高確認**（段階2、`checkBalance`）: 本文Lambda・相槌Lambda・読み上げLambdaはターンの始めに財布を読み、0以下（財布が無いときも0）なら始めない。会話ログも書かず、LLM も走らない。財布を読めなかったとき（DynamoDB の障害）は止めずに続ける（障害で全部の会話を止めないため。損はその間の原価だけ）。STT（Soniox の一時鍵）は止めないので、止めたターンの音声認識の原価（1ターン0.1円未満）は運営持ち。
   - **RnD は止めない**（2026-11-03）。`infra/config/stages.ts` の `wallet.stopAtZero` が false の環境は `checkBalance` がいつも続けてよいと返す（環境変数 `WALLET_STOP_AT_ZERO`）。財布の無い外部テスターや家族の端末が、0.8.6 以前のアプリでは何も出ずに黙って止まっていたため。引き落としは記録するので残高はマイナスになる。止まる動きを試すときは一時的に true にしてデプロイする。
   - **App**: 本文・読み上げは 402 `{"error":"no_balance"}` を返し、アプリは「ポイントがなくなりました。ポイントを追加すると、また話せます」を出す。相槌も 402 で返し、アプリは鳴らさない。利用状況の残高が0以下なら赤字にして「会話と読み上げは、ポイントを追加するまで止まっています」を添える。
   - **ESP32**: 本体は画面が無いので、本文Lambdaが「ポイントがなくなったよ。おうちのひとにきいてね。」をずんだもんの声で1回返す（キャラクターの声にしないのは、止めるときに有料のTTSを使わないため。合成は1インスタンスで1回だけで、原価は運営持ち）。通常の返答と同じ並び（`segment` → `tts_start` → PCM → `done`）なのでファームは変えない。相槌は 402 で返し、ファームは200以外を捨てる。
4. **購入**: Web購入ページで金額を選ぶ → 課金Lambda（`billing-app`）が本人の `owner_id` をメタデータに付けたStripe Checkoutセッションを作って返す → 支払い完了のWebhook（`payment_intent.succeeded`）を署名検証して SQS 経由で `billing-worker` が受け、PaymentIntent の ID が台帳に無ければ `purchase` を書いて残高に足す（同じWebhookが二重に来ても1回だけ処理）→ プッシュ通知（段階4）。詳細は 11.10。
5. **表示**: アプリの利用状況ページに残高と「今月の消費」を出す。消費内訳は既存の集計をそのまま使う。

### 11.4 認証との関係

- 購入ページで「誰の残高に足すか」を決めるには本人確認が要るので、**購入機能は認証（Cognito）の後**に出す。順番は「認証 → ウォレットと消費記録 → 購入ページ → プッシュ」。
- 認証前でも、付与と消費と残高表示は `owner_id` 単位で先に動かせる。無料枠だけで運用する期間になる。
- 認証導入時に `sub → owner_id` の対応表を作る方針なので、残高は `owner_id` のまま持ち続けられる。

### 11.5 手数料と最低購入額

- Stripeは国内カード3.6%、固定費なし。500円の購入で18円。PayPalは3.6%＋40円、Squareは3.25%〜で、カード決済はどこも3〜4%。App Store課金は15〜30%。
- 手数料と原価を引いた粗利を保つため、購入単位は500円以上にする。

### 11.6 会話ログと原価の分離（2026-10-30 方針、着手時に改めて合意する）

- **いま**: `toytalker-usage` は日 × 機器 × 種類の合計（文章なし）。一方 `toytalker-chat-logs` の返答の行に、会話の文章と一緒に1ターンの原価（`cost_llm` `cost_tts` `cost_stt` `cost_tool` `cost_total`、トークン数、文字数）が入っている。利用状況の「日次詳細（会話ごとのコスト）」はこの行から金額と文章を同時に読む。
- **困ること**: ロードマップ7の会話保護とぶつかる。`chat-logs` に保持期間（TTL）を付けると原価も消える、運用者に「コストは見えるが会話は読めない」権限を作れない、CMK で読める人を絞るとコストの集計も絞られる。
- **方針**: 1ターンの原価は台帳 `toytalker-wallet-ledger` の `consume` 行（文章なし、`ref` に会話ログのキー）と `usage` の合計に持ち、`chat-logs` からコストの列（`cost_*`、トークン数、文字数、`tool_usage`、`tts_fallback`）を外して文章だけにする。「日次詳細」は台帳から金額、`chat-logs` から文章を引く。台帳にあって `chat-logs` に無いターン（保持期間で文章だけ消えた）は文章なしで金額だけ出す。
- **決めたこと（2026-10-31）**: (a) 段階1で分離と台帳と残高の引き落としを一緒に出す（11.8）。(b) 過去分のコスト列（RnD の 3,903行）は台帳へ移さない。日次詳細は台帳に行が無ければ `chat-logs` のコスト列を読む（それも無い2026-09以前の行は計算し直す）。会話保護（CMK・TTL）を入れるのは新しい本番アカウントで、そこは最初から分離した形で始まるので、RnD の旧行が残っていても困らない。(c) ESP32 も App と同じ形にする。
- **日付は日本時間で区切る**（2026-11-01）: `usage` の日付（並べ替えキーの先頭）と「日次詳細」の1日は日本時間（`backend/shared/jst.mjs`）。`chat-logs`・台帳の `timestamp` は UTC のまま持ち、日次詳細は日本時間の1日を UTC の範囲にして引く。それより前の `usage` の行は UTC の日付のまま（移さない）。為替の月は従来どおり UTC。

  後払いは「運営が損をしない」原則に反し、ロードマップ8の「費用の天井はポイント制で作る」も無くなる。定額は使い込まれるほど赤字になる（第7節と同じ理由）。

- **Apple の外部リンク（2026-11-03 調査。Apple の「Changes to iOS in Japan」と国内の解説記事）**: iOS アプリから購入ページへ押せるリンクを出すには、ライセンス契約の付属文書 A12 に同意して entitlement を取り、リンクのタップから7日以内の外部の売上に **Store services commission 15%**（Small Business Program なら 10%）を払い、毎月15日までに外部の取引を Apple へ報告し、アプリ内の開示シートを実装する。さらに **Kids カテゴリのアプリと 13 歳未満の利用者には外部の Web での購入案内そのものができない**（13〜17 歳は保護者ゲートの後ろなら可）。いまの「URL を文字で書くだけ（押せない）」は、解説記事（Repro）では Apple・Google とも手数料なしの扱いとされるが、Apple の公式ページには文字だけの案内の記述が無い（未確認）。**決定**: 3a は文字の案内のまま。ボタンにするのは、売上が出てから「15% を払ってでも導線が要るか」で判断する（500円の購入で 75円。Stripe の 18円と合わせて 93円）。アプリは親のアカウントで使うものなので App Store のカテゴリは Kids にしない（Kids だと外部購入の案内が一切できない）。Android（Google）も外部リンクには手数料があるので同じ扱い。
- Stripe Checkoutで使える支払い手段は日本アカウントの設定次第。PayPalは当面入れない。
- **返金（決定 2026-11-02）: 原則返金しない。例外は2つ。** (1) 買い間違いで、その購入の後に1度も使っていないときは、購入から14日以内なら運用者が Stripe で取り消し、台帳に `refund`（マイナス）を書く。Stripe の手数料3.6%は戻らないので運営の持ち出し（500円で18円）。(2) 運営の障害で減った分は、お金ではなく `adjust` でポイントを足す。理由: 資金決済法は前払いのポイントの払い戻しを原則禁止している（金融庁の資料。届出前の発行者にも当てはまるかは未確認）。返金しないことと例外の条件は、特商法の最終確認画面の「申込みの撤回又は解除に関する事項」として購入画面に出す。
- **チャージバック（決定 2026-11-02）**: Stripe から `charge.dispute.created` が来たら、Webhook のLambdaがその購入額を台帳に `dispute`（マイナス）で書いて残高から引き、オートチャージを止め、運用者にメールする。残高が負になれば次の会話から止まる（11.3）。基本は争わない（申し立て1件 ¥1,500 は勝ち負けにかかわらず運営の負担で、購入額が小さいので争う手間に見合わない）。争って勝ったときは逆向きの `adjust` で戻す。3-D セキュアを通した支払いの不正利用はカード会社の負担になる（ライアビリティシフト）が、3-D セキュアを通さない自動の買い足しでは運営の負担になる。
- **オートチャージと 3-D セキュア（2026-11-02 確認、Stripe の「日本の 3D セキュア必須化の例外」）**: カードの保存時に `usage=off_session`（Checkout なら `setup_future_usage=off_session`）で一度 3-D セキュアを通せば、その後の運営側から引く支払い（MIT）は 3-D セキュア不要。Apple Pay・Google Pay・Link は免除。保存した時点の同意（マンデート）として、買い足す条件・額・月の上限を申し込み画面で示して同意を取る。新しい Off-Session Payments API（プレビュー）は使わず、`PaymentIntent` に `off_session=true` を付ける従来の形で作る。**設定の変更に 3-D セキュアが要るか（2026-11-06 決着）**: 利用者が設定（額・条件・月の上限）を変えるのが Stripe の言う「顧客からの契約内容の変更の申出」（原文 "If any change to a contract, service, or product requires customer approval, the associated payment must be customer-initiated (CIT) and must explicitly request 3DS."）に当たるかを Stripe に聞いた。2026-11-02 の AI 窓口は断定できず、11-03 のチャットの担当者は「下げる変更は保存し直し不要」と言ったが、日本の事情が分かる担当からのメールで確定した。**Stripe プロダクトサポートの答え（2026-11-06、メール。Gmail に保存）**: (1) 1回の額・条件・月の上限の変更は、上げる・下げるのどちらも契約内容の変更に当たる。変更後の条件に同意を取り、Checkout の設定フロー（`usage=off_session` の SetupIntent、3-D セキュアあり）をもう一度通してカードを保存し直す。(2) 止める操作は以後の自動請求が無いので 3-D セキュアの再実行は不要。(3) 保存し直した後の最初の請求を CIT にする必要は無く、同じ条件での自動の買い足しは MIT として引ける。(4) カード発行会社の判断で個別の off-session 決済に追加認証が求められることがあるので、利用者をもう一度操作できる画面へ誘導して 3-D セキュアを完了させる救済の流れを用意することを推奨（https://docs.stripe.com/payments/3d-secure/authentication-flow）。**設計**: 設定を変える操作（新しく申し込む・上げる・下げる）はすべて Checkout の setup モードで保存し直す。止める操作だけ保存し直さない。追加認証を求められて失敗した買い足しは `auto_status: failed` にし、利用者に購入ページから保存し直してもらう（11.10）。Stripe への追加の問い合わせは不要。
- **特商法の最終確認画面（2026-11-02 確認、消費者庁「通信販売の申込み段階における表示についてのガイドライン」）**: オートチャージそのものの記述は無いが、「自動更新のある契約はその旨を出す」「期限の無い継続契約は1年分など一定期間の総額の目安を出すのが望ましい」「解約の条件・方法を出す」とあるので、自動更新と同じ扱いで出す。オートチャージの申し込み画面: 自動で買い足すこと、条件（残高が◯円を下回ったら）、1回の額、月の上限（総額の目安の代わり）、支払いの時期（下回った時点）と方法（保存したカード）、止め方（同じ Web ページでいつでも。止めたら次の買い足しから止まる）。単発の購入画面: 額、支払い方法、有効期限、返金しないことと例外。どちらも6項目（分量・対価・支払いの時期と方法・提供時期・申込期間・撤回と解除）を満たす。
- グループとメンバーの招待（[先送り項目](deferred-items.md)）との関係（2026-10-31）: ポイントはグループ（`owner_id`）に付くので、メンバーが増えても同じ財布を複数人で使うだけ。ただし `purchase` の行に買った人のユーザー ID（`sub`）を書いておく（メンバーが増えてから後で足せないため）。

### 11.9 消費税（2026-11-02、未確認。本番で売る前に税務署の相談窓口で確かめる）

- **値段は税込みで決める**: 購入ページは「500円」（または「500円（税込）」）と出し、親が払うのはちょうどその額。1ポイント=税込みの1円で、会話で引く額（マージン2.0後の円）も税込みとして扱う。親に見える数字（購入額・残高・消費額）は全部これでそろい、税は運営の帳簿の中だけの話にする。
- **いまは納めない（免税事業者）**: 2年前の売上が年1,000万円以下なら消費税を納めない。前年の上半期に売上か給与が1,000万円を超えると早まる例外がある。
- **売上が増えたら**: 年1,000万円を超えた年の2年後から、売上の約11分の1（500円なら約45円）を納める。AWS の国内請求や Stripe 手数料に含まれる消費税は差し引ける。値段・ポイント・仕組みは変えなくてよく、減るのは運営の取り分だけで、実際のマージンは 2.0 から約1.82 になる。そのときに単価かマージンを見直す（2年の猶予があるので急がない）。
- **書き方**: 免税のあいだは「うち消費税◯円」と税額を分けて書かない（納めていない税を受け取っているように見えるため）。
- **インボイスは登録しない**: 買い手が事業者のときの制度で、買い手は家庭なので要らない。
- **ポイントの売上をいつ計上するか**（売ったときか、使われたときか）は課税事業者になったら税理士と決める。台帳に `purchase` と `consume` が両方あるので、どちらにも対応できる。
- Stripe の Tax（税の自動計算）と Billing（従量の後払い請求）は使わない（2026-11-02、Stripe のアカウント作成時）。どちらも取引ごとに追加の手数料がかかり、国内だけで税込みの値段なら税の計算は要らず、ポイントの引き落としは自分の台帳で行うため。

**買い足し（5分ごと）**: billing の `auto_enabled` の行を読み、財布の残高が `auto_below_jpy` を下回っていれば予約して請求する。Streams（テーブルの変更の流れ）ではなくポーリングにしたのは、条件の最小値 100円が約140ターン（1時間近い会話）に当たり5分の遅れで困らず、at-least-once・シャード詰まり・フィルタの確認が要らず、手元から1回呼んで試せるため。即時性が要るようになったら Streams に置き換える。
- 予約: 条件付き UpdateItem で「予約が無い」「`auto_charged_jpy + auto_amount_jpy ≤ auto_monthly_cap_jpy`（月が変わっていれば0から）」「`auto_last_charged_at` から1時間以上」のときだけ `auto_reservation` を書く。上限に届くなら `cap_reached` にして止める（その月は知らせるだけ。段階4）。1時間の cooldown は、条件 500円・額 500円のような組で買い足した直後にまた下回って連続請求するのを防ぐ。
- 請求: `PaymentIntent` を `customer`・`payment_method`・`off_session: true`・`confirm: true`・冪等キー = 予約 ID で作る。**再試行は同じ予約 ID を冪等キーにして同じ要求を出す**（Stripe は同じ冪等キーには同じ PaymentIntent を返す。24時間）。予約を消すのは Webhook で成功か最終失敗を受けたときだけで、「古いから外す」はしない（請求は成功したが Lambda が落ちて印を消せなかったとき、新しい ID で再請求して二重に引くため）。24時間を超えて残った予約は運用者へメール。
- 設定の変更（11.7 の Stripe の答え、2026-11-06）: 新しく申し込む・上げる・下げる → すべて Checkout の setup モードで保存し直す（新しい同意文を見せ、3-D セキュアを通す）。止める → 保存し直さず billing を更新するだけ。

**最終確認画面（特商法）**: 自分のページと Stripe の画面の両方に出す。自分のページで 11.7 の項目（単発: 額・支払い方法・有効期限・返金しないことと例外。オートチャージ: 自動で買い足すこと・条件・1回の額・月の上限・支払いの時期と方法・止め方）を全部出して「同意して支払いへ進む」。実際の「支払う」は Stripe の画面にあるので、要点を Checkout の `custom_text.submit` にも入れ、`consent_collection.terms_of_service` で同意のチェックも取る。どこまでを最終確認画面とみなすかはガイドラインから読み切れない（推測）ので両方に置く。同意文には版番号を付け、`auto_consent.version` に残す。

**有効期限（毎日）**: wallets を Scan（財布が数千を超えたら索引。13）し、`last_used_at` から 335日で予告の記録、365日で台帳に `expire`（残高を0にする額。キーは日付と `owner_id` で1日1回）。予告の通知は段階4のプッシュ。月次レポートに全員の残高の合計（3月末・9月末の値、11.7 の資金決済法）。実装の詳細は下の「3c の実装」。

**親への知らせ**: 段階4のプッシュまでは Stripe の領収書メール（Customer にログインのメールを入れる）で代わりにする。チャージバックを減らす効果もある。

**実装で決まったこと（2026-11-03）**: (1) `billing-app` の Function URL は、他の Lambda を IAM 認証に切り替えた後も公開（NONE）のまま（`FunctionSpec.url.alwaysPublic`）。CloudFront の OAC の署名には本文の SHA-256 を `x-amz-content-sha256` で添える必要があり、Stripe の Webhook はそれを付けられないため。守りはトークンと Webhook の署名で、本番の WAF（CloudFront）は直叩きには効かない（Lambda の呼び出し回数のアラームで気づく）。(2) 購入ページのリンクと Stripe の戻り先は `/buy/index.html`（CloudFront の既定ルートオブジェクトはルートにしか効かない）。`/buy/` で開けるようにするなら CloudFront Function で書き換える（web/README）。(3) Stripe の SDK は使わず REST を fetch で呼ぶ（`backend/shared/stripe.mjs`。Checkout・Customer・PaymentIntent・Event の数本だけで、依存を増やさない）。(4) Checkout の `consent_collection.terms_of_service` は本番（`stripeLivemode`）だけ付ける。Stripe の設定（公開情報）に利用規約の URL `https://toytalker.zakicorp.com/buy/terms.html` が要るが、sandbox は事業者情報を入れられない（本番の申し込みで入れる。2026-11-03 に確認）。同意は購入ページの確認画面でも取っている（`consent_version`）。(5) 親への領収書は Stripe のメール（Customer にログインのメールを入れる。Stripe の設定で「支払い成功時のメール」を ON にする）。(6) トークンの検証（`backend/shared/auth.mjs`）はアプリのクライアント ID だけを受け付けるので、`billing-app` にだけ環境変数 `COGNITO_WEB_CLIENT_ID` で購入ページの Web クライアントも渡して通す。他の Lambda は Web クライアントのトークンを受け付けない（購入ページのトークンで `/me` やデバイス登録は叩けない）。

**残る前提**: 最大の信頼点は Stripe の署名秘密と worker の鍵（SSM の読み取りは関数ごとの最小権限）。トークンを盗まれた人にできるのは、止める・残高と下4桁を見る・購入ページを開くまでで、**被害者のカードで請求額を変えることはできない**（額・条件・上限の変更はすべて 3-D セキュア付きの保存し直しが要る）。金銭被害の最大は既存設定の月の上限まで。CSRF はトークンがヘッダー送り（cookie 不使用）なので成立しない。カード情報は Stripe の Checkout に任せ（PCI は SAQ-A 相当）、手元は brand・下4桁・期限だけ。ログには event ID・PaymentIntent ID だけで、メール・`sub`・カード番号は書かない。

**順番**: 3a = billing テーブル・Lambda 2本・SQS・単発の購入・Webhook（`purchase` / `refund` / `dispute`）・購入ページと最終確認画面・`last_used_at`。3b = オートチャージ（setup・5分ごとの買い足し・月の上限・失敗）。3c = 有効期限の毎日の処理・月次レポートの残高合計。

**3b の実装（2026-11-07。設計どおりの点は省く）**:
- 経路: `POST /billing/auto-charge/setup`（設定を検査して Checkout の setup モードを作る。設定と同意の版・`sub` はセッションと SetupIntent の metadata に載せる）→ Stripe でカード登録（3-D セキュア）→ `checkout.session.completed` → worker が SetupIntent を `expand[]=payment_method` で取り直し（`status: succeeded`・`usage: off_session`・Customer の `owner_id` が一致することを確認）、billing にカードと設定・`auto_consent`・`auto_status: active` を書き、その場で残高が条件を下回っていれば買い足す。古いセッションの完了が後から届いても `auto_consent.at` が新しい方を残す。戻り先は `auto-done.html`（申し込みを始めた時刻より新しい同意が付くまで数秒ごとに読み直す）。
- 止める: `PUT /billing/auto-charge` `{ enabled: false }` → `auto_enabled: false`・`auto_status: stopped`（設計の4値に足した）。カードと設定は残し、再開は申し込み直し（保存し直し）。チャージバックで止まった家庭（`stopped_by_dispute`）の申し込みは 403 `auto_blocked`（運用者が billing の `auto_status` を直すまで）。
- 買い足し: EventBridge Scheduler `toytalker-billing-auto-charge-<環境>`（5分ごと、`{ "task": "auto-charge" }`）。予約 `auto_reservation` は `{ id, at, amount_jpy, balance_jpy, payment_intent?, pi_status?, notified_at? }`。Stripe から答えが返ったら `payment_intent` を書き、以後は Webhook を待つだけ。答えが返る前に落ちていたら次の回に同じ冪等キー `auto-charge:<予約 ID>` で出し直す。**402（カード拒否・`authentication_required`）はその場で `failed` にして予約を消す**（請求は成立していない。Webhook の `payment_failed` も同じ内容を書くだけ）。通信の失敗や 5xx は予約を残して次の回へ。24時間を超えた予約は `auto_charge_stuck` で運用者へ1回メール。`cap_reached` は月が変わった回の予約で `active` に戻る。
- 手元で1回走らせる: `aws lambda invoke --function-name toytalker-billing-worker-rnd --cli-binary-format raw-in-base64-out --payload '{"task":"auto-charge"}' out.json`（ログの `status` に `seen / charged / waiting / skipped / cap_reached / declined` の数が出る）。
- sandbox での確認の手順（2026-11-07 に (1)〜(6) すべて実施し、期待どおり）: (1) worker の restricted key に SetupIntents と PaymentMethods の Read を足す（Stripe の画面で鍵を編集。SSM の値は変わらない）。(2) 購入ページで申し込み（テストカード `4242…`。本物に近いのは `4000 0025 0000 3155` で、登録時だけ 3-D セキュアが出て off-session の請求は通る）→ `auto-done.html` に設定が出る → billing の行にカードと `auto_status: active`。(3) `adjust` で残高を条件より下げて5分待つ（か手元で1回走らせる）→ 台帳に `purchase`（`kind: auto`）、`auto_charged_jpy` が増え、予約が消える。(4) 失敗: カードを `4000 0000 0000 0341`（保存はできるが請求で拒否）か `4000 0027 6000 3184`（登録時に 3-D セキュアが出て、off-session の請求は毎回 `authentication_required` で拒否）で登録し直して同じ流れ → `auto_status: failed`、購入ページに理由。(5) 上限: 上限 1,000円・額 1,000円に変えて（今月の累計は残る）残高を下げると `cap_reached`（累計の確認が1時間の間隔より先なので待たずに見られる）。(6) 止める → `auto_enabled: false`、5分後に買い足しが出ない。

**3c の実装（2026-11-07。設計どおりの点は省く）**:
- 経路: EventBridge Scheduler `toytalker-billing-expire-<環境>`（毎日 04:00 JST、`{ "task": "expire" }`）→ worker が wallets を Scan し、財布ごとに (1) `last_used_at` が無ければ今日を起点として付ける（`stamped`。段階3より前からある財布は、この処理が最初に見た日 = 段階3を出した日から数える。定数は持たない）、(2) 残高が0以下なら何もしない、(3) 335日以上なら `expiry_warned_at` / `expiry_warned_for` を書く（`warned`。同じ起点に対しては1回だけ）、(4) 365日以上なら台帳に `expire` を書いて残高を0にし、財布に `expired_at` を書く（`expired`）。
- 二重と競合の防ぎ方: `expire` の台帳キーは `<その日の始まり（JST）の時刻>#expire#<日付>` で1日1回（同じ日に2回走っても2行目は書けない = `duplicate`）。財布の更新は「残高と `last_used_at` が Scan で読んだときのまま」の条件付きで、Scan の後に使われた・調整された財布は失効させない（`changed`。次の日に見直す）。残高は DynamoDB の数値の文字列のまま持ち回る（`wrapNumbers`。`consume` の積み重ねで `975.01661000000000052` のように JavaScript の数値より長い桁になっていて、丸めると条件が一致しない。2026-11-08 に RnD で見つけて直した）。予告の記録も `last_used_at` が同じときだけ。
- オートチャージは失効の前に止める（`auto_enabled: false`・`auto_status: stopped_by_expiry`。2026-11-08 決定）。止めないと残高0が条件を満たし、1年使っていない家庭のカードに5分以内に請求が走る。カードと設定は残り、再開は購入ページから申し込み直し。
- 画面: `GET /billing` に `expired_at`（失効して0になった時刻。その後に使っていれば null）。購入ページのオートチャージの欄は `stopped_by_expiry` を「失効のため止めた」と出す。購入ページは失効していれば「◯日に有効期限が過ぎ、残っていたポイントは失効しました」を出す。失効した家庭があれば運用者へ `points_expired` のメール1通（日付・件数・合計・owner_id）。
- 月次レポートに「前払いポイントの残高」の節（残高合計・残高のある財布の数・30日以内に失効する財布）。対象月が3月・9月なら基準日の目安と出し、合計が 1,000万円を超えていれば届出の注意を出す。月次 Lambda に wallets の Scan 権限を足した。
- 手元で1回走らせる: `aws lambda invoke --function-name toytalker-billing-worker-rnd --cli-binary-format raw-in-base64-out --payload '{"task":"expire"}' out.json`（ログの `status` に `seen / stamped / warned / expired / changed / skipped / failed` の数）。`{"task":"expire","dry_run":true}` なら読むだけで何も書かない。公開ページの反映は `web/README`（`--cache-control "no-cache"` を付ける）。
- RnD での確認の手順（2026-11-08 にすべて実施し、期待どおり）: (1) dry_run で財布の数と `stamped` の数を見る → 本番と同じ入力で1回走らせ、起点の無い財布に `last_used_at` が付く（10件）。(2) 試験用の財布の `last_used_at` を手で 340日前にする（`aws dynamodb update-item`）→ 走らせる → `expiry_warned_for` が付き、2回目は `skipped`。(3) 366日前にする → 走らせる → 台帳に `expire`、残高0、`expired_at`、購入ページに失効の文言、運用者にメール。2回目は残高0なので `skipped`。(4) オートチャージを有効にして (3) → `auto_stopped` が付き `stopped_by_expiry`、買い足しの回は何も出ない。(5) `wallet-adjust.ts` で残高を戻し、購入か会話で `last_used_at` が延びて購入ページの文言が戻る。
- 同じ財布を同じ日に2回失効させることはできない（台帳キーが日付なので2回目は `duplicate` → `skipped`。オートチャージを止める処理だけは走る）。検証でもう一度失効させたいときは日を改める。

**Stripe 側の設定（2026-11-03 に sandbox で実施。本番の申し込み時に同じものを作る）**: 鍵は「Create secret key → Building your own integration → Custom permissions」で2本。`toytalker-billing-app`: Checkout Sessions・Customers・Products・Prices の Write。`toytalker-billing-worker`: Events・Customers・Charges and Refunds・Setup Intents・Payment Methods の Read、Payment Intents の Write（Charges and Refunds の Read は返金の一覧を `/refunds` から取るのに要る。API 版 2022-11-15 以降は `charge` に同梱されない。Setup Intents・Payment Methods の Read は 3b で足す: 保存したカードの ID と brand・下4桁・期限を取る）。Webhook は「Add destination」で `payment_intent.succeeded` `payment_intent.payment_failed` `checkout.session.completed` `charge.refunded` `charge.dispute.created` の5つ、宛先 `https://api-rnd.zakicorp.com/billing/webhook`（CloudFront 経由で通った）、署名の秘密は送信先の画面の Signing secret。3本とも SSM（`infra/scripts/put-secret.ts` か AWS コンソールのパラメータストア）。sandbox では事業者情報（利用規約 URL）を入れられない。
