# 原価と課金の考え方（2026-09-13 時点の方針）

従量課金で「使った分だけ、安く、気軽に」を実現するための、原価の見方と料金の組み立て。月次運用レポートLambda（第10節）の前提になる。2026-09-10の市場調査（旧 cost-estimate.md）と2026-09-12のツールコスト記録（旧 search-cost-tracking.md）は末尾に統合した。

## 1. 原価の記録と請求額の関係

```
請求額（円） = API単価（USD） × 使用量 × その月の為替 × マージン
```

- **API単価**: `toytalker-api-unit-prices` にドル建てで保存（Sakuraのみ円建て）。プロバイダー×種別ごと（`google#llm` など）。自動更新はしない。
- **為替**: `toytalker-exchange-rates` に月ごとの行。毎月1日に運用Lambdaが ECB（欧州中央銀行）の公表レートを保存し、その月は固定。行が無い月は150円で計算される。
- **マージン**: `service#margin` の1行。現在 **2.0**。これが従量課金の「売価」そのもの。
- 記録される種別は `stt / llm / tts / tool` の4つ。相槌のLLM・TTSと、AWS・為替・カード手数料は記録しない（マージンで吸収）。

## 2. 1時間の会話の原価（マージン前）

前提: 40ターン、AI発話30分、子供の発話15分、LLMはGemini 2.5 Flash（1ターン入力2,500トークン・出力80トークン）、為替152円。

| 項目 | Sakura（ずんだもん） | Cartesia（リアル系） |
|---|---|---|
| TTS | 3.6円（12,000モーラ） | 約160円（1万字超、$0.00005/字） |
| LLM | 5.8円 | 5.8円 |
| STT（Soniox） | 3.3円 | 3.3円 |
| ツール（検索2回） | 0.3円 | 0.3円 |
| **記録される原価** | **約13円** | **約170〜180円** |
| 相槌（Gemini Flash 40回＋TTS） | 1.6円 | 約2円 |
| AWS（Lambda実行が中心、転送・ログ・DynamoDB） | 3.3円 | 約4円 |
| カード海外手数料（約2%） | 0.3円 | 約4円 |
| **本当の原価** | **約18円** | **約190〜200円** |

- DynamoDBは1時間で0.1円未満。ログを何年ためても問題にならない。
- 記録外の原価は「ターン数に比例」なので、TTSが安いSakuraでは記録原価の約40%、Cartesiaでは約3%にあたる。

## 3. マージン2.0での収支

| ボイス | 請求（1時間） | 本当の原価 | 決済手数料（Stripe 3.6%） | 手元に残る割合 |
|---|---|---|---|---|
| Sakura | 約26円 | 約18円 | 約1円 | 約27% |
| Cartesia | 約350〜400円 | 約200円 | 約13円 | 約45% |

どちらも赤字にならない。**マージン2.0で進め、月次レポートで実請求と見比べて薄ければ2.5に上げる**。値はDynamoDBの1行なのですぐ変えられる。過去の記録は計算時の値を保持するので遡って変わらない。

### 1ターンあたり・500円で遊べる量（Sakura）

| | 1ターン請求 | 500円で | 1日20分（約13ターン）なら |
|---|---|---|---|
| 返答ふつう | 約0.65円 | 約770ターン（約19時間） | 約2か月 |
| 返答長め | 約0.85円 | 約600ターン（約15時間） | 約1か月半 |

Cartesiaは1ターン約9円で、500円は約1.3時間。

## 4. 為替と手数料の扱い

- **為替は月初にECB値で固定**。市場レート（Googleの表示など）とは1〜2%ずれることがあるが、月単位の記録としては誤差の範囲。実勢に寄せたければ運用Lambdaを毎日更新に変えられる。
- **各社からの請求**はドル建て都度課金（OpenAI・Anthropic・Soniox・FishAudio）、前払いクレジット（Cartesia月額。Serperは2026-10-28まで無料クレジットのみ）、円建て（Sakura、Googleは請求アカウント次第）が混在する。カードで払う分には海外事務手数料（1.6〜2.2%）が乗る。
- 実支払いと記録額を一致させようとせず、**ずれはマージンで吸収し、月次レポートで確認する**。
- ユーザーから受け取る側の決済手数料（Stripe約3.6%、App Store 15〜30%）は別物で、売上から引かれる。

## 5. 従量課金の形

- **前払いポイント制**を採る。例: 500円分を購入し、会話のたびに請求額ぶんを減らす。未払いリスクが無く、少額決済の繰り返しを避けられ、ユーザーにも上限が見える。
- いまの記録（利用者・日・種別ごとの円額）がそのままポイント減算の元データになる。
- iOSアプリ内でポイントを売るとApp Store手数料がかかるため、Web購入の経路を検討する。規約・法規制は実装前に確認。
- アプリの声の選択画面に「この声は1回約9円」「ずんだもんは1回約0.7円」のように単価を出し、従量の納得感を作る。

## 6. ポケとも（シャープ）との比較

| | 1回あたり | 400回ぶん |
|---|---|---|
| ポケとも（ノーマル495円/400回、他プランも同単価、無制限3,300円） | 約1.24円 | 495円 |
| ToyTalker Sakura | 約0.65円 | 約260円 |
| ToyTalker Cartesia | 約9円 | 約3,600円 |

Sakuraならほぼ半額で、使わない月は0円。ポケともの1回1.24円は市場が受け入れている水準なので、マージンを上げる余地はある。

## 7. プレミアムボイス（声優の声など）の料金体系

- **使い放題の定額はしない**。声優クローン級の単価（1ターン原価約4.5円）だと、月730ターンで原価割れになる。子供が気に入って使い込むほど赤字になる構造は避ける。
- 採る形は「**月額固定（解放料）＋従量（今までどおり）**」。
  - 月額は声優へのライセンス料をまかなう。ライセンスが売上分配型なら月額は低めでも成立する。
  - 会話はその声の原価×2.0をポイントから消費（1回約9円）。使われ方に関係なく変動費は従量が必ずカバーする。
  - 二重取りに見えないよう、月額にポイントを少し含める（例: 月額500円に300円分のポイント込み）。
- 声優のライセンス条件（用途・期間・停止時の扱い・分配率）は料金設計より先に固める。AIによる声の合成は業界的に敏感なので契約を明確にする。
- 実装: `toytalker-voices` にプラン印を付け、アプリの出し分けに加えて**Lambda側でも加入者かを確認**してから合成する。コスト記録は声ごとの単価で計算しているので変更なし。

## 8. 今後の課題

- **単価はモデル単位の行を優先する**（2026-10-27実装）: 本文Lambdaは `${provider}#llm#${model_id}`（例 `anthropic#llm#claude-haiku-5-5`）→ `${provider}#llm` の順で探す。プロバイダー行は従来どおり残し、同じ会社で2つ目以降のモデルはモデル付きの行を足す。Gemini 3.5 Flash Lite は 2.5 Flash と同単価なので `google#llm` に落ちる。
- **単価行の属性**: 2026-09-13に全行へ `provider` / `api_type` を属性として追加した（キーを `#` で分けた値）。コンソールでの絞り込みと集計コードの簡略化のためで、計算はこれまでどおりキーで引く。新しい行を足すときもこの2つ（モデル付きなら `model` も）を入れる。
- **Sonioxの見積もり**: 文字数から逆算しているが、実際は音声を流した時間で課金されている可能性がある。ESP32は聞いている間ずっと送るので、月次レポートの手動確認で最初に見る。
- **LLM入力トークン**: 会話履歴を長く持つほど膨らむ。履歴の上限を決めておくと原価が安定する。
- **相槌の定型音声化**: 原価よりレイテンシ改善の効果が大きい。別件として検討。
- **AWS Lambda**: 本文Lambdaは2GBでLLM・TTSの応答待ち中も課金される。記録外の原価では最大の項目。

## 9. 有料ツール（外部API）のコスト記録（2026-09-12）

- LLMのfunction callingで呼ぶツールのうち、外部に料金が発生するもの（現状はBrave検索）だけを `tool` 種別で回数課金として記録する。自前のLambda/DynamoDBを呼ぶだけの無料ツールは何も記録しない。検索は「調べ物をよくする子」と「雑談だけの子」で回数が大きく違うため、一律マージンではなく回数で数える。
- 単価は `toytalker-api-unit-prices` の `${provider}#tool` 行、`input_unit_type = "requests"`。`brave#tool` = $0.005/回（定価。毎月$5分=1,000回の無料枠は月次で差し引く）。1回検索のターンでツール代は約0.75円（マージン前）。2026-10-27に Serper（$0.001/回だが$50前払いが6か月で失効し、月27回の利用では1回約$0.31相当だった。API検索クエリの保持ポリシーの記載なし）から切替。`serper#tool` の単価行は履歴の参照用に残す。
- 有料ツールを増やすとき: `backend/shared/llm.mjs` の `PAID_TOOLS` に `ツール名: { provider, model }` を1行足し、単価行を足す。アプリ側は円グラフの色を付けたい場合だけ `CHART_COLORS` に追加。無料ツールを増やすときは何もしない。
- 残骸: 最初は `search` 種別で実装し同日 `tool` へ汎用化した。`2026-09-12#<device>#search` の利用状況行と `serper#search` の単価行が1件ずつ残っている。参照されないので消してよい。

## 10. 月次運用レポートLambda（為替更新・請求突き合わせ・単価点検）

2026-09-12に `toytalker-ops-monthly-lambda` を追加。毎月1日 09:00 JST に動き、結果を1通のメールで送る。値の自動修正はしない。

### やること

1. **為替**: Frankfurter（ECB公表レート、キー不要）からUSD→JPYを取り、`toytalker-exchange-rates` に当月の行が無ければ作る。既存行は維持（`FX_OVERWRITE=true` で上書き）。
2. **先月の記録集計**: `toytalker-usage` を先月分でスキャンし、プロバイダー×種別ごとにマージン後の円額・マージン前のUSD実費・使用量をまとめる。
3. **各社の実績との突き合わせ**: APIで請求を取れる社（OpenAI・Anthropic）は差分と割合を出し、20%超なら要確認印。ElevenLabsは使用文字数。取れない社（Cartesia・Serper・Google・Soniox・Sakura・Fish Audio）は記録実費と確認先URLを並べる。
4. **点検**: 単価行が無くて記録されなかった呼び出し（記録側Lambdaの `[Pricing] missing price` ログをCloudWatchから検索）、180日以上更新されていない単価行、対象月の為替行の有無。
5. **通知**: SNSトピック `toytalker-ops-monthly` にメール。件名はASCII固定（`ToyTalker monthly cost report YYYY-MM`）。

### 記録側の変更（同日）

- App本文・ESP32本文・読み上げの3 Lambdaで、`toytalker-usage` に `cost_usd`（マージン前のUSD実費）を加算する。突き合わせはこの値で行う。2026-09-12より前の行は `cost_jpy / margin / usd_jpy_rate` で割り戻すため概算になる（レポートに行数を表示）。
- 単価行が無いときに `console.warn("[Pricing] missing price for <provider#api_type>")` を出す。以前は静かに記録されなかった。

### 構築と運用

- ディレクトリ: `backend/toytalker-ops-monthly-lambda/`
- 構築・更新はCDK（`infra/`、2026-09-16から）。SNSトピックとメール購読（宛先は `infra/config/stages.ts` の `opsEmail`）、実行ロール、Lambda（Node.js 24、5分、256MB）、EventBridge Scheduler `toytalker-ops-monthly`（`cron(0 9 1 * ? *)`、Asia/Tokyo）をスタックが作る。コード更新も `cd infra && npx cdk deploy --context stage=rnd`。新しいアカウントでは初回deploy後にメール内のリンクで購読を確認する。以前の `setup.sh` / `deploy.sh` は削除済み。
- 手動実行: `{"month":"2026-08","send":false}` のように対象月と送信有無を指定できる。`send:false` は戻り値の `report` に本文を返すだけでメールを送らない。`fx:false` で為替更新を省略。
- 環境変数:

| 変数 | 内容 |
|---|---|
| `OPS_SNS_TOPIC_ARN` | 必須。CDKが設定 |
| `FX_OVERWRITE` | `true` で当月の為替行を毎回上書き。既定は無い月だけ作成 |
| `STALE_PRICE_DAYS` | 単価行の鮮度しきい値。既定180 |
| `OPENAI_ADMIN_KEY` / `ANTHROPIC_ADMIN_KEY` | 任意。組織の請求額をAPIで取る管理者キー。読み取り専用に絞れず漏洩時の影響が大きいため、当面は置かない方針（レポートの数字と各社ダッシュボードを手で見比べる） |
| `ELEVENLABS_API_KEY` | 任意。使用文字数の取得。本文Lambdaと同じ値を設定済みだが `user_read` 権限が無く401になる。権限付きのキーに差し替えると取得できる |

### 確認と見直しの目安

- 2026-09-12に `{"month":"2026-08","send":false}` で8月分（利用者8人、合計81.77円、実費$0.27）を生成し、9-13にメール送信を確認。2026-09の為替行は154.04円（Frankfurter 2026-09-11）。8月以前は為替行が無く150円固定で記録されている。
- 差分が20%を超えて印が付いたら、まず単価行の単位・値を疑う（トークン種別の違い、キャッシュ料金、音声トークン換算など）。
- 「単価行なしの警告」が出たら `toytalker-api-unit-prices` に行を足す。足すまでその呼び出しは記録されない。
- 単価の自動取得はしない。各社がAPIで単価を公開しておらず、料金ページの読み取りは壊れやすいため。
- プロビジョニングプロファイル等の期限は別件（1年）。

## 11. 前払いポイント制の仕様（2026-09-13 合意、段階1は RnD deploy済み）

第5節の方針（従量課金・前払いポイント・マージン2.0が売価）を実装できる粒度に落としたもの。前提は「ログインはCognito（Apple / Google / LINE）、決済はStripe Checkout、購入はWebページ」。認証の設計は [先送り項目](deferred-items.md) の「ユーザー認証」を参照。

### 11.1 決めたこと

**原則（2026-10-31）: 運営側が損をする状況を作らない。** 原価が売上を上回る使われ方（未払い、無料で使い続けられる、無料で配ったポイントの原価が回収されない）は仕組みで塞ぐ。ビジネスとして続けるための前提で、下の表や 11.7 の決めごとはこれに合わせる。

| 項目 | 決定 |
|---|---|
| ポイントの単位 | 円。1ポイント=1円で、購入額がそのまま残高になる。表示も「残り 1,230円分」のように円で出す |
| 消費額 | 記録している請求額（マージン2.0後の円）をそのまま引く。単価表・為替・マージンの仕組みは変えない |
| 消費のタイミング | 会話は本文Lambda（App / ESP32）がターン終了時に `cost_total` を引く。読み上げも同様。相槌は引かない（マージンで吸収） |
| 無料枠・特典 | **配らない（2026-11-01）**。本体の登録特典も特典コードも作らない。仕組みが増えると穴（偽の本体や大量のアカウントで集める）ができ、小さな運営では効果に見合わないので、費用を下げる工夫とサービスの品質に力を使う。お詫びやキャンペーンでポイントを渡すときは、運用者が `adjust` で手で足す。旧案（本体1台に300円分、アプリだけの利用者に100円分）は採らない。本体を買った人は残高0から始まるので、初めて話すまでの流れ（セットアップの途中で購入へ案内するなど）は段階3で考える |
| 払い方 | **前払い ＋ オートチャージ（使うかは親が選ぶ）**（2026-11-01）。基本はポイントを買う形。オートチャージを選んだ家庭は、残高が決めた額を下回ったら保存したカードで決めた額を買い足す（例: 100円を下回ったら500円）。毎月決まった日に買う形にはしない（使わない月に請求が来て、使われない残高も増えるため）。自動で買い足す額には月の上限を付け、親が選ぶ（初期値は月3,000円）。上限に達したら、その月はもう自動で買い足さずに知らせる。後払いと月額の定額は採らない（11.7） |
| 残高0のとき | **会話を止めて親に知らせる**（2026-11-01。旧案の「無料継続モード」（ずんだもん固定で1日50ターン）は原則に反するので採らない）。会話の始めに残高を見て、0以下なら本体が一言伝えて（例:「ポイントがなくなったよ。おうちのひとにきいてね」）その会話を始めない。アプリには表示とプッシュで知らせる。オートチャージが失敗した（カードの期限切れなど）ときも同じで、運営は損をしない |
| 購入 | Webの購入ページ（`toytalk.zakicorp.com/buy`）でログイン後、500 / 1,000 / 3,000円から選ぶ。Stripe Checkoutへ遷移し、カード・Apple Pay・Google Pay・Linkが使える。オートチャージの申し込み（カードの保存、買い足す条件と額、月の上限）と止める操作も同じWebページで行う |
| iOSアプリ | 残高と消費内訳の表示のみ。購入導線はアプリ内課金ルールに触れないよう、Webページの案内にとどめる（スマホ新法の運用が固まったら外部リンクを検討） |
| 通知 | 残高が100円を下回ったら1日1回プッシュ（オートチャージの家庭は不要）。残高0で止めたとき、購入完了時、オートチャージで買い足したとき・失敗したとき・月の上限に達したときにプッシュ |
| 返金・調整 | 手動。運用者がレジャー（台帳）に調整行を書く |

### 11.2 データ

- **`toytalker-wallets`**（残高の要約、`owner_id` がキー）: `balance_jpy`、`updated_at`。段階4で `low_balance_notified_date` を足す。オートチャージの設定（買い足す条件と額、月の上限、今月自動で買った額、Stripe の顧客ID）の置き場所は段階3で決める（財布は本文Lambdaが毎ターン書くので、設定を書ける権限を本文Lambdaに渡さない）。
- **`toytalker-wallet-ledger`**（追記だけの台帳、`owner_id` ＋ `timestamp#type#id` がキー）: `type`（`purchase` / `consume` / `adjust`）、`amount_jpy`（消費はマイナス）、`ref`、`memo`。キーの `id` は `consume` なら `device_id`、`purchase` なら Stripe のセッションID。`grant`（特典）は特典をやめたので使わない。
- **`adjust`**（運用者の手作業の調整。返金・お詫び・検証用など）: 1回の調整につき1行を足し、`memo` に理由、`by` に書いた人を入れる。書いた行は直さず、間違えたら逆向きの `adjust` を足して打ち消す。書く手段はまだ無い（コードにあるのは `recordConsume` だけ）。使うときに `recordConsume` と同じ形（台帳の行と残高の加算を1回の書き込みで）の関数と、運用者が手元から呼ぶスクリプトを作る。日次詳細は `consume` の行だけを拾うので、`adjust` の行が増えても表示は崩れない。
- `consume` の行は1ターンの原価の正本（11.6）: `ref`（chat-logs の並べ替えキー `session_id#…#timestamp#…`。返答の行と同じ時刻）、`session_id`、`source`（`app` / `esp` / `tts`）、`cost_usd`（マージン前）、`cost_stt` `cost_llm` `cost_tts` `cost_tool`、`stt_chars`、`llm_provider` `llm_model` `llm_tokens_in` `llm_tokens_out`、`tts_provider` `tts_chars` `tts_fallback`、`tool_usage`、`character_id`。文章は持たない。読み上げ（`source: tts`）は `ref` 無し。
- 台帳の行と残高の加算は1つのトランザクションで書く（`backend/shared/wallet.mjs`）。台帳の行は「まだ無ければ」の条件付きなので二重に引かない。片方だけ残ることも無いので、`balance_after` は持たない（必要なら台帳を足し上げる）。
- 権限: 本文Lambda 2本と読み上げLambdaは、台帳に PutItem、財布に UpdateItem だけ（台帳を読む・消すことはできない）。設定Lambdaは両方を GetItem・Query で読むだけ。

### 11.3 流れ

1. **付与**: しない（特典は配らない、11.1）。運用者が渡すときは `adjust`。
2. **消費**: 本文Lambdaがターン終了時、既存のコスト計算のあとに `cost_total` を残高から引き、台帳に `consume` を書く。読み上げLambdaも同じ。そのターンで残高が負になっても最後まで返す（止めるのは次の会話の始め）。オートチャージの家庭で残高が条件を下回ったら買い足す（段階3。Stripe の鍵を本文Lambdaに持たせず、別のLambdaで引く案）。
3. **残高確認**: 本文Lambdaはターン開始時に残高を読む。0以下なら停止の文言を返して始めない（段階2）。
4. **購入**: Web購入ページで金額を選ぶ → デバイス設定Lambdaが `owner_id` をメタデータに付けたStripe Checkoutセッションを作って返す → 支払い完了のWebhook（`checkout.session.completed`）をLambdaが受け、セッションIDが台帳に無ければ `purchase` を書いて残高に足す（同じWebhookが二重に来ても1回だけ処理）→ プッシュ通知。
5. **表示**: アプリの利用状況ページに残高と「今月の消費」を出す。消費内訳は既存の集計をそのまま使う。

### 11.4 認証との関係

- 購入ページで「誰の残高に足すか」を決めるには本人確認が要るので、**購入機能は認証（Cognito）の後**に出す。順番は「認証 → ウォレットと消費記録 → 購入ページ → プッシュ」。
- 認証前でも、付与と消費と残高表示は `owner_id` 単位で先に動かせる。無料枠だけで運用する期間になる。
- 認証導入時に `sub → owner_id` の対応表を作る方針なので、残高は `owner_id` のまま持ち続けられる。

### 11.5 手数料と最低購入額

- Stripeは国内カード3.6%、固定費なし。500円の購入で18円。PayPalは3.6%＋40円、Squareは3.25%〜で、カード決済はどこも3〜4%。App Store課金は15〜30%。
- 手数料と原価を引いた粗利を保つため、購入単位は500円以上にする。

### 11.6 会話ログと原価の分離（2026-10-30 方針、着手時に改めて合意する）

- **いま**: `toytalker-usage` は日 × 機器 × 種類の合計（文章なし）。一方 `toytalker-chat-logs` の返答の行に、会話の文章と一緒に1ターンの原価（`cost_llm` `cost_tts` `cost_stt` `cost_tool` `cost_total`、トークン数、文字数）が入っている。利用状況の「日次詳細（会話ごとのコスト）」はこの行から金額と文章を同時に読む。
- **困ること**: ロードマップ7の会話保護とぶつかる。`chat-logs` に保持期間（TTL）を付けると原価も消える、運用者に「コストは見えるが会話は読めない」権限を作れない、CMK で読める人を絞るとコストの集計も絞られる。
- **方針**: 1ターンの原価は台帳 `toytalker-wallet-ledger` の `consume` 行（文章なし、`ref` に会話ログのキー）と `usage` の合計に持ち、`chat-logs` からコストの列（`cost_*`、トークン数、文字数、`tool_usage`、`tts_fallback`）を外して文章だけにする。「日次詳細」は台帳から金額、`chat-logs` から文章を引く。台帳にあって `chat-logs` に無いターン（保持期間で文章だけ消えた）は文章なしで金額だけ出す。
- **決めたこと（2026-10-31）**: (a) 段階1で分離と台帳と残高の引き落としを一緒に出す（11.8）。(b) 過去分のコスト列（RnD の 3,903行）は台帳へ移さない。日次詳細は台帳に行が無ければ `chat-logs` のコスト列を読む（それも無い2026-09以前の行は計算し直す）。会話保護（CMK・TTL）を入れるのは新しい本番アカウントで、そこは最初から分離した形で始まるので、RnD の旧行が残っていても困らない。(c) ESP32 も App と同じ形にする。
- **日付は日本時間で区切る**（2026-11-01）: `usage` の日付（並べ替えキーの先頭）と「日次詳細」の1日は日本時間（`backend/shared/jst.mjs`）。`chat-logs`・台帳の `timestamp` は UTC のまま持ち、日次詳細は日本時間の1日を UTC の範囲にして引く。それより前の `usage` の行は UTC の日付のまま（移さない）。為替の月は従来どおり UTC。

### 11.7 未決定・確認事項

- **財布が1人に2つある**（2026-11-01に気づき、同日 RnD のテーブルで確認。段階2の前に直す）: 開発者のアプリ（Google ログイン、`sub 8784…`）は users で `u_284b…` に向いているが、ESP32 試験機（`90:da:72:49:ba:e5`）は認証の導入前にアプリから登録したので、ログイン前の端末の仮の ID `u_584a…` のもの。`u_584a…` には本体5台・キャラクター10体・ボイス11個・会話3,512行・利用額248行、`u_284b…`（2026-10-29 の初回ログインで発行）にはキャラクター1体・会話124行・利用額13行がある。ESP の利用がアプリの残高に出ないのはこのため。アプリの1ターンが `u_584a…` に入っていたのはログアウト中と推測（未確認）。**直し方（決定）**: users の `sub 8784…` の行の `owner_id` を `u_584a…` に書き換える（[利用者認証](auth.md) の救済と同じ。1行の書き換えで、戻すときは書き直すだけ）。`u_284b…` の会話と利用額は残るがアプリから見えなくなる。キャラクター1体は要るなら `owner_id` を書き換えて移す。財布の残高は移さず、マイナスは段階2を出すときに検証用の `adjust` で足す（下の「段階1で溜まったマイナス」）。本番は最初からログイン必須なので起きない
- **残高0のとき（決定 2026-11-01、11.1）**: 止めて親に知らせる。旧案の無料継続モード（ずんだもん固定で1日50ターン）は、1ターンの原価がマージン前で約0.35円なので1人最大で月約500円を運営がまるごと負担し、原則に反するため採らない。
- **登録特典はやめる**（2026-11-01。2026-10-31 の「本体1台につき1回」から変更、11.1）。理由は [先送り項目](deferred-items.md) の「登録特典・特典コード」。
- **残高のチェック**: 会話の始めに残高を読み、0以下なら始めない。0をまたいだ最後の1ターンのマイナス（約1円）は許す。後払いは未払いの危険があるので、原則からは前払い（+ オートチャージ）が合う。
- **払い方（決定 2026-11-01、11.1）**: 前払い ＋ オートチャージ（使うかは親が選ぶ。残高が決めた額を下回ったら買い足す。月の上限は親が選び、初期値は月3,000円）。理由: 親が気にするのは (1) 思わぬ高額請求が来ない、(2) 損をしない（ポイントが消えない・使わない月に払わない）、(3) 手間が少ない、の3つと見ている（推測。いまの利用者、特に子どもがいる家庭に聞いて確かめる）。前払いは (1) を満たし、オートチャージで (3) が後払い並みになり、残高が減ったときにだけ買うので (2) の「使わない月に払わない」も満たす。
  | | 前払い ＋ オートチャージ（採用） | 月末の後払い（従量） | 月額の定額（ポケとも型） |
  |---|---|---|---|
  | 高額請求の心配 | 無い（月の上限まで） | 月の上限設定が必須 | 無い |
  | 損をしない | 期限しだい | 使った分だけ | 使わない月も払う |
  | 手間 | 申し込めば何もしない | 何もしない | 何もしない |
  | 未払いの危険 | 無い（失敗したら残高0で止まる） | ある（原価が先に出ていく） | 小さい |
  | 資金決済法 | 対象（下の期限の項） | 対象外 | 対象外 |
  | 資金繰り | 先に入る | 後から入る | 毎月入る |

  後払いは「運営が損をしない」原則に反し、ロードマップ8の「費用の天井はポイント制で作る」も無くなる。定額は使い込まれるほど赤字になる（第7節と同じ理由）。段階3の実装前に確かめること（記憶で書いていて未確認）: (a) 日本のネットのカード決済は 3-D セキュアが必須になったので、カードを保存するときに本人認証が要る。その後の自動の引き落としは Stripe の off-session（保存したカードで、本人がその場にいないときに引く）で扱えるか。(b) 特定商取引法の最終確認画面に、自動で買い足す条件・額・月の上限・止め方を出す必要があるか。
- **ポイントの有効期限**（2026-10-31、段階3の前に決める）。自社のサービスだけに使う前払いのポイントは資金決済法の「自家型前払式支払手段」に当たり、期限が6か月以内なら対象外、6か月超・無期限なら対象だが、届出（と未使用残高の半分以上の供託）が要るのは基準日（3月末・9月末）の未使用残高が1,000万円を超えたときだけ（財務局の案内と解説サイトで確認。条文は未確認）。6か月は子ども向けのおもちゃでは印象が悪いので外す。案は3つ:
  - 無期限: いちばん安心で作りも単純。使われない残高（前受金）がずっと残る。後から期限を付けるのは利用者に不利な変更になる。
  - 購入から1年（Anthropic・OpenAI の API クレジットと同じ）: 購入ごとに期限を持ち、古い購入分から使う。毎月500円買って使い切っていれば何も消えず、消えるのは1年経っても使い残した分だけ。
  - **最後に使った（買った）日から1年（おすすめ）**: 使っている家庭では消えず、1年放置した財布だけが失効する。財布に最終利用日を1つ持つだけで作れる。
  - どれでも、月次レポートに全員の残高の合計を出し、3月末・9月末の値を見えるようにする。
- **段階1で溜まったマイナス**（2026-11-01）: 0にきっちり戻さず、段階2を出すときに検証用として `adjust` でポイントを足す（使う財布は、直した後の `u_584a…` だけ）。

- 残高0で止めるときの本体の文言と、アプリでの見せ方（段階2）。
- 本体1台あたりの無料枠（300円分）を本体価格にどう含めるか。

- 返金の運用ルール（未使用分のみ返すか）。
- グループとメンバーの招待（[先送り項目](deferred-items.md)）との関係（2026-10-31）: ポイントはグループ（`owner_id`）に付くので、メンバーが増えても同じ財布を複数人で使うだけ。ただし `purchase` の行に買った人のユーザー ID（`sub`）を書いておく（メンバーが増えてから後で足せないため）。
