## 引き継いだ状態

v0.7の作成時はv0.6のスケッチと4つのヘッダーを独立したファイルとして複製した。Arduino IDEの個人設定はコピーしていない。v0.7からv0.6のヘッダーを参照しないので、AEC開発でv0.6の動作が変わることを避けられる。

- `VOICE_BARGE_DETECT_ONLY=true`。AEC未使用・初期化失敗時の生マイクは音量検出ログのみで、自動停止しない。AECの停止設定は別の `AEC_BARGE_DETECT_ONLY`。
- 生マイク比較用のRMS閾値3,200、保持120ms、ウォームアップ500msを継承。AEC処理後の判定には別の閾値・保持時間を使う。
- `VoiceRxTestMode::MonitorResetEachTurn`。再生中もマイクを動かし、再生後にRXを解放、次の録音で再確保する。
- TTSセグメント間400ms、受信処理、音量・メモリ・切替時間の計測、ボタン割り込みを継承。
- 現時点の起動表示は `ToyTalker Mini v0.7 (AEC barge-in trial)`。初期化に成功した場合だけ `[AEC] ready=1` が出る。

v0.6の10ターン連続会話、音量方式での検出→録音復帰69ms / 36ms、再生音による誤停止等は [v0.6の実機記録](esp32-v06-voice-barge-in.md) にある。これらはv0.7やAECを実機確認した結果ではない。

## 今回の実装

`AecMonitor.h` の `AEC_ENABLED=true`。Espressifの `AEC_MODE_FD_LOW_COST` / NLP `NORMAL` / filter length 4を使用する。モデル用パーティションは追加していない。AEC後のRMSを自動停止の条件に使う。AEC後の音声をSonioxへ送る実装や、停止前の発声を録音へ引き継ぐ実装はまだない。停止後は通常STTに戻り、ボタンでの停止も継続する。

### 再生参照とI2S

v0.7のみ `driver/i2s.h` のlegacy APIから、同じインストール済みコアの `driver/i2s_std.h` へ変更した。新旧ドライバは混在させない。ネットワーク到着時やDMAコピー時のPCMではなく、TXの `on_sent` callbackで、送信を終えたDMAバッファを取り出すための変更。

- マイク: I2S0、16kHz、32bit、左slot、RX DMA 4×512。再生後のRX解放・次回STTでの再確保を継続。
- 再生: I2S1、24kHz、stereo 16bit、TX DMA 8×1023。従来の実サイズ4092 bytesを明示した。ピン、再生音量、区切り400msは継承。
- TXは `auto_clear_after_cb=true` / `auto_clear_before_cb=false`。ゲイン・クリップ後の送信波形をクリア前に取得し、再生データが来ない区間はクリアされた無音も取得する。相槌・本文・区切り無音・末尾flushが同じ経路になる。
- RXの `on_recv` とTXの `on_sent` でDMA完了時刻を記録。これはデジタル転送の完了時刻であり、スピーカーの音響遅延を直接測っているわけではない。
- 従来の `[DMA_TAIL]` は新APIのDMAサイズ・キュー溢れカウンターへ接続した。ドライバ変更後の実機での終了時間は再確認する。

### 参照の整列と評価

参照には24kHzの25タップローパスフィルター（7kHz cutoff）をかけてから、16kHzのマイク時刻へ線形補間する。フィルターの0.5msの群遅延を参照時刻に反映する。DMAサンプル数に沿った時計を使い、IRQ時刻の揺れへ毎フレーム追従せず、小さく補正する。連番欠落や3msを超える時刻差は不連続として扱う。

`AEC_REFERENCE_ADVANCE_MS=16` は、参照をマイクより先の時刻から与えてAECフィルターに因果的な余裕を持たせる試験値。物理的なエコー遅延の実測値ではない。必要な最後の参照サンプル（補間相手を含む）が到着したら、512 samples / 32msのマイクフレームを処理する。未到着なら最大96ms待つ。処理前に全512サンプルを検証し、参照が不足・欠落・上書き済みならそのフレームを評価せず、連続音量窓も切る。参照不足を無音として成功扱いにはしない。

初版は一律96ms待っていたが、01:36の実機結果を受けて到着時点で処理できるよう変更した。起動ログは `max_ref_wait_ms=96`。実際の待ち時間はDMA完了・参照時刻・タスク実行タイミングに依存する。最初の非ゼロTX波形が届く前は検出が未有効なのでAEC演算を省き、接続・受信へCPU時間を残す。**再生終了→STT再開時は保留音声を捨て、その消化を待たない。** 処理中の1フレームとタスク停止通知を待つ時間は残る。未処理の末尾はサマリに含まれず、`held_discarded` に保留枚数を出す。

マイクはSPH0645のDCを除去して16bitへ飽和変換する。v0.6の20msごとの分散RMSと厳密に同じ尺度ではない。AEC用の持続値は32ms×4枚=128msの窓で、v0.6の120ms値からそのまま閾値を移さない。各ターンの参照履歴・時計・音量統計は初期化し、最初の再生音から500msは統計のウォームアップにする。AEC本体は従来起動時に一度確保して再利用していたが、18:26の結果を受け、現在は `AEC_RESET_EACH_TURN=true` で2ターン目以降に本体だけを破棄・再作成する比較版。初回は起動時の未使用インスタンスを使う。小さな受渡しキュー・参照履歴・PCM作業バッファは再利用する。

### メモリと失敗時

インストール済みSDKは `CONFIG_I2S_ISR_IRAM_SAFE=1`。ISRの小さな受渡しキューは内部SRAMに置き、履歴・遅延マイク音声はPSRAMに置く。ISR内でPSRAM、音声処理、ヒープ確保、ログ出力へ触れない。ISRとタスクの共有カウンターは短いESP-IDF critical sectionで保護し、データのコピー中はロックしない。このツールチェーンの `std::atomic<uint32_t>` は常時lock-freeではないため、ISRでは使わない。

AECの状態領域はPSRAMを指定し、APIへ渡す3つの512-sampleバッファは16-byte境界の内部RAM。監視タスクのスタックは4KB→8KB。ISR受渡しを含む `aecMonitor` は約8.4KBの静的内部RAMを使用する。静的RAMのビルド表示と、AEC内部の実行時確保・TLS等の動的確保は別々に評価する。

AEC初期化やバッファ確保に失敗した場合は確保分を解放し、音量計測だけへ戻る。その場合も自動停止はOFF。再生タスクの確保失敗も検出し、リングを使用せず直接再生へ戻る。TLSアロケーターは計測版ではコア標準だったが、01:20の接続失敗を受け、現在は以下のPSRAM固定に変更した。

### TLS作業メモリのPSRAM移行

`TlsMemory.h` の `TLS_PSRAM_ENABLED=true`。起動時、WiFi接続・HTTPS・WSS・AEC初期化より前に一度だけ `mbedtls_platform_set_calloc_free()` を設定し、mbedTLSのcallocを `MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT` へ固定する。Lambda・Soniox・相槌HTTPSに共通で効く。設定は接続中に変更せず、PSRAM確保失敗時に内部RAMへは戻さない。サイズの乗算オーバーフローを拒否し、freeは元の内部RAM割り当ても扱える `heap_caps_free()` を使う。DMA・ISR・タスクスタックの確保先は変更していない。

Arduino 3.3.11 / IDF 5.5.5のローカルSDKで `CONFIG_MBEDTLS_INTERNAL_MEM_ALLOC=1`、`MBEDTLS_PLATFORM_MEMORY`、実行時アロケーター設定APIを確認した。[Espressifの実装](https://github.com/espressif/esp-idf/blob/v5.5.5/components/mbedtls/port/esp_mem.c) も、内部RAM指定とPSRAM指定のcallocを別の構成として持つ。スケッチ内でSDK設定マクロを書き換える方式は使わない。

起動時にmbedTLS公開callocで20,000 bytesを確保し、外部RAMであることと全ゼロを検査して解放する。`[TLS_MEM] allocator=psram ready=1 ... external=1 zeroed=1` が成功ログ。PSRAMがない・API設定失敗・プローブ不一致なら、アンプOFFでネットワーク接続前に起動を止める。`[BUILD] arduino=... idf=...` も記録する。

`[TLS_MEM]` の `calls / fail / largest_req` は起動プローブを含む累積確保呼び出し数・失敗数・最大要求。現在の使用バイト数ではない。`psram_free / psram_max_blk` と内部RAMの `[HEAP_CHECK]` を同じ接続段階で比較する。前回よりRAMが減っただけでリークと断定しない。音声リングとAECとTLSがPSRAMを共有するので、実機で連続会話・接続時間・音切れ・AECの欠落も確認する。

APIの出発点は [Espressif公式AEC](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/acoustic_echo_cancellation/README.html)。手元のSDKには `esp_aec.h` と `libespressif__esp-sr.a` があり、`aec_create_from_config` / `aec_get_chunksize` / `aec_process` / `aec_destroy` をモデル領域なしで単体リンクできた。実装ではローカルのAPI仕様を確認する。Arduino IDE、Flash 4MB、QSPI PSRAM 2MBを維持し、ESP-IDFやPlatformIOへの移行は行わない。

DMA callbackとauto-clearの順序は [ESP-IDF v5.5.4のI2S実装](https://github.com/espressif/esp-idf/blob/v5.5.4/components/esp_driver_i2s/i2s_common.c) も確認した。

## 現在の音声介入試験

`AecBargeGate.h` の `AEC_BARGE_DETECT_ONLY=false` で自動停止を試す。判定はAEC出力のRMSが1,200以上で、512 samples × 4フレーム = 128ms連続すること。最初の実際の再生音（相槌を含む）から500msは判定しない。閾値は交互試験の再生のみ789〜832と介入あり1,660〜1,720の間に置く仮の値で、初回の弱い介入1,123を検出できる設定ではない。

同じ候補4フレームの入力・出力エネルギーを比較し、AEC出力のRMSがマイク入力の25%以上残っていることも条件にする。1フレームだけの比率や、別時刻のターン最大値は比較しない。比率で却下した後も窓を更新するので、後から声を重ねれば再び候補になる。これは無発声での誤検出を受けた試験値であり、人の声を識別する機能ではない。再生音に埋もれた小さな声も却下する可能性がある。

入力変換で飽和したフレーム、未ウォームアップ、評価時点で音声が200msより古い場合は候補をリセットする。飽和後は新鮮で飽和のない8フレーム（256ms分）を評価対象から外し、その後に128msの候補を新しく作る。参照不足・マイクの不連続で候補を切っても、この保護は消さない。再度の飽和で保護を延長し、次ターン開始で全状態をリセットする。通常の声で飽和しなければ、この待ちは追加されない。1ターン1回だけ発火する。飽和しない接触音や再生音の残りで誤停止する可能性は残る。

発火時は監視タスクでアンプをOFFにしてから既存の割り込みフラグを立て、captureを止める。ソケット・再生タスク・I2Sドライバの終了は従来のボタン割り込みと共通の処理で行い、通常STTへ復帰する。AEC初期化失敗時は生マイクの計測のみとなり、自動停止しない。

1. v0.7を書き込み、`[AEC] ready=1` と `detect_only=0 barge_rms=1200 barge_hold_ms=128 min_retained_pct=25 clip_recovery_ms=256` を確認する。
2. 端末を置いたまま触らず、返答中は黙って10〜20ターン続ける。今回の誤検出は16ターン目なので、初回だけで判断しない。
3. 次の返答の途中に「ちょっと待って、こんにちは」など声を重ね、止まった後も続けて話す。停止前の音声はSTTに引き継がないため、話し始めの欠けと停止後の認識を分けて確認する。
4. 再生のみ・介入ありを交互に3〜5回試し、誤停止・取りこぼし・2回目以降の遅延を確認する。ボタンで戻れることも確認する。

`[AEC_TRIGGER]` に発火フレームの `mic/ref/out` と `audio_age_ms`、`[VOICE] trigger_to_record_ms` に発火→録音ON、`trigger_to_first_send_ms` に発火→最初の音声送信成功を出す。`audio_age_ms` は判定に使った最後のマイクフレーム終端から判定までの時間であり、発声開始からの時間ではない。128msの保持・参照の到着待ち・AEC演算があるため、発火後の復帰時間だけを応答全体の遅延としない。Soniox再接続待ちは初回送信の時間に含まれる。

追加の `[AEC_GATE]` は比率で却下した候補窓数 `residual_reject_windows`、飽和フレーム数 `clip_frames`、保護したフレーム数 `recovery_frames` を出す。停止時は `[AEC_TRIGGER] window_retained_pct` と、直前4フレームの `[AEC_GATE_FRAME] index=0..3 mic=... out=...` を確認する。4フレームの詳細は録音の最初の送信後にまとめて出す。停止・録音切替の前にログ出力を増やさないため。

計測へ戻す場合は `AEC_BARGE_DETECT_ONLY=true` で再ビルドする。ボタン割り込みとAEC前後の計測は残る。

## 計測モードでの実機試験（自動停止OFF）

以下は `AEC_BARGE_DETECT_ONLY=true` で、最後まで再生させて比較する手順。

1. v0.7を書き込み、起動ログの `[AEC] ready=1` と `[AEC_MEM]` を確認する。`init failed` や音量計測だけの表示ならAECは動いていない。
2. 再生中は黙って、2〜3ターン会話する。声による停止が起きないこと、再生速度・音切れ・録音復帰に問題がないことを確認する。
3. 次の返答の途中に声を重ねる。今回も声で止まらないのが正常。その後、ボタンで停止して通常STTへ戻れることを確認する。
4. 黙っていた回・声を重ねた回それぞれの `[AEC_LEVEL]` / `[AEC_STATS]` と、発声中の `[AEC]` 行を残す。終了サマリは次のSTT音声の最初の送信成功後に出る。Soniox再接続中は遅れる。
5. 有効な比較が取れたら10ターン以上の会話でメモリ・音切れ・切替時間を確認する。新しいI2S構成の安定性はv0.6の10ターン結果だけでは保証しない。

| ログ | 意味 |
| --- | --- |
| `[AEC] mic / ref / out` | 同じ処理フレームのマイク入力・参照・AEC出力RMS。`mic_max / out_max` は直前約1秒の最大値 |
| `reduction_db` | 参照音がある有効フレームでの入出力エネルギー比。大きいほど出力が小さい。条件がなければ `nan`。音響測定のERLEや音源識別の証明ではない |
| `[AEC_LEVEL] mic_sustained / out_sustained` | 有効・ウォームアップ後の128ms持続値。再生のみと声ありで、処理後の値が分かれるか比較する |
| `paired / missing` | 処理できたフレーム / 参照不足で除外したフレーム。開始境界で少数のmissingはあり得るが、継続的に増える場合は整列を調べる |
| `mic_drop / ref_drop / pending_drop` | 受渡し・保留領域の溢れ。音声処理が追いついているかの手掛かり |
| `clock_resets / format_errors` | サンプル連続性の喪失 / 想定と異なるDMA形式 |
| `clips` | 評価に使ったマイク入力の16bit飽和サンプル数 |
| `cpu_max_us / slow_frames` | 1フレームの整列・AEC・集計にかかった最大時間 / 32msを超えた回数。ISRコピーと参照フィルター等を含む全CPU使用率ではない |

再生のみで出力が下がることに加え、人の声が残るか、欠落で評価区間が減っていないか、通常会話が安定するかを確認する。自動停止の実験と、安定版への採用判断は分ける。

## 初回の実機結果（2026-09-10 00:36〜00:37）

ユーザー提供の `スクリーンショット 2026-09-10 003635.png` / `003710.png` / `003748.png` の順でgeneration 1 / 2 / 3を確認した。3回目はユーザーが「介入あり」と明示。1・2回目は直前の試験手順に沿った再生のみの回として比較する。起動時の `[AEC_MEM]` は今回の画像に含まれないが、`paired` と処理後の値があり、AEC処理の実行は確認できる。

## 無発声での誤検出への対策（2026-09-10、13:19ログへの補足）

保存コミット `dd77e42` の後、ユーザーが「俺何も話してない」と補足。この停止は意図した声による介入ではなく誤検出として扱う。再生音の残り・接触音・マイク入力の乱れのどれかは、引き続き音声データなしでは特定できない。

発火フレームは `mic=5822 out=1304`（約22.4%）で、強く抑制された出力でも絶対閾値1,200を超えると止まる実装だった。また、ターンの `clips=318` に対し、従来は飽和した当該フレームを除外するだけで、その後の保護期間がなかった。この二点に対して以下を追加した。

- 同じ128ms候補窓で、出力RMSが入力の25%以上残る条件。固定閾値を一律に上げず、強く抑制された入力の残りを却下する試み。25%は公式推奨値ではなく今回の試験値。AEC前後の同時刻窓を比較しても、AEC内部遅延や声と再生音の混合を分離測定できるわけではない。
- 飽和後256ms分の新鮮な非飽和音声で保護。128msの連続判定はその後に始める。声でも飽和すれば反応が遅れるため、近距離・大声の試験も必要。これはAECの回復時間を測定した値ではない。
- 発火した4フレームと、却下・保護の件数を記録。ターン全体の最大値やクリップ数から、発火の直前も同じ状態だったと推定しない。

既存のRMS 1,200 / 128ms、AEC演算・マイク変換・再生・STT・Sonioxの処理は維持する。固定長の小さな窓だけを追加し、動的確保や新しい待機処理は追加しない。NLPを強くする変更は今回は行わない。[EspressifのNLP説明](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/acoustic_echo_cancellation/README.html#nlp-level-description) も、強い抑制で近端音声に影響する可能性を示している。

試験では①返答中は黙って10〜20ターン、②通常距離の声で介入を交互に確認する。誤停止があれば `[AEC_TRIGGER]`、`[AEC_GATE_FRAME]`、`[AEC_GATE]` を確認し、反応しなくなった場合は `[AEC_LEVEL]` と `[AEC_GATE]` を見る。画像に実際の候補4フレームはないため、今回の変更で当時の停止を必ず防げるとはまだ言えない。

## 状態持越しの切り分け（2026-09-10 18:26）

誤検出保護版についてユーザーから「めちゃくちゃいい感じ」だが、最後に自分の再生音で割り込んだかもしれない、AECが徐々にずれることはないか、との報告。`スクリーンショット 2026-09-10 182613.png` のgeneration 7は以下の状態だった。発火時に無発声かつ非接触だったかは未確認で、音源の断定はしない。

- `[AEC_TRIGGER] mic=1415 ref=917 out=4527 audio_age_ms=84 window_retained_pct=91.6`、`cause=aec_level`。今回もAECのゲートが直接の停止理由。
- 発火直前4フレームは、古い順に `mic/out=3167/1348, 6786/2819, 4827/6164, 1415/4527`。後半は出力が入力より大きいが、AEC内部の時間遅れも含む値なので、これだけで増幅・発散・同期ずれと断定しない。
- `residual_reject_windows=0 clip_frames=0 recovery_frames=0`。今回の窓は91.6%残っており、25%の比率条件で却下する対象ではない。入力飽和もなく、前回の保護だけではこの候補を防げない。
- `paired=106 missing=0 mic_drop=0 ref_drop=0 pending_drop=0 clock_resets=0 format_errors=0 clips=0 slow_frames=0 cpu_max_us=23376`。大きな欠落や時計の不連続は記録されていない。`clock_resets=0` は小さな時間ずれや、実際の音響経路と参照のずれを否定するものではない。
- `underruns=0 ws_max_block_ms=26`、`trigger_to_record_ms=30 trigger_to_first_send_ms=63`。`ALLOC_FAIL total=0` / `TLS_MEM fail=0`。通信・再生の詰まりによる停止を示すログではない。

コード上、時計・参照履歴・マイクDCは毎ターン初期化している一方、AEC本体の学習済みフィルターと内部の音声履歴は持ち越していた。録音中はAECに音声を渡さず、マイク/再生I2Sもターン間で作り直すため、次ターンを連続した同じ音声列として扱う状態持越しが影響する可能性がある。これは調査仮説であり、今回の原因と確定したものではない。

比較のため `AecMonitor.h` に `AEC_RESET_EACH_TURN=true` を追加。インストール済み `esp_aec.h` に公開のreset APIがないため、`aec_destroy()` → `aec_create_from_config()` で本体だけを作り直す。前の監視タスクの停止確認後、今回のcapture・監視タスクの開始前にloopが実行する。ISRは本体へ触れない。古い本体を解放してから同じ設定で確保し、2個分のAEC領域を同時には保持しない。失敗したターンは自動停止しない生マイク計測へ戻り、確保済み作業領域を保持して次のターンで再試行する。

閾値・比率・飽和後の保護・500msのウォームアップ・参照の16ms advance・NLP強度は変更しない。`[AEC_RESET] generation=... enabled=1 recreated=1 ready=1 elapsed_us=...` が2回目以降の成功ログ。1回目は `recreated=0`。作り直す所要時間は相槌再生前の準備に加わるので、`elapsed_us` と体感速度を確認する。再学習が必要になることで、ターン冒頭の抑制が弱くなる可能性もある。

同じ配置・音量で、返答中は無発声・非接触の会話を10〜20ターン、その後に声での介入を確認する。`[AEC_RESET]` と、正常終了/誤停止双方の `[AEC_LEVEL]` / `[AEC_STATS]` / `[AEC_GATE_FRAME]` を残す。`AEC_RESET_EACH_TURN=false` で再ビルドすると、直前の誤検出保護版と同じ本体持越しに戻せる。改善しなければ、マイク/参照/出力の波形を保存して遅れ・相関を測り、固定の参照ずれや再生音の変化を調べる。

## ビルドと復旧

Arduino IDEでは `devices/mcu/esp32_s3/toytalker_mini_v0.7/toytalker_mini_v0.7.ino` を開く。ESP32S3 Dev Module / Flash 4MB / QIO 80MHz / QSPI PSRAM / No FS 4MB (2MB APP x2) / USB CDC Enabledなど、実機で使っている設定を維持する。

```powershell
arduino-cli compile --fqbn esp32:esp32:esp32s3:PSRAM=enabled,FlashSize=4M,PartitionScheme=no_fs,CDCOnBoot=cdc --build-path "$env:TEMP/toytalker_v07_build" devices/mcu/esp32_s3/toytalker_mini_v0.7
```

v0.6へ戻す場合は、そのフォルダーの `toytalker_mini_v0.6.ino` を開いて同じボード設定でUSB書き込みする。現在の保存状態は計測モードなので、音量方式の自動停止を試すときは [v0.6の調整手順](esp32-v06-voice-barge-in.md#調整する定数) に従う。通常会話の安定版へ戻す場合はv0.5を使う。スケッチの切替にFlash全消去は不要。

比較用に `AecMonitor.h` の `AEC_ENABLED=false` とすれば、標準I2S APIのまま音量計測だけで再ビルドできる。音響処理を外す切り分けであり、旧ドライバと同じ条件ではない。旧ドライバへ戻すときはv0.6スケッチを使う。
