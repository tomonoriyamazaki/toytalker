## いまの状態（2026-11-17）

- **未着手**。2026-11-15 に最初の形を決め、11-16〜17 の相談で作り直した（下の「決めたこと」）。数字はコードと文書からの見積もりで、実機ではまだ何も測っていない。

- **言える範囲**: ポリシーに書けるのは「運営は保存しません」まで。文章は Lambda のメモリ上を通り、LLM・STT・TTS の事業者へ送られる。USB の対策は「ケーブルがあれば誰でも」を「測定器と専門知識がある人」まで上げるもので、絶対ではない。家の Wi-Fi が届く場所で電源を入れて話しかければ、おもちゃは覚えていることを答える（話すおもちゃである以上、残る）。
- **運営側に残るもの**（会話の中身ではないが、ゼロではない）: メールアドレス、機器の登録、キャラクター設定（`personality_prompt` に子どもの名前を書く人はいる）、クローンボイス、利用の記録（いつ何回話したか）、決済、送信元 IP。行の `chat_log` を立てれば1台だけ会話を保存できる能力も残る（調査用。ポリシーに書く）。

## 決めたこと

- **置き場所は本体。スマホには整理済みの項目だけを写す**（BLE）。Lambda は通すだけで、DynamoDB にも Lambda ログにも書かない（ログに文章を書かない規則のまま）。
- **覚え方は「全文を本体に溜めて、後で整理する」**（2026-11-17。11-15 の「会話中に LLM の道具で覚える」を置き換え）。会話の文章をフラッシュに溜め、休むとき・起動時などに未整理の分を Lambda 経由で LLM へ送り、結果（項目の足し引き）を本体に書いて、整理の済んだ全文を消す。道具で覚える形より良い点: 会話中の返事が遅くならない、道具を呼ぶかどうかの安定性に頼らない、会話の記録（いつ何を話したか）も同じ処理で作れる。
- **11-15 に却下した「休む直前にまとめて要約する」との違い**: 却下の理由は ①スイッチで急に切られると覚えない ②要約し直すたびに中身が薄まる ③保護者が1項目ずつ直せない ④LLM の呼び出しが1回増える。①は全文がフラッシュに残り次の起動で拾えるので消える。②③は結果を文章のかたまりではなく項目の足し引きにするので消える。④は受け入れる（1日分で入力 5,000〜6,000 トークン・出力数百トークン、小さめのモデルで1回1円未満の見込み。単価はモデル次第の概算）。LLM の事業者へ新しい情報が渡るわけではない（会話のときに一度送った文章を、同じ事業者へもう一度送る）。
- **全文は本体の外に出さない**（スマホにも渡さない）。保護者が BLE で見られるのは整理後の項目だけ。子どものプライバシーの線引き。「親が BLE で抜くときにスマホ側で要約する」形は取らない（抜かない家では整理されない、要約のために全文がスマホを通る）。
- **手動メモリを持つ**: 保護者がアプリで入れる（呼び名、誕生日、好み、伝言）。入れたときに BLE で本体へ書き、起動時は本体が自分の中から読む（BLE は設定のときしか動かず、スマホが近くにあるとも限らないので、起動時にスマホから読む形は取れない）。自動の整理は手動メモリを書き換えない。食い違ったら手動が優先。
- **自分から話しかける**: 起動時に「日付＋記憶」を送り、LLM に一言作らせる（誕生日などの日、保護者の伝言）。毎回話しかけるかは設定（起動のたびに LLM と TTS のポイントがかかる）。
- **スマホの写しを OS のバックアップ（iCloud・Google）に入れるかは、利用者が選ぶ**。iOS はファイル単位の除外の印、Android はバックアップされないフォルダで切り替える（Expo での置き場所は未確認）。
- **保護者が見る・消すのは BLE で、本体のボタン操作を必須にし、見ている間は音と LED で合図を出す**。離れた所からは見られず、アカウントを乗っ取った他人にも何も出ない（運営側に無いため）。子どもがいない間に本体を操作して見ることは止めない（日記帳を見るのと同じ扱い）。
- **本体をなくす・壊すと記憶も消える**。戻せるのは、スマホに写してあった整理済みの項目だけ（スマホ → 新しい本体へ BLE で書き戻す。買い替えの移し替えも同じ経路）。
- **譲渡・持ち主のリセットで消す**。
- **全文を持つ本体には Flash Encryption を入れる**（2026-11-17。11-09 の見送りは「本体に会話に関する情報が無い」が前提だった。下の「なくした本体から読まれないために」）。入れられない本体では、溜める全文を少なくする。
- **却下: 記憶を暗号化し、鍵をサーバーが持って会話の開始時に渡す**。鍵をもらうためのデバイス鍵が同じフラッシュに平文で入っているので、吸い出した人が本体になりすませば鍵を取れる。効くのは「持ち主が機器を削除した後」だけ。他人がアプリから読むのを防ぐのは持ち主の印の働きで、この鍵ではない。

## 整理の決まり（たたき台。未決定）

- ごっこ遊びや作り話は「事実」として登録しない。聞き間違いらしいものは登録しない。
- 会話の記録は話題の水準にとどめ、発言をそのまま写さない。
- 手動メモリは書き換えない。
- **未決定: 会話の記録の細かさ**。子どもが「ないしょだよ」と言った話や悩みごと（友だちとのけんかなど）を、保護者に見える記録にどこまで書くか。製品の性格を決める。Claude の案は「話題としては書くが、中身は書かない」（例:「友だちの話をした」）。

## 仕組み（案）

1. 本体が毎回の要求に、手動メモリ・自動の好み・直近の会話の記録を添える。Lambda はキャラクターの設定の後ろに足して LLM へ渡す。保存しない。
2. 本体は発話と返答をフラッシュの未整理の全文に足す。
3. 整理のタイミングで、本体が「未整理の全文＋今の項目の一覧」を整理用の入口へ送る。Lambda は LLM に項目の足し引き（足す・書き換える・消す）を作らせて返す。保存しない。
4. 本体が項目を書き換え、整理の済んだ全文を消す。
5. 起動時、設定が入なら「日付＋記憶」で一言を作らせて話す。日付はネットから取る。

アプリ経由の会話（v2）は、同じものをアプリの中に持てば足りる（未検討）。

## 持ち主が変わったとき（案、2026-11-16 相談。未決定）

BLE で読むやり取りは本体とスマホの間だけでサーバーを通らず、本体はつないできたアプリが誰のアカウントかを知らない。ログイン（Cognito）だけでは守れないので、本体に「持ち主の印」を持たせる。

1. **設定のとき**: アプリが、ログイン中の `owner_id` から作った印を本体に書く。
2. **読む・消す・書くとき**: アプリが同じ印を示し、本体は一致したときだけ応じる。印そのものを BLE に流さず、本体が出した乱数への答えで照合する（盗み聞きで印が漏れないように）。
3. **違う印で設定し直されたとき**: 本体は記憶を消してから新しい印を受け入れる。

- 新しい持ち主は自分の印が合わないので読めず、使い始める設定で前の子の記憶は消える。元の持ち主は機種変更しても同じアカウントなら同じ印で読める。拾った人は印（推測できない乱数の `owner_id` 由来）が分からない。
- **足す（2026-11-17）: BLE を流れる中身も暗号化する**。照合だけでは項目が平文で流れる。印から作った鍵で中身を暗号化する（mbedtls はファームに入っている）。
- **足す（2026-11-17）: Wi-Fi の設定し直しにも印を求め、合わなければ記憶を消す**。拾った人が自分の Wi-Fi につないで「ぼくの好きな食べ物は？」と聞く経路を塞ぐ。
- あわせて消す場面: アプリで機器を削除したとき（鍵発行の応答で本体へ伝える。本体は起動時と3分ごとに呼ぶ）、本体のボタンで持ち主をリセットしたとき（操作はロードマップ4の宿題で未決定）。
- **印の無い本体に特別な処理は作らない**（2026-11-16 決定。以前の本体はそのまま使えるようにする）。規則は2つで、新品にも以前の本体にも同じに効く: 印が無ければ最初に示された印を受け入れる。印が無い間は覚えない（印が入る前にたまった記憶を、拾った人が自分の印を入れて読むのを防ぐ）。以前の本体は会話は今まで通りで、覚える機能だけ持ち主がアプリで一度つないでから始まる。

## なくした本体から読まれないために

何か・費用・やると決めたときの設計は [先送り項目](deferred-items.md) の「Secure Boot と Flash Encryption」。追加の部品は要らない（ESP32-S3 のチップに入っている機能で、今の MINI-1 でも使える）。下の Espressif の仕様は記憶ベースなので、試すときに公式文書で確かめる。

- **Flash Encryption（USB で読む攻撃への根治）**: フラッシュの中身を、eFuse に焼いた鍵で暗号化する。鍵はソフトからも USB からも読み出せず、吸い出しても暗号文しか出ない。OTA では入らず USB での書き込みが要るので、配布済みの本体は回収しない限り対象外。
- **NVS の暗号化**: Flash Encryption は `nvs` を自動では暗号化しない。別に組まないと Wi-Fi パスワードとデバイス鍵は平文のまま。記憶を `nvs` ではなく専用の区画に置けば、記憶そのものは Flash Encryption だけで守れる。
- **Secure Boot が要る理由**: 読まれることへの対策は Flash Encryption が主で、Secure Boot は「ファームをすり替えられること」への対策。
  1. **OTA の経路（こちらが本命）**: 記憶を本体へ移すと、全台へ一度に届く経路は OTA だけになる。運営の AWS か配信元が破られて偽のファームを配られると、動いている本体の中では復号済みなので、全員分の記憶を外へ送らせることができる。クラウドから消した「全員分が一度に出る」危険が、OTA に残る。AWS の外に置いた鍵の署名を本体が確かめれば、配信元が破られても偽ファームは起動しない。今の OTA（TLS + CA 固定 + manifest の SHA）は通信路の保護で、配信元が破られた場合は守れない。
  2. **改ざんの検知**: Flash Encryption は中身を隠すが、書き換えられたことは検知しない（暗号文を古いものへ戻す、壊す）。Espressif は2つを一緒に使うことを勧めている。
- **軽い代わりの案（未検討）**: OTA の .bin に AWS の外の鍵で署名し、ファームが切り替える前に自分で確かめる。1 の危険はこれでも塞げ、eFuse とブートローダーの変更が要らない。2 は塞げない。
- **一番の不確かさ**: Arduino IDE の環境のままで Flash Encryption（と Secure Boot）を組めるか。Arduino の出来合いのブートローダーは対応していないので、ブートローダーだけ別に作って esptool で書く形が通るかを、潰してよい板1枚で先に試す。ここが通らないと「全文を本体に溜める」の前提が崩れる。

## 置き場所の大きさ

今のフラッシュは 4MB で空きが無い（`devices/mcu/esp32_s3/toytalker_mini_v0.7/partitions.csv`）。区画表は USB 書き込みでしか変わらないので、配布済みの本体で使えるのは `nvs` だけ。

| 区画 | 大きさ | 用途 |
|---|---|---|
| `nvs` | 20KB | Wi-Fi 設定、デバイス鍵、モード、OTA の状態、音量 |
| `app0` / `app1` | 1,792KB ×2 | ファーム（余裕は 15%、約 280KB） |
| `voices` | 384KB | キーホルダーモードの声（約30秒分） |
| `coredump` | 64KB | 落ちたときの記録 |

- **上限を決めるのは置き場所ではなく、毎回 LLM へ送る量**（料金と返事の遅れ）。手動メモリ・自動の好み・直近の記録を合わせて 1,000〜2,000 文字が実用。日本語は1文字3バイト。
- **配布済みの本体（`nvs` だけ）**: 使えるのは約16KB（1面 4KB を整理用に空ける）。使用中は約5KB、空きは約10KB の見込み（推定: ファームが書く分 約1KB、Wi-Fi の接続先の情報 約2KB、無線の校正データ 約2KB）。項目に 3KB ほど、全文は数往復分しか置けない。文字列（`putString`）は1項目 4,000 バイトまでで、まとめて持つなら面をまたげるバイト列（`putBytes`）。
- **新しい基板で区画を切り直す場合（4MB のまま）**: `voices` から 128KB をもらえば約4万文字。テキストだけならこれで足りる。
- **モジュールを替える場合**: 今は ESP32-S3-MINI-1-N4R2（15.4×20.5mm）。MINI-1 には「フラッシュが大きくて PSRAM もある」版が無いはずなので、ファームの枠か声が足りなくなった時点で WROOM-1 になる。候補は **WROOM-1-N16R8**（16MB。JLCPCB で MINI より +$0.4、在庫は約 7,000 → 約 20,000。2026-11-17 に利用者が確認。N16R2 は JLCPCB に無い）。変わる点（ピンは基板を直すときにデータシートで確かめる）: ボタンの GPIO35 が使えない（octal PSRAM が GPIO35〜37 を使う）、マイク DATA の GPIO34 が WROOM-1 に出ていないはず、外形 18×25.5mm・厚さ +0.7mm（外装に入るかは Fusion で当てる）、PSRAM が 2MB quad → 8MB octal（Arduino のボード設定とメモリまわりを見直す）。

## 作る前に確かめること

4. **整理に使う LLM と、実際の料金・かかる時間**。休むときの整理が終わる前に電源を切られた場合に、全文が残って次の起動でやり直せること。

6. **WROOM-1 のピンと外形**（データシート、Fusion）。

## 残る論点

- **記憶は毎回 LLM の事業者へ送られる**。プライバシーポリシーに書く（[販売の準備](sales-readiness.md) の B・C）。
- **間違いを覚える**: ごっこ遊びの話や聞き間違いが「事実」として残る。整理の決まりと、保護者が消せることで受ける。
- **本番で「変な返答をした」を調べられない**: 保護者がアプリから自分の意思で項目を送る形は作れる（全文は本体の外に出さないので、送れるのは整理後の項目まで）。全文が要る調査は、持ち主に断ったうえでの `chat_log`。
- **保護者が「今回の会話」の全文も見られるようにするか**: 上の決定では見せない。会話を見る機能そのものは [先送り項目](deferred-items.md) の「親が会話を見る機能」。
