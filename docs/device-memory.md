## いまの状態（2026-11-15）

- **未着手**。2026-11-15 の相談で形を決めた。大きさの数字はコードからの見積もりで、実機ではまだ何も測っていない。
- **前提**: 本番系は会話の文章を保存しない（[先送り項目](deferred-items.md) の「会話ログの保持期間」）。そのため「先週の話を覚えている」はサーバーには作れない。
- **同じ日の「自動のメモリは本番系では作らない」との関係**: あれは運営側（サーバー）に置く形の話。置き場所を本体の中だけにすれば運営側には何も溜まらず、「会話は保存しません」と両立する。残る「誰も残すものを選んでいない」は、保護者が本体を手に取って見て消せることで受ける。

## 決めたこと

- **置き場所は本体の `nvs` だけ**。Lambda は通すだけで、DynamoDB にも Lambda ログにも書かない（ログに文章を書かない規則のまま）。
- **覚え方は LLM の道具（「覚える」）**。会話中に出た好みなどを、返事を作る LLM がその場で項目として登録する。検索（Brave）と同じ道具呼び出しの仕組みに1つ足す。
- **却下: 休む直前にまとめて要約する**。無音3分・2回押しで休む直前に「前の要約＋今回の会話」を LLM へ送る形。スイッチで急に切られると覚えない、LLM の呼び出しが1回増える、要約し直すたびに中身が薄まる、保護者が1項目ずつ直せない。
- **保護者が見る・消すのは BLE で、本体のボタン操作を必須にし、見ている間は音と LED で合図を出す**。離れた所からは見られず、アカウントを乗っ取った他人にも何も出ない（運営側に無いため）。子どもがいない間に本体を操作して見ることは止めない（日記帳を見るのと同じ扱い。提供する機能としてはここまで）。
- **本体をなくす・壊すと記憶も消える**。バックアップはどこにも無い。性質として受け入れる。買い替えのときの移し替え（古い本体 → スマホ → 新しい本体、BLE）は要望が出たら。
- **譲渡・持ち主のリセットで消す**。

## 仕組み（案）

1. 本体が、覚えた項目の一覧を毎回の要求に添える。Lambda はキャラクターの設定の後ろに足して LLM へ渡す。
2. LLM が返事をしながら `覚える（好きな食べ物 = カレー）` を呼ぶ。
3. Lambda が応答のメタデータ枠（`sendMeta`、type 0x01。`segment` や `mark` と同じ枠）で本体へ返す。保存しない。
4. 本体が `nvs` に書く。同じ名前の項目は書き換える。
5. 間違いを直すために「忘れる」道具も持たせる。

アプリ経由の会話（v2）は、同じ項目をアプリの中に持てば足りる（未検討）。

## 持ち主が変わったとき（案、2026-11-16 相談。未決定）

BLE で読むやり取りは本体とスマホの間だけでサーバーを通らず、本体はつないできたアプリが誰のアカウントかを知らない。ログイン（Cognito）だけでは守れないので、本体に「持ち主の印」を持たせる。

1. **設定のとき**: アプリが、ログイン中の `owner_id` から作った印を本体に書く（`nvs`）。
2. **読む・消すとき**: アプリが同じ印を示し、本体は一致したときだけ応じる。印そのものを BLE に流さず、本体が出した乱数への答えで照合する形にする（盗み聞きで印が漏れないように）。
3. **違う印で設定し直されたとき**: 本体は記憶を消してから新しい印を受け入れる。

- 新しい持ち主は自分の印が合わないので読めず、使い始める設定で前の子の記憶は消える。元の持ち主は機種変更しても同じアカウントなら同じ印で読める。拾った人は印（推測できない乱数の `owner_id` 由来）が分からない。
- あわせて消す場面: アプリで機器を削除したとき（鍵発行の応答で本体へ伝える。本体は起動時と3分ごとに呼ぶ）、本体のボタンで持ち主をリセットしたとき（操作はロードマップ4の宿題で未決定）。
- **印の無い本体に特別な処理は作らない**（2026-11-16 決定。以前の本体はそのまま使えるようにする。余計な処理は増やさない）。規則は2つで、新品にも以前の本体にも同じに効く: 印が無ければ最初に示された印を受け入れる（新品の初回設定で必ず通る処理）。印が無い間は覚えない（印が入る前にたまった記憶を、拾った人が自分の印を入れて読むのを防ぐ）。以前の本体は会話は今まで通りで、覚える機能だけ持ち主がアプリで一度つないでから始まる。
- 防げないのは、分解して USB でフラッシュを直接読むこと（下の「残る論点」）。

## 置き場所の大きさ

フラッシュは 4MB で空きが無い（`devices/mcu/esp32_s3/toytalker_mini_v0.7/partitions.csv`）。区画表は USB 書き込みでしか変わらないので、配布済みの本体で使えるのは `nvs` だけ。

| 区画 | 大きさ | 用途 |
|---|---|---|
| `nvs` | 20KB | Wi-Fi 設定、デバイス鍵、モード、OTA の状態、音量 |
| `app0` / `app1` | 1,792KB ×2 | ファーム |
| `voices` | 384KB | キーホルダーモードの声 |
| `coredump` | 64KB | 落ちたときの記録 |

- `nvs` で使えるのは約16KB（1面 4KB を整理用に空ける）。**使用中は約5KB、空きは約10KB の見込み（推定）**: ファームが書く分 約1KB、Wi-Fi の部品が書く接続先の情報 約2KB、無線の校正データ 約2KB。下の2つはライブラリが自動で書くもので、大きさは概算。
- 日本語は1文字3バイト。**上限の案: 30項目・合計 3KB（約1,000文字）**。6KB は入るが、書き換えのたびに古い分と新しい分が一時的に並ぶのできつい。
- 文字列（`putString`）は1つの面に連続して収める必要があり、1項目 4,000 バイトまで。まとめて持つなら面をまたげるバイト列（`putBytes`）にする。
- 会話の全文は入らない。置くなら `voices` を削るしかなく（64KB で約21,000文字、声は約5秒減る）、配布済みの本体には届かない。

## 作る前に確かめること

1. **`nvs` の実際の空き**: 試験機で `nvs_get_stats` を呼び、使用中と空きの枠数を起動時のログに出す。上の見積もりをこの数字で置き換える。
2. **登録する回の返事の遅れ**: 道具を呼ぶと LLM とのやり取りが1往復増えることがある。実機で測る。
3. **登録の加減**: 何でも登録する・全然登録しないのどちらにも振れ得る。試験機で数日使って中身を見る。項目数の上限と、いっぱいのときの書き換え方を決める。
4. **既定の LLM が道具を安定して呼ぶか**（`toytalker-llms` の `is_default` の行）。

## 残る論点

- **覚えた項目は毎回 LLM の事業者へ送られる**。プライバシーポリシーに書く（[販売の準備](sales-readiness.md) の B・C）。
- **間違いを覚える**: ごっこ遊びの話や聞き間違いが「事実」として残る。保護者が消せることと「忘れる」道具で受ける。
- **フラッシュは暗号化していない**（[先送り項目](deferred-items.md) の「Secure Boot と Flash Encryption」は見送り中）。本体を手に取って USB で読めば覚えた項目が出る。被害がその1台に閉じる点は変わらないが、「本体には会話に関する情報が無い」という前提は変わる。
- **保護者が「今回の会話」も見られるようにするか**: 本体は直近5往復を RAM に持つ。起動中だけ見られる形にはできるが、BLE 設定に入るときに RAM の中身が残るかは未確認。会話を見る機能そのものは [先送り項目](deferred-items.md) の「親が会話を見る機能」。
