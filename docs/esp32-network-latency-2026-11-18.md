# 回線ごとの速さの違いを ESP32 で測った（2026-11-18）

自宅 Wi-Fi・テザリング・レンタル Wi-Fi 2種で、会話の速さと音の途切れがどう違うかを実機で測った記録。入口は [ESP32ファーム](esp32-firmware.md)。

## 結論

- **分かれ目は回線の会社でも Wi-Fi ルーターの機種でもなく、往復時間の短さと揺れの小ささ**（利用者と合意した見立て。下の「なぜ差が出るか」は推測を含む）。
- **聞こえる途切れが出たのは、にゃんこ Wi-Fi だけ**。5G CONNECT・テザリング・自宅では、途切れの回数（`underruns`）は数えられているのに、利用者には一度も聞こえなかった。
- **`underruns` の回数は、聞こえる途切れの指標としては粗い**。数えられた途切れはどの回線でも返答の1文目の冒頭に集まっていて、止まった長さは記録していない。
- **アプリより遅く感じる分のうち、ファームで縮められるのは TLS の約 0.6 秒と相槌の待ち（入ると 0.8〜1.7 秒）**。サーバーが最初の文を作る約 1.5 秒はアプリと同じ。
- 測ったのは各回線とも1か所（自宅の室内）・1回だけ。5G CONNECT とにゃんこはレンタルで、計測後に返却したので測り直せない。

## 測った条件

| 項目 | 内容 |
|---|---|
| 本体 | v0.3 基板、`90:da:72:7a:25:a4`、ファーム 0.7.35 |
| 自宅 | 光回線の Wi-Fi。本体から見た電波は −78〜−80 dBm（弱い） |
| テザリング | iPhone、LINEMO（ソフトバンクの回線） |
| 5G CONNECT | レンタルの WiMAX +5G ルーター（au 系） |
| にゃんこ | レンタルのクラウド SIM ルーター |
| モバイル3回線の電波 | ルーターを本体のそばに置いた。−23〜−32 dBm（最強クラス） |
| 相手 | RnD（`api-rnd.zakicorp.com` の `/chat-mcu`、声は ElevenLabs） |

測り方は2つ。

1. **計測スケッチでの自動計測**（`devices/mcu/esp32_s3/net_latency_test/`）。各回線で接続の計測 20 回と、決まった文での1ターン 5 回。失敗は 0。
2. **会話ファーム 0.7.35 で利用者が実際に話す**。にゃんこ 3 ターン、5G CONNECT 3 ターン、テザリング 4 ターン、自宅 3 ターン。

## 自動計測の結果（中央値）

| 回線 | TCP 接続（API） | TLS（API） | TCP 接続（Soniox） | TLS（Soniox） | 最初の音 | 鳴り始め | 受信の速さ |
|---|---|---|---|---|---|---|---|
| 自宅 | 9 ms | 303 ms | 10 ms | 1,181 ms | 1,559 ms | 1,608 ms | 2,778 kbps |
| テザリング | 46 ms | 387 ms | 46 ms | 1,248 ms | 1,681 ms | 1,812 ms | 1,360 kbps |
| 5G CONNECT | 192 ms（遅い1割は 352 ms） | 577 ms | 54 ms | 1,390 ms | 1,725 ms | 1,955 ms | 763 kbps |
| にゃんこ | 47 ms（遅い1割は 202 ms） | 589 ms | 45 ms | 1,436 ms | 2,070 ms | 2,262 ms | 919 kbps |

- 「最初の音」「鳴り始め」は要求の TLS を張り始めてからの時間。「鳴り始め」は 0.34 秒ぶん溜まった時点（スケッチは実際には鳴らさず計算で出す）。
- 「受信の速さ」は最初の音から最後の音までで割った値。サーバーが次の文を作る待ちを含むので、回線の実力より低く出る。再生に必要なのは 384 kbps。
- 計算上の途切れは、どの回線でも 0 回だった。**スケッチは会話ファームの1文目の途切れを再現しない**。
- TLS は往復が 9 ms の自宅でも API 宛 0.3 秒、Soniox 宛 1.2 秒かかる。回線ではなく本体の暗号計算の時間。
- **5G CONNECT は API 宛（CloudFront）の接続だけが遅く、Soniox 宛は 54 ms で他の回線と同じ**。理由は分かっていない。

### 途切れの回数と、聞こえた途切れ

- `[PLAYER] underrun` は、どの回線でも返答の1文目に出ていた（自宅 1・1 回、5G CONNECT 2 回、テザリング 1・3・2・2 回、にゃんこ 5 回と 3 回。にゃんこの3ターン目だけ2文目にも 1 回）。
- 1文目は 0.34 秒ぶん溜まった直後で溜めが薄く、同じ頃に Soniox の先行接続も動いている。
- 文の受信が再生より遅かったのは、にゃんこの2ターン目の1文目だけ（2.1 秒の音声を受け取るのに 2.3 秒）。利用者に聞こえた途切れと合う。
- 文ごとの受信の速さ（`[PCM_TIMING]` から。中央値 / 最小）:

| 回線 | 中央値 | 最小 | 必要量（384 kbps）の何倍か |
|---|---|---|---|
| 自宅 | 1,079 kbps | 929 kbps | 2.8 倍 |
| 5G CONNECT | 598 kbps | 523 kbps | 1.6 倍 |
| テザリング | 565 kbps | 462 kbps | 1.5 倍 |
| にゃんこ | 541 kbps | 485 kbps | 1.4 倍 |

返答全体で割ると、どの回線も再生の 1.0〜1.3 倍に見える。これはサーバーが次の文を作る待ちと、本体の再生バッファ（5.4 秒ぶん）が満杯で受信を止める待ちが混ざるためで、回線の比較には使えない。

### 「アプリより遅い」の内訳（自宅、待ちなしのターン）

送信を決めてから鳴り始めるまで約 2.5 秒。

| 区間 | 時間 | 縮められるか |
|---|---|---|
| TLS 接続 | 0.63〜0.67 秒 | [ロードマップ](roadmap.md) 39（未着手） |
| サーバーの最初の文（LLM と TTS） | 約 1.5 秒 | アプリと同じ。ファームでは縮まらない |
| 溜めてから鳴らす | 0.05〜0.25 秒 | ほぼ下限 |

- モバイル回線の TLS は 0.67〜0.95 秒で、回線が遅いほど 39 が効く。
- **相槌の取得待ち**が 13 ターン中 4 ターンに入り、0.8〜1.7 秒かかった（にゃんこ 2 回、5G CONNECT 1 回、自宅 1 回、テザリング 0 回）。「相槌の取得を待たずに本文を送る」案は [ESP32ファーム](esp32-firmware.md) の「本体側の計測を次の要求に添える」の項に前からあり、ロードマップの項目にはなっていない。
- 送信を決める前には、話し終わりの判定（Soniox 側。自宅の3ターンで 0.16〜1.66 秒）と猶予 0.6 秒がある。今回は調べていない。

## なぜ差が出るか（推測）

確認した事実は1つ。**本体の TCP の受信の枠は 5,760 バイトで固定**（コア 3.3.11 の `esp32s3-libs` の `CONFIG_LWIP_TCP_WND_DEFAULT`。枠を広げる設定は入っていない）。

ここから先は推測。

- サーバーは 5,760 バイト送るごとに本体の応答を待つので、受信の上限は「5,760 バイト ÷ 往復時間」になる。往復 9 ms で約 5,100 kbps、46 ms で約 1,000 kbps、120 ms で再生ぎりぎりの 384 kbps、200 ms で約 230 kbps。
- にゃんこは普段の往復が 47 ms でも、遅いときは 202 ms まで伸びる。その瞬間は上限が再生を下回るので、聞こえる途切れになったと見ている。
- 会話ファームは、1往復ごとに本体側で約 0.035 秒余計にかかっているように見える。文の受信の速さから逆算した1往復の時間から回線の往復を引くと、自宅 34 ms・テザリング 36 ms・にゃんこ 38 ms でほぼ同じになる。受信の取り出しが、再生・マイク・Soniox の先行接続と CPU を分け合って遅れている可能性がある。コードは追っていない。
- **5G CONNECT はこの式に合わない**。API 宛の接続は 192 ms なのに、会話中は 598 kbps 出ていた（式どおりなら約 240 kbps）。接続の瞬間だけ遅く、流れ始めると往復が短い、という型に見える。
- アプリ（スマホ）は受信の枠が大きく、TLS も使い回せて計算も速いので、往復時間の影響を受けにくい。
- 回線の往復時間を決めるものは、契約の種類（キャリア本体の回線か、他社の回線を借りるクラウド SIM か）、その場所での電波のつかみ、時間帯の混み具合だと考えている。今回のデータでは切り分けていない。

## 次にやるなら

- **止まった長さを記録する**。`underruns` の回数ではなく、止まった合計の ms を `[TURN_REPORT]` と `device.prev` に足せば、聞こえる途切れと合うはず（未着手、ロードマップに無い）。
- **往復時間を続けて測る**。計測スケッチに足し、受信の速さと並べれば上の推測を確かめられる。
- **同じ回線を別の場所・別の時間で測る**。会社・機種・場所のどれが効くかを切り分けるにはこれが要る。

## 計測スケッチの使い方

`devices/mcu/esp32_s3/net_latency_test/net_latency_test.ino`。シリアルから1行の命令を送ると、結果を `[NET] {JSON}` の行で返す。

| 命令 | 動き |
|---|---|
| `L <名前>` | 以後の結果に付けるラベル |
| `J` / `J <SSID>⇥<パスワード>` | 本体に保存済みの Wi-Fi へ接続 / 指定の Wi-Fi へ接続（保存しない） |
| `H <回数>` | API と Soniox への DNS・TCP・TLS の時間（要求は送らない） |
| `T <回数>` | 決まった文で `/chat-mcu` へ1ターン（`fw:"net-test"`、セッション `net-test-…`。RnD に課金が発生する） |
| `W <SSID>⇥<パスワード>` | 会話ファームが使う Wi-Fi 設定を書き換える（元の設定は本体内に1回だけ退避） |
| `R` | 退避した Wi-Fi 設定へ戻す |
| `S` | 状態 |

Wi-Fi のパスワードはスケッチにもリポジトリにも書かない。シリアルから渡す。

### 会話ファームを消さずに書いて、元に戻す手順

本体の会話ファームは app0 に入れたまま、空いている app1 に計測スケッチを書いて起動先だけ切り替えた。フラッシュ全体の読み出しは esptool が途中で止まるので（約 1.1MB 付近）、全体の退避には頼らない。

1. otadata（`0xE000`、`0x2000` バイト）を読んで退避する。
2. 計測スケッチの .bin を app1（`0x1D0000`）へ書く。
3. 起動先を app1 にした otadata を書く（2つ目の区画に連番 2 と、その CRC を入れる）。
4. 終わったら、退避した otadata を書き戻し、app1 を消す。起動ログが `running=app0` で元の版になっていることを確かめる。

OTA で app1 に版が入っている本体では、この手順は app1 の版を上書きする。先に otadata でどちらが動いているかを確かめること。今回の本体は app1 が空だった。
